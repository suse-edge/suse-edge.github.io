SUSE Telco Cloud es una plataforma diseñada para alojar aplicaciones Telco modernas, nativas de nube, a escala, desde el kernel hasta el edge.

Esta página explica la arquitectura y los componentes utilizados en SUSE Telco Cloud.

== Componentes

Existen dos bloques diferentes, la pila de gestión y la pila de tiempo de ejecución:

* *Pila de gestión*: Esta es la parte de SUSE Telco Cloud que se utiliza para gestionar el aprovisionamiento y el ciclo de vida de las pilas de tiempo de ejecución. gracias a los siguientes componentes:
  ** Gestión de clústeres múltiples en entornos de nube pública y privada con <<components-rancher,Rancher>>
  ** Soporte para equipo sin sistema operativo con <<components-metal3,Metal^3^>>, <<components-metallb,MetalLB>> y proveedores de infraestructura `CAPI` (Cluster API)
  ** Aislamiento integral de inquilinos e integraciones de `IDP` (proveedor de identidad)
  ** Amplio mercado de integraciones y extensiones de terceros
  ** API neutral respecto al proveedor y rico ecosistema de proveedores
  ** Control de las actualizaciones transaccionales de SUSE Linux Micro
  ** Motor GitOps para gestionar el ciclo de vida de los clústeres mediante repositorios Git con <<components-fleet,Fleet>>

* *Pila de tiempo de ejecución*: Esta es la parte de SUSE Telco Cloud que se utiliza para ejecutar las cargas de trabajo.
  ** <<components-rke2,RKE2>> sirve como la distribución de Kubernetes ligera y reforzada en seguridad, optimizada para entornos de telecomunicaciones edge y centrados en el cumplimiento.
  ** (Opcional) <<components-suse-security,SUSE Security>> para habilitar funciones de seguridad como el escaneo de vulnerabilidades de imágenes, la inspección profunda de paquetes y el control automático del tráfico intraclúster.
  ** (Opcional) Almacenamiento en bloques con <<components-suse-storage,SUSE Storage>> para habilitar una forma sencilla y fácil de utilizar una solución de almacenamiento nativo de nube.
  ** Sistema operativo optimizado con <<components-slmicro,SUSE Linux Micro>> para habilitar un SO seguro, ligero e inmutable (sistema de archivos transaccional) para ejecutar contenedores. SUSE Linux Micro está disponible en arquitecturas {aarch64} y {x86-64}, y también es compatible con `Real-Time Kernel` para casos de uso de telecomunicaciones y edge.

== Modelo de despliegue

SUSE Telco Cloud sigue un modelo de despliegue de dos etapas: el clúster de gestión se despliega utilizando una imagen generada por <<components-eib,Edge Image Builder>>, y los clústeres en sentido descendente se aprovisionan mediante el aprovisionamiento de red dirigido. Este capítulo ofrece una visión general de este modelo de despliegue, ya que es el enfoque recomendado y compatible para los entornos de SUSE Telco Cloud.

=== ¿Por qué este modelo de despliegue?

El clúster de gestión es un despliegue único en una sola ubicación. El aprovisionamiento basado en imágenes agrupa todos los componentes en una única imagen arrancable. De este modo, el clúster de gestión se iniciará por sí mismo, lo que requiere una complejidad operativa mínima. Es la forma más sencilla y directa de ponerlo en marcha.

Los clústeres descendentes, sin embargo, son otra historia. En entornos de telecomunicaciones, se despliegan a gran escala en muchos centros de datos y en sitios edge, a menudo sin disponer de experiencia técnica in situ. El aprovisionamiento de red dirigido está diseñado para esto: requiere que los servidores de destino admitan una interfaz de gestión fuera de banda como Redfish, a través de la cual el clúster de gestión enciende, inspecciona y aprovisiona de forma remota los nodos bare-metal sin ninguna intervención in situ.

Integrar toda la configuración específica del clúster en una imagen de arranque, como requeriría el aprovisionamiento basado en imágenes, significa que cada variación del sitio exige una imagen diferente, y cualquier cambio de configuración requiere reconstruir y redistribuir las imágenes en todos los sitios. El aprovisionamiento de red dirigido resuelve esto manteniendo la imagen del SO genérica y gestionando toda la configuración específica del clúster, incluidos los perfiles de red, Kubernetes y Telco, desde el clúster de gestión en el momento del aprovisionamiento. Los operadores simplemente instalan en rack, encienden y conectan el hardware, y el clúster de gestión se encarga del resto.

Esta separación también permite una integración completa de GitOps. Dado que toda la definición del clúster en sentido descendente se expresa como manifiestos de Cluster API, puede almacenarse en Git y ser reconciliada por Fleet en todos los sitios, lo que hace que las operaciones de aprovisionamiento, configuración y ciclo de vida sean totalmente auditables y repetibles sin intervención manual.
