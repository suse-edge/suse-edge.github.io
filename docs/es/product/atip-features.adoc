[#kernel-image-for-real-time]
== Imagen del núcleo de Linux para tiempo real

La imagen del núcleo de Linux en tiempo real no es necesariamente mejor que un núcleo de Linux estándar.
Es un núcleo de Linux diferente ajustado para un caso de uso específico. El núcleo de Linux en tiempo real está ajustado para una menor latencia a costa del rendimiento. El núcleo de Linux en tiempo real no se recomienda para un uso de propósito general, pero en nuestro caso, es el núcleo recomendado para cargas de trabajo de telecomunicaciones donde la latencia es un factor clave.

Existen cuatro características principales:

* Ejecución determinista:
+
Obtenga una mayor previsibilidad: garantice que los procesos comerciales críticos se completen a tiempo en cada ocasión y ofrezca un servicio de alta calidad, incluso bajo cargas de sistema elevadas. Al proteger los recursos clave del sistema para procesos de alta prioridad, puede garantizar una mayor previsibilidad para las aplicaciones sensibles al tiempo.
+
* Bajo jitter:
+
El bajo jitter, basado en la tecnología altamente determinista, ayuda a mantener las aplicaciones sincronizadas con el mundo real. Esto ayuda a los servicios que necesitan cálculos continuos y repetidos.
+
* Herencia de prioridad:
+
La herencia de prioridad se refiere a la capacidad de un proceso de baja prioridad para adquirir una prioridad mayor cuando un proceso de mayor prioridad requiere que este finalice antes de poder completar su tarea. SUSE Linux Enterprise Real Time resuelve estos problemas de inversión de prioridad para procesos de misión crítica.
+
* Interrupciones de hilos:
+
Los procesos que se ejecutan en modo de interrupción en un sistema operativo de propósito general no pueden ser interrumpidos. Con SUSE Linux Enterprise Real Time, estas interrupciones han sido encapsuladas por hilos del núcleo de Linux, que son interrumpibles y permiten que las interrupciones de hardware y software sean interrumpidas por procesos de mayor prioridad definidos por el usuario.
+
En nuestro caso, si ha instalado una imagen de tiempo real como `SUSE Linux Micro RT`, ya está instalado el núcleo de Linux en tiempo real. Desde el https://scc.suse.com/[SUSE Customer Center], puede descargar la imagen del núcleo de Linux en tiempo real.
+

[NOTE]
====
Para obtener más información sobre el núcleo de Linux en tiempo real, visite https://www.suse.com/products/realtime/[SUSE Real Time].
====

[#kernel-args]
== Argumentos del núcleo de Linux para baja latencia y alto rendimiento.

Configurar los argumentos adecuados del núcleo de Linux es esencial para optimizar el rendimiento, lograr una baja latencia y garantizar el despliegue exitoso del clúster para cargas de trabajo de telecomunicaciones. Aunque algunos parámetros están diseñados específicamente para permitir que el núcleo de Linux en tiempo real funcione de manera óptima, esta sección se aplica tanto a las configuraciones del núcleo en tiempo real como a las predeterminadas. Además, ciertos argumentos son obligatorios para que el método de aprovisionamiento de red dirigida despliegue correctamente los nodos de clúster en sentido descendente.

* Elimine `kthread_cpus` cuando utilice el núcleo de Linux en tiempo real de SUSE. Este parámetro controla en qué CPU se crean los hilos del núcleo de Linux. También controla qué CPU se permiten para el PID 1 y para cargar módulos del núcleo de Linux (el asistente de espacio de usuario kmod). Este parámetro no se reconoce y no tiene ningún efecto.

* Aísle los núcleos de CPU utilizando `isolcpus`, `nohz_full`, `rcu_nocbs` y `irqaffinity`. Para obtener una lista completa de las técnicas de fijación de CPU, consulte el capítulo <<cpu-pinning-host,CPU Pinning on Host>>.

* Añada los indicadores `domain,nohz,managed_irq` al argumento del núcleo de Linux `isolcpus`. Sin ningún indicador, `isolcpus` equivale a especificar solo el indicador `domain`. Esto aísla las CPU especificadas de la programación, incluidas las tareas del núcleo de Linux. El indicador `nohz` detiene el tick del planificador en las CPU especificadas (si solo hay una tarea ejecutable en una CPU), y el indicador `managed_irq` evita el enrutamiento de interrupciones externas (de dispositivo) gestionadas en las CPU especificadas. Tenga en cuenta que las líneas IRQ de los dispositivos NVMe están totalmente gestionadas por el núcleo de Linux y, como consecuencia, se enrutarán a los núcleos no aislados (de mantenimiento). Por ejemplo, la línea de comandos proporcionada al final de esta sección dará como resultado que solo se asignen cuatro colas (más una cola de administración/control) en el sistema:

+
[,shell]
----
for I in $(grep nvme0 /proc/interrupts | cut -d ':' -f1); do cat /proc/irq/${I}/effective_affinity_list; done | column
39      0       19      20      39
----
+
Este comportamiento evita cualquier interrupción causada por la E/S de disco en cualquier aplicación sensible al tiempo que se ejecute en los núcleos aislados, pero podría requerir atención y un diseño cuidadoso para las cargas de trabajo centradas en el almacenamiento.

* Ajuste los ticks (interrupciones periódicas del temporizador del núcleo de Linux):
** `skew_tick=1`: los ticks a veces pueden ocurrir simultáneamente. En lugar de que todas las CPU reciban su tick de temporizador en el mismo momento exacto, `skew_tick=1` hace que ocurran en momentos ligeramente desplazados. Esto ayuda a reducir la inestabilidad del sistema, lo que resulta en tiempos de respuesta de interrupción más consistentes y bajos (un requisito esencial para aplicaciones sensibles a la latencia).
** `nohz=on`: detiene el tick periódico del temporizador en las CPUs inactivas.
** `nohz_full=<cpu-cores>`: Detiene el tick periódico del temporizador en las CPUs especificadas que están dedicadas a aplicaciones en tiempo real.

* Deshabilite la gestión de Machine Check Exception (MCE) especificando `mce=off`. Las MCE son errores de hardware detectados por el procesador y deshabilitarlas puede evitar registros ruidosos.

* Añada `nowatchdog` para deshabilitar el watchdog de soft-lockup, que se implementa como un temporizador que se ejecuta en el contexto de interrupción de hardware del temporizador. Cuando expira (es decir, se detecta un bloqueo suave), imprimirá una advertencia (en el contexto de interrupción de hardware), ejecutando cualquier objetivo de latencia. Incluso si nunca expira, entra en la lista de temporizadores, aumentando ligeramente la sobrecarga de cada interrupción de temporizador. Esta opción también deshabilita el watchdog NMI, por lo que las NMI no pueden interferir.

* `nmi_watchdog=0` deshabilita el watchdog NMI (Non-Maskable Interrupt). Esto puede omitirse cuando se utiliza `nowatchdog`.

* RCU (Read-Copy-Update) es un mecanismo del núcleo de Linux que permite el acceso concurrente y sin bloqueos para muchos lectores a datos compartidos. Una retrollamada RCU, una función activada tras un «período de gracia», garantiza que todos los lectores anteriores hayan terminado para que los datos antiguos puedan recuperarse de forma segura. Ajustamos RCU, especialmente para cargas de trabajo sensibles, para descargar estas retrollamadas de las CPU dedicadas (ancladas), evitando que las operaciones del núcleo de Linux interfieran con tareas críticas y sensibles al tiempo.
** Especifique las CPU ancladas en `rcu_nocbs` para que las retrollamadas RCU no se ejecuten en ellas. Esto ayuda a reducir el jitter y la latencia para las cargas de trabajo en tiempo real.
** `rcu_nocb_poll` hace que las CPUs sin retrollamadas «sondeen» regularmente para ver si se requiere la gestión de retrollamadas. Esto puede reducir la sobrecarga de interrupciones.
** `rcupdate.rcu_cpu_stall_suppress=1` suprime las advertencias de bloqueo de CPU RCU, que a veces pueden ser falsos positivos en sistemas en tiempo real con mucha carga.
** `rcupdate.rcu_expedited=1` acelera el período de gracia para las operaciones RCU, haciendo que las secciones críticas del lado de lectura sean más receptivas.
** `rcupdate.rcu_normal_after_boot=1` Cuando se utiliza con rcu_expedited, permite que RCU vuelva a la operación normal (no acelerada) después del arranque del sistema.
** `rcupdate.rcu_task_stall_timeout=0` deshabilita el detector de bloqueo de tareas RCU, evitando posibles advertencias o detenciones del sistema por tareas RCU de larga duración.
** `rcutree.kthread_prio=99` establece la prioridad del hilo del kernel de retrollamada RCU al valor más alto posible (99), asegurando que se programe inmediatamente para gestionar las retrollamadas rápidamente cuando sea necesario.

* Añadid `ignition.platform.id=openstack` para que Metal^3^ y Cluster API puedan aprovisionar/desaprovisionar el clúster correctamente. Esto es utilizado por el agente Python de Metal^3^, que proviene de OpenStack Ironic.

* Activad https://documentation.suse.com/smart/network/html/network-interface-predictable-naming/index.html[Denominación predecible de interfaces de red] mediante `net.ifnames=1`. A partir de SUSE Linux Micro 6.2, esto está activado por defecto y no se requiere una configuración explícita. Para versiones anteriores a la 6.2, esto debe establecerse explícitamente como un argumento del kernel. Esto se alinea con la configuración `predictableNicNames` en el gráfico de Helm de Metal^3^ del clúster de gestión, que es necesaria para que el aprovisionamiento de red dirigida funcione correctamente. La denominación coherente de las interfaces también es fundamental cuando se utiliza SR-IOV.

* Eliminad `intel_pstate=passive`. Esta opción configura `intel_pstate` para que funcione con gobernadores cpufreq genéricos, pero para que esto funcione, desactiva como efecto secundario los estados P gestionados por hardware (`HWP`). Para reducir la latencia del hardware, no se recomienda esta opción para cargas de trabajo en tiempo real.

* Sustituya `intel_idle.max_cstate=0 processor.max_cstate=1` por `idle=poll`. Para evitar las transiciones de estado C, se utiliza la opción `idle=poll` para desactivar dichas transiciones y mantener la CPU en el estado C más alto. La opción `intel_idle.max_cstate=0` desactiva `intel_idle`, por lo que se utiliza `acpi_idle`, y `acpi_idle.max_cstate=1` establece entonces el estado C máximo para acpi_idle.
En arquitecturas {x86-64}, el primer estado C ACPI es siempre `POLL`, pero utiliza una función `poll_idle()`, que puede introducir una pequeña latencia al leer el reloj periódicamente y reiniciar el bucle principal en `do_idle()` tras un tiempo de espera (esto también implica borrar y establecer el indicador de tarea `TIF_POLL`).
Por el contrario, `idle=poll` se ejecuta en un bucle continuo, en espera activa de que se reprograme una tarea. Esto minimiza la latencia de salida del estado de inactividad, pero a costa de mantener la CPU funcionando a máxima velocidad en el hilo de inactividad.

* Desactivad C1E en la BIOS. Esta opción es importante para desactivar el estado C1E en la BIOS y evitar que la CPU entre en el estado C1E cuando está inactiva. El estado C1E es un estado de bajo consumo que puede introducir latencia cuando la CPU está inactiva.

El resto de esta documentación cubre parámetros adicionales, incluyendo páginas enormes (huge pages) e IOMMU.

Esto proporciona un ejemplo de argumentos del kernel para un servidor Intel de 32 núcleos, incluyendo los ajustes mencionados anteriormente:

----

[#cpu-pinning-host]
== Fijación de CPU en el host

La fijación de CPU, también conocida como afinidad de procesador, es la técnica de vincular un proceso o hilo a un núcleo de CPU específico, evitando que el planificador del sistema operativo lo mueva. Al asegurar que un proceso siempre se ejecute en el mismo núcleo, se beneficia de un acceso más rápido a los datos que permanecen en la memoria caché de ese núcleo. Esta práctica es común en entornos de informática de alto rendimiento porque mejora drásticamente el rendimiento y reduce la sobrecarga.

=== Aislamiento de CPU mediante TuneD
`tuned` es una herramienta de ajuste del sistema que supervisa las condiciones del sistema para optimizar el rendimiento utilizando varios perfiles predefinidos. Una característica clave es su capacidad para aislar núcleos de CPU para cargas de trabajo específicas, como aplicaciones en tiempo real. Esto evita que el sistema operativo utilice estos núcleos y aumente potencialmente la latencia.

Para habilitar y configurar esta función, lo primero es crear un perfil para los núcleos de CPU que queremos aislar. En este ejemplo, de entre 64 núcleos, dedicamos 60 núcleos (`1-30,33-62`) a las aplicaciones y los 4 núcleos restantes se utilizan para tareas de mantenimiento. Tened en cuenta que el diseño de las CPU aisladas depende en gran medida de las aplicaciones en tiempo real.

[,shell]
----
$ echo "export tuned_params" >> /etc/grub.d/00_tuned

$ echo "isolated_cores=1-30,33-62" >> /etc/tuned/cpu-partitioning-variables.conf

$ tuned-adm profile cpu-partitioning
Tuned (re)started, changes applied.
----

=== Aislamiento de CPU mediante argumentos del kernel
A continuación, debemos modificar la opción de GRUB para aislar los núcleos de CPU y otros parámetros importantes para el uso de la CPU.
Las siguientes opciones son importantes para personalizarlas con vuestras especificaciones de hardware actuales:

[,shell]

|===
| parameter | valor | description

| isolcpus
| domain,nohz,managed_irq,1-30,33-62
| Aislad los núcleos 1-30 y 33-62. `domain` indica que estas CPU forman parte del dominio de aislamiento. `nohz` habilita el funcionamiento sin tick en estas CPU aisladas cuando están inactivas, para reducir las interrupciones. `managed_irq` aísla las CPU fijadas para que no sean objetivo de las IRQ. Esto contempla `irqaffinity=0-7`, que ya dirige la mayoría de las IRQ a los núcleos de mantenimiento.

| skew_tick
| 1
| Esta opción permite al kernel sesgar las interrupciones del temporizador a través de las CPU aisladas.

| nohz
| on
| Cuando está habilitado, la interrupción periódica del temporizador del kernel (el 'tick') se detiene en cualquier núcleo de CPU que quede inactivo. Esto beneficia principalmente a las CPU de mantenimiento (`0,31,32,63`), conservando energía y reduciendo las activaciones innecesarias en esos núcleos de propósito general.

| nohz_full
| 1-30,33-62
| Para los núcleos aislados, esto detiene el tick y lo hace incluso cuando la CPU está ejecutando una única tarea activa. Significa que hace que la CPU funcione en modo sin tick completo (o 'dyntick'). El kernel solo enviará interrupciones de temporizador cuando sean realmente necesarias.

| rcu_nocbs
| 1-30,33-62
| Esta opción descarga el procesamiento de retrollamadas RCU de núcleos de CPU especificados.

| rcu_nocb_poll
| 
| Cuando esta opción está establecida, las CPU sin retrollamadas RCU realizarán un sondeo periódico para ver si se requiere el manejo de retrollamadas, en lugar de ser despertadas explícitamente por otras CPU. Esto puede reducir la sobrecarga de interrupciones.

| irqaffinity
| 0,31,32,63
| Esta opción permite al kernel ejecutar las interrupciones en los núcleos de mantenimiento.

| inactivo
| poll
| Esto minimiza la latencia de salida del estado de inactividad, pero a costa de mantener la CPU funcionando a máxima velocidad en el hilo de inactividad.

| nmi_watchdog
| 0
| Esta opción deshabilita solo el watchdog NMI. Esto puede omitirse cuando `nowatchdog` está establecido.

| nowatchdog
|
| Esta opción deshabilita el watchdog de soft-lockup, que se implementa como un temporizador que se ejecuta en el contexto de interrupción de hardware del temporizador.
|===

Los siguientes comandos modifican la configuración de GRUB y aplican los cambios mencionados anteriormente para que estén presentes en el próximo arranque:

Editad el archivo `/etc/default/grub` con los parámetros anteriores y el archivo quedará así:

[,shell]
----
GRUB_CMDLINE_LINUX="BOOT_IMAGE=/boot/vmlinuz-6.4.0-9-rt root=UUID=77b713de-5cc7-4d4c-8fc6-f5eca0a43cf9 skew_tick=1 rd.timeout=60 rd.retry=45 console=ttyS1,115200 console=tty0 default_hugepagesz=1G hugepagesz=1G hugepages=40 hugepagesz=2M hugepages=0 ignition.platform.id=openstack net.ifnames=1 intel_iommu=on iommu=pt irqaffinity=0,31,32,63 isolcpus=domain,nohz,managed_irq,1-30,33-62 nohz_full=1-30,33-62 nohz=on mce=off nosoftlockup nowatchdog nmi_watchdog=0 quiet rcu_nocb_poll rcu_nocbs=1-30,33-62 rcupdate.rcu_cpu_stall_suppress=1 rcupdate.rcu_expedited=1 rcupdate.rcu_normal_after_boot=1 rcupdate.rcu_task_stall_timeout=0 rcutree.kthread_prio=99 security=selinux selinux=1 idle=poll"
----

Actualizad la configuración de GRUB:
[,shell]
----
$ transactional-update grub.cfg
$ reboot
----

Para validar que los parámetros se aplican después del reinicio, se puede utilizar el siguiente comando para comprobar la línea de comandos del kernel:

[,shell]
----
$ cat /proc/cmdline
----

Existe otro script que se puede utilizar para ajustar la configuración de la CPU y los parámetros de red, que básicamente realiza los siguientes pasos:

* Estableced el gobernador de CPU en `performance`.
* Desactivad la migración del temporizador a las CPU aisladas.
* Migrad los hilos kdaemon a las CPU de mantenimiento.
* Ajustad la latencia de las CPU aisladas al valor más bajo posible.
* Retrasad las actualizaciones de vmstat a 300 segundos.
* Configurad los parámetros de ajuste de red para un rendimiento óptimo.

El script está disponible en https://raw.githubusercontent.com/suse-edge/telco-cloud-examples/refs/heads/{release-tag-telco-cloud}/telco-examples/downstream-clusters/dhcp-less/eib/custom/files/performance-settings.sh[el repositorio de ejemplos de SUSE Telco Cloud].

[#cpu-pinning-k8s]
== Fijación de CPU en Kubernetes

=== Versiones de RKE2 < v1.32
Habilitad la fijación de CPU en vuestro clúster RKE2 editando el archivo de configuración de RKE2. Añadid los siguientes argumentos de kubelet en el archivo `/etc/rancher/rke2/config.yaml`. Aseguraos de especificar los núcleos de CPU de mantenimiento en los argumentos `kubelet-reserved` y `system-reserved`:

[,yaml]
----
kubelet-arg:
- "cpu-manager-policy=static"
- "cpu-manager-policy-options=full-pcpus-only=true"
- "cpu-manager-reconcile-period=0s"
- "kubelet-reserved=cpu=0,31,32,63"
- "system-reserved=cpu=0,31,32,63"
----

=== Versiones de RKE2 >= v1.32
Si vuestra versión de RKE2 es v1.32 o superior, no se pueden utilizar argumentos de línea de comandos para configurar kubelet, siguiendo la práctica de Kubernetes upstream. Para configurar la fijación de CPU, es necesario crear un archivo de configuración de kubelet. Consultad la https://documentation.suse.com/cloudnative/rke2/latest/en/install/configuration.html#_kubelet_configuration[documentación de RKE2].

Cread un nuevo archivo de configuración de kubelet como `01-cpu-pinning.conf` y colocadlo en el directorio `/var/lib/rancher/rke2/agent/etc/kubelet.conf.d/`:

[,yaml]
----
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
cpuManagerPolicy: static
reservedSystemCPUs: 0,31,32,63
topologyManagerPolicy: single-numa-node
----

Para que los cambios de configuración surtan efecto, es necesario reiniciar el servicio RKE2 correspondiente (servidor o agente). Esta acción interrumpirá brevemente el servicio RKE2 en el host. Ejecute solo uno de los siguientes comandos, dependiendo del tipo de nodo:

[,shell]
----
# If the node is RKE2 agent
systemctl restart rke2-agent
# Else if the node is RKE2 server
systemctl restart rke2-server
----

=== Desplegar cargas de trabajo aprovechando CPUs con afinidad

Existen tres formas de utilizar la función mediante la `Static Policy` definida en kubelet, dependiendo de las solicitudes y límites que defina en su carga de trabajo:

1. Clase de QoS `BestEffort`: Si no define ninguna solicitud o límite para `CPU`, el pod se programa en la primera `CPU` disponible en el sistema.
+
Un ejemplo de uso de la clase de QoS `BestEffort` podría ser:
+
[,yaml]
----
spec:
  containers:
  - name: nginx
    image: nginx
----
+
2. Clase de QoS `Burstable`: Si define una solicitud de CPU que no es igual a los límites, o si no hay ninguna solicitud de CPU.
+
Ejemplos de uso de la clase de QoS `Burstable` podrían ser:
+
[,yaml]
----
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
      requests:
        memory: "100Mi"
----
+
O bien
+
[,yaml]
----
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "2"
      requests:
        memory: "100Mi"
        cpu: "1"
----
+
3.  Clase de QoS `Guaranteed`: Si define una solicitud de CPU que es igual a los límites.
+
Un ejemplo de uso de la clase de QoS `Guaranteed` podría ser:
+
[,yaml]
----
spec:
  containers:
    - name: nginx
      image: nginx
      resources:
        limits:
          memory: "200Mi"
          cpu: "2"
        requests:
          memory: "200Mi"
          cpu: "2"
----


[#network-parameters]
== Parámetros de red

El ajuste de red es esencial para lograr un rendimiento óptimo en las cargas de trabajo de telecomunicaciones. El script performance-settings.sh incluye una función `configure_network_tuning` que establece varios parámetros de red del kernel para optimizar los tamaños de búfer, el procesamiento de paquetes y el rendimiento de UDP.

[NOTE]
====
Los valores de ajuste de red proporcionados son ejemplos que han sido probados y validados. Sin embargo, deben adaptarse a su caso de uso específico, a los requisitos de la carga de trabajo y a la configuración del hardware.
====

Los siguientes parámetros de red son configurados por el script:

=== Parámetros de red principales

* `net.core.rmem_max` (1342177280 bytes): Tamaño máximo del búfer de recepción de socket. Este parámetro establece la cantidad máxima de memoria que se puede asignar para recibir datos en cualquier socket.

* `net.core.wmem_max` (516777216 bytes): Tamaño máximo del búfer de socket de envío. Este parámetro establece la cantidad máxima de memoria que se puede asignar para enviar datos en cualquier socket.

* `net.core.rmem_default` (10000000 bytes): Tamaño predeterminado del búfer de socket de recepción. Este es el tamaño inicial del búfer para recibir datos en nuevos sockets.

* `net.core.wmem_default` (10000000 bytes): Tamaño predeterminado del búfer de socket de envío. Este es el tamaño inicial del búfer para enviar datos en nuevos sockets.

* `net.core.netdev_max_backlog` (416384 paquetes): Número máximo de paquetes en cola en el lado de entrada cuando la interfaz recibe paquetes más rápido de lo que el núcleo de Linux puede procesarlos. Aumentar este valor ayuda a evitar la pérdida de paquetes durante las ráfagas de tráfico.

* `net.core.optmem_max` (25165824 bytes): Tamaño máximo del búfer auxiliar permitido por socket. Esto afecta al tamaño de los búferes de memoria de opciones.

* `net.core.netdev_budget` (1024 paquetes): Número máximo de paquetes que pueden ser procesados en una ejecución de softirq. Esto ayuda a controlar la utilización de la CPU durante el procesamiento de paquetes.

=== Parámetros específicos de UDP

* `net.ipv4.udp_mem` (11416320 15221760 22832640 páginas): Controla la cantidad de memoria (en páginas) utilizada por UDP. Los tres valores representan:
** Umbral mínimo: Por debajo de esto, UDP no recibe presión
** Umbral de presión: UDP comienza a aplicar presión de memoria
** Umbral máximo: Páginas máximas de memoria para UDP

* `net.ipv4.udp_rmem_min` (16384 bytes): Tamaño mínimo del búfer de recepción para sockets UDP. Garantiza un tamaño de búfer base para la recepción UDP.

* `net.ipv4.udp_wmem_min` (16384 bytes): Tamaño mínimo del búfer de envío para sockets UDP. Garantiza un tamaño de búfer base para la transmisión UDP.

=== Programación en tiempo real

* `kernel.sched_rt_runtime_us` (-1): Desactiva el mecanismo de limitación en tiempo real. Establecer esto en -1 permite a las tareas en tiempo real un tiempo de CPU ilimitado, lo cual es esencial para cargas de trabajo de telecomunicaciones que requieren una latencia determinista.

[IMPORTANT]
====
Estos parámetros se configuran automáticamente al utilizar el script performance-settings.sh del repositorio SUSE Telco Cloud Examples. El script debe integrarse en su proceso de creación de imágenes tal como se describe en la sección <<atip-automated-provisioning,Aprovisionamiento automatizado>>.
====

=== Bond CNI
En términos generales, la vinculación proporciona un método para agregar múltiples interfaces de red en una única interfaz lógica vinculada. Esto se utiliza habitualmente para aumentar la disponibilidad del servicio mediante la introducción de rutas de red redundantes, pero también puede utilizarse para incrementar el ancho de banda con ciertos modos de vinculación.
Los siguientes complementos CNI son compatibles con el complemento Bond CNI en combinación con multus:

* MACVLAN
* Dispositivo host
* SR-IOV

==== Bond CNI con MACVLAN

Usar el Bond CNI con SR-IOV es bastante sencillo. Para más detalles sobre cómo configurar SR-IOV, consultad <<sriov>>. [#sriov]
== SR-IOV

SR-IOV (Single Root I/O Virtualization) permite que un único dispositivo físico, como un adaptador de red, separe sus recursos entre múltiples `PCIe` funciones de hardware. Esto permite el acceso directo a los recursos para diversas aplicaciones.

Proporcionamos dos métodos distintos para desplegar `SR-IOV` en su clúster:

* <<option1-sriov-deviceplugin>>: Este método es compatible tanto con dispositivos de red como con aceleradores vRAN.
* <<option2-sriov-helm>>: Este método automatizado proporciona un despliegue más sencillo. Este método es solo para dispositivos de red.

En casos excepcionales en los que necesite ambas soluciones (usar el Operador de red para dispositivos de red y el Plugin de dispositivo para aceleradores vRAN), debe desplegarlas en espacios de nombres de Kubernetes separados. Esta separación es esencial para evitar conflictos entre ambos despliegues.

El Plugin de dispositivo SR-IOV utiliza un configMap que contiene un archivo JSON para definir qué recursos de hardware debe exponer Kubernetes. Esta configuración se basa en dos conceptos fundamentales: `selectors` (para el descubrimiento de hardware) y `resources` (para la exposición en Kubernetes).

Un `resource` es la entidad con nombre que consumen los pods (p. ej., `rancher.io/intel_fec_5g`). Los recursos pueden definirse como uno de los dos tipos siguientes:

* `accelerator`: Se utiliza para tarjetas aceleradoras vRAN (como ACC100/vRAN Boost).
* `netdevice`: Se utiliza para interfaces de red estándar (NIC).

Define los dispositivos de destino utilizando `selectors` para filtrar el hardware en el nodo:

* `vendors`: `8086` (Intel)
* `devices`: `57c3` (FEC VF), `1889` (NIC VF)
* `drivers`: `vfio-pci`
* `pfNames`: `eno16595np0` (nombre de la interfaz física)

Para tarjetas de red, también puede seleccionar un subconjunto de Funciones Virtuales (VF) a partir de una Función Física:

* `pfNames`: `["eth1#1,2,3,4,5,6"]` o bien `[eth1#1-6]`

Para permitir que los pods soliciten los dispositivos, cada recurso debe tener un nombre, que se compone de un prefijo y un nombre:

* `resourceName`: `pci_sriov_net_bh_dpdk`
* `resourcePrefix`: `rancher.io`

Los pods solicitarían entonces el nombre de recurso combinado: `rancher.io/pci_sriov_net_bh_dpdk`.

[NOTE]
====
Este documento no enumera todos los selectores posibles. Los diferentes tipos de recursos utilizan diferentes conjuntos de selectores. Para obtener detalles completos, consulte el https://github.com/k8snetworkplumbingwg/sriov-network-device-plugin[repositorio del plugin de dispositivos de red SR-IOV].

[#dpdk]
== DPDK

`DPDK` (Data Plane Development Kit) es un conjunto de bibliotecas y controladores para el procesamiento rápido de paquetes. Se utiliza para acelerar las cargas de trabajo de procesamiento de paquetes que se ejecutan en una amplia variedad de arquitecturas de CPU.
El DPDK incluye bibliotecas de plano de datos y controladores de tarjeta de interfaz de red (`NIC`) optimizados para lo siguiente:

1. Un gestor de colas implementa colas sin bloqueo.
2. Un gestor de búferes preasigna búferes de tamaño fijo.
3. Un gestor de memoria asigna grupos de objetos en la memoria y utiliza un anillo para almacenar objetos libres; garantiza que los objetos se distribuyan equitativamente en todos los `DRAM` canales.
4. Los controladores en modo sondeo (`PMD`) están diseñados para funcionar sin notificaciones asíncronas, lo que reduce la sobrecarga.
5. Un marco de paquetes como un conjunto de bibliotecas que sirven de ayuda para desarrollar el procesamiento de paquetes.

Los siguientes pasos mostrarán cómo habilitar `DPDK` y cómo crear `VFs` a partir de `NICs` para que sean utilizados por las interfaces `DPDK`:

* Instale el paquete `DPDK`:

[,shell]

[#acceleration]
== Aceleración vRAN (`Intel ACC100/VRB1/VRB2`)

A medida que los proveedores de servicios de comunicaciones pasan de las redes 4G a las 5G, muchos están adoptando arquitecturas de red de acceso por radio virtualizada (vRAN) para obtener una mayor capacidad de canal y un despliegue más sencillo de servicios y aplicaciones basados en el borde. Las soluciones vRAN están idealmente situadas para ofrecer servicios de baja latencia con la flexibilidad de aumentar o disminuir la capacidad en función del volumen de tráfico en tiempo real y la demanda en la red.

Una de las cargas de trabajo 4G y 5G que requiere más computación es la capa 1 de RAN (`L1`) `FEC`, que resuelve los errores de transmisión de datos en canales de comunicación poco fiables o ruidosos. La tecnología `FEC` detecta y corrige un número limitado de errores en datos 4G o 5G, eliminando la necesidad de retransmisión. Dado que la transacción de aceleración `FEC` no contiene información sobre el estado de la celda, puede virtualizarse fácilmente, lo que permite obtener ventajas de agrupación y una migración sencilla de celdas.

Históricamente, Intel proporcionaba la tarjeta aceleradora vRAN ACC100 para ejecutar rápidamente algoritmos FEC de Layer 1, liberando potencia de procesamiento del host para la CPU principal. Desde entonces, Intel ha integrado esta tecnología directamente en las CPU más recientes, empezando por Sapphire Rapids, bajo el nombre `Intel vRAN Boost` (VRB). Intel vRAN Boost actúa como un acelerador de descarga en la propia CPU, eliminando la necesidad de una tarjeta de hardware independiente. Esta sección detalla la configuración de SUSE Telco Cloud para que las cargas de trabajo aprovechen ACC100 o Intel vRAN Boost.

[#huge-pages]
== Páginas enormes

Cuando un proceso utiliza `RAM`, `CPU` marca la porción exacta utilizada por dicho proceso. Para lograr eficiencia, el `CPU` asigna `RAM` en bloques conocidos como `pages`; el tamaño `page` predeterminado en muchas plataformas es `4 KB`. Las páginas pueden intercambiarse a disco (entre otras operaciones).

Dado que el espacio de direcciones del proceso es virtual, el `CPU` y el sistema operativo deben realizar un seguimiento de qué `pages` pertenecen a cada proceso y dónde está almacenado cada uno. Cuanto mayor sea el número de `pages`, más tiempo se tarda en consultar las asignaciones de memoria. Por ejemplo, un proceso que utiliza `1 GB` de memoria implica 262,144 entradas que comprobar (1 GB / 4 KB). Si cada `page table entry` ocupa 8 bytes, esto resulta en un total de `2 MB` (262,144 * 8) de datos que consultar.

La mayoría de las arquitecturas `CPU` actuales permiten la definición de bloques de `pages` cada uno con un tamaño mayor que el valor `4 KB` predeterminado (siendo `1 GB` y `2 MB` valores típicos admitidos) conocidos como `huge pages`, lo que reduce el número de entradas que el `CPU/Operating System` debe consultar.

* Parámetros del kernel

Para habilitar `huge pages`, debemos añadir los siguientes parámetros del kernel. En este ejemplo, configuramos 40 páginas de `1 GB` de tamaño cada una y 0 páginas de `2 MB` de tamaño cada una, aunque los tamaños de páginas enormes que se deben admitir y la cantidad exacta de páginas para cada uno deben ajustarse según los requisitos de memoria de la aplicación:

|===
| parameter | valor | description

| hugepagesz
| 1 G
| Esta opción permite establecer el tamaño de las «huge pages» en 1 GB

| hugepages
| 40
| Este es el número de «huge pages» solicitado para asignar en el arranque para el tamaño definido justo antes (1 GB)

| hugepagesz
| 2M
| Esta opción permite establecer el tamaño de las «huge pages» en 2 MB

| hugepages
| 0
| Este es el número de «huge pages» solicitado para asignar en el arranque para el tamaño definido justo antes (2 MB)

| default_hugepagesz
| 1 G
| Este es el valor predeterminado para el tamaño de las «huge pages»
|===

Modificad el archivo GRUB `/etc/default/grub` para añadir estos parámetros en `GRUB_CMDLINE_LINUX`:

[,shell]
----
default_hugepagesz=1G hugepagesz=1G hugepages=40 hugepagesz=2M hugepages=0
----

Actualizad la configuración de GRUB y reiniciad el sistema para aplicar los cambios:

[,shell]
----
$ transactional-update grub.cfg
$ reboot
----

Para validar que los parámetros se aplican tras el reinicio, podéis comprobar la línea de comandos:

[,shell]
----
$ cat /proc/cmdline
----

* Uso de páginas enormes

Para usar las páginas enormes, debemos montarlas:

[,shell]
----
$ mkdir -p /hugepages
$ mount -t hugetlbfs nodev /hugepages
----

Desplegad una carga de trabajo de Kubernetes, creando los recursos y los volúmenes:

[,yaml]
----
...
 resources:
   requests:
     memory: "24Gi"
     hugepages-1Gi: 16Gi
     intel.com/intel_sriov_oru: '4'
   limits:
     memory: "24Gi"
     hugepages-1Gi: 16Gi
     intel.com/intel_sriov_oru: '4'
...
----

[,yaml]
----
...
volumeMounts:
  - name: hugepage
    mountPath: /hugepages
...
volumes:
  - name: hugepage
    emptyDir:
      medium: HugePages
...

[#numa-aware-scheduling]
== Planificación consciente de NUMA

El acceso no uniforme a memoria o la arquitectura de memoria no uniforme (`NUMA`) es un diseño de memoria física utilizado en la arquitectura de `SMP` (multiprocesadores), donde el tiempo de acceso a la memoria depende de la ubicación de la memoria en relación con un procesador. Bajo `NUMA`, un procesador puede acceder a su propia memoria local más rápido que a la memoria no local, es decir, a la memoria local de otro procesador o a la memoria compartida entre procesadores.

=== Identificación de nodos NUMA

Para identificar los nodos `NUMA`, utilice el siguiente comando en su sistema:

[,shell]
----
$ lscpu | grep NUMA
NUMA node(s):                       1
NUMA node0 CPU(s):                  0-63
----

[NOTE]
====
Para este ejemplo, solo tenemos un nodo `NUMA` que muestra 64 `CPUs`.

`NUMA` debe estar habilitado en `BIOS`. Si `dmesg` no tiene registros de la inicialización NUMA durante el arranque, es posible que los mensajes relacionados con `NUMA` en el búfer de anillo del kernel se hayan sobrescrito.

[#ptp-configuration]
== Protocolo de tiempo de precisión

[#ptp-introduction]
=== Introducción

El Protocolo de tiempo de precisión (PTP), definido por el estándar IEEE 1588, distribuye tiempo de alta precisión a través de una red de paquetes. Cuando las tarjetas de interfaz de red (NIC) marcan el tiempo de los paquetes PTP en el hardware, se alcanza una precisión de submicrosegundos, mucho más allá de lo que NTP puede ofrecer. En entornos de telecomunicaciones, PTP es un componente básico de las redes de acceso por radio (RAN) 5G, donde las unidades de radio requieren una alineación estricta de fase y tiempo para transmitir correctamente. SUSE Telco Cloud implementa PTP a través del paquete `linuxptp` y se dirige a los perfiles de telecomunicaciones ITU-T G.8275.1 e ITU-T G.8275.2 descritos a continuación.

Un dominio PTP se construye a partir de un pequeño conjunto de funciones de reloj:

* *Grandmaster (GM)*: la fuente principal de tiempo para el dominio. Normalmente está bloqueado a un reloj de referencia de tiempo primario (PRTC), generalmente controlado por un receptor GNSS, y transmite el tiempo hacia los nodos descendentes. La precisión del GM establece el límite de calidad para todo el dominio.
* *Ordinary Clock (OC)*: un nodo final con un único puerto PTP. En un despliegue de telecomunicaciones, actúa como receptor de tiempo, disciplinando su reloj local a partir de un Grandmaster o Boundary Clock en sentido ascendente. Un nodo de computación que ejecuta una carga de trabajo de radio es un OC típico.
* *Boundary Clock (BC)*: un nodo multipuerto que recibe tiempo en un puerto (receptor de tiempo) y lo regenera hacia otros nodos en sus puertos restantes (transmisor de tiempo). La inserción de Boundary Clocks a lo largo de la vía acorta la cadena entre cada OC y la referencia, limitando el error que la red acumularía de otro modo, salto tras salto.

La distinción entre un Ordinary Clock y un Boundary Clock es fundamental al diseñar la topología:

* Un *Ordinary Clock* tiene un *único* puerto PTP y se sitúa en el edge del dominio.
Solo consume tiempo para disciplinar su propio reloj y nunca reenvía el tiempo a otros nodos.
* Un *reloj de contorno* tiene *múltiples* puertos PTP. Consume tiempo en su puerto de receptor de tiempo y lo *regenera* en sus puertos de transmisor de tiempo, terminando la cadena de temporización ascendente e iniciando una nueva cadena descendente. Esta regeneración es lo que evita que el error se acumule a lo largo de una larga cadena de nodos.

Los siguientes elementos de hardware y señalización soportan estas funciones:

* *Reloj de hardware PTP (PHC)*: el reloj integrado en la NIC que PTP sincroniza realmente. Alinear el reloj del sistema operativo con el PHC es un paso independiente gestionado por un daemon dedicado.
* *Ethernet síncrono (SyncE)*: sincronización de frecuencia de capa física. PTP transporta la fase y el tiempo dentro de los paquetes, mientras que SyncE recupera una frecuencia estable directamente de la señal Ethernet. SyncE es una *mejora opcional*: PTP por sí solo ya proporciona fase y tiempo, y SyncE se añade únicamente cuando un nodo necesita una mayor estabilidad de frecuencia y una retención más larga en caso de que la fuente de tiempo PTP se pierda temporalmente.
* *Bucle de enganche de fase digital (DPLL)*: un bloque de temporización de hardware que se engancha a una señal de referencia y la filtra para generar un reloj estable y limpio. Es lo que disciplina el PHC a partir de las entradas disponibles y, en plataformas con más de una NIC, mantiene alineados los diferentes relojes de las NIC.

En cada nodo, estas funciones son llevadas a cabo por los daemons `linuxptp`: `ptp4l` ejecuta el protocolo PTP y disciplina el PHC, y `phc2sys` alinea el reloj del sistema con el PHC. En un Grandmaster, `ts2phc` dirige además el PHC desde la referencia GNSS. Sus funciones e instalación se tratan en <<ptp-prerequisites>>.

El reloj de hardware en sí es gestionado por el subsistema DPLL del kernel de Linux junto con el controlador de red. El grado de control de la temporización, y cómo se distribuye la temporización dentro de un nodo con múltiples NIC, depende de dónde se sitúe el DPLL gestionable:

* *NIC con un DPLL integrado*: el DPLL está integrado en la NIC y se configura a través del subsistema DPLL de Linux. Selecciona y se bloquea en la referencia elegida y disciplina el PHC, proporcionando un control total sobre la frecuencia y el holdover.
* *NIC sin un DPLL integrado*: la NIC no expone ningún DPLL configurable. `ptp4l` disciplina el PHC directamente, y el subsistema puede, como mucho, informar del estado de bloqueo (solo lectura); el manejo avanzado de frecuencia depende entonces de una fuente de temporización externa.
* *DPLL integrado compartido entre varias NICs*: el DPLL no está incrustado en una sola NIC, sino que se encuentra en la plataforma, externo a las NICs. Disciplina y mantiene los PHCs de varias NICs alineados a partir de una referencia común, por lo que cada NIC en el nodo comparte el mismo tiempo. Esta disposición se utiliza en plataformas multi-NIC que distribuyen la temporización internamente en lugar de depender de cableado externo.

=== Requisitos previos

Esta guía cubre únicamente perfiles específicos de telecomunicaciones, por lo que se asume el uso de marca de tiempo por hardware y de un reloj de hardware PTP (PHC) en la NIC. Los adaptadores de red de grado de telecomunicaciones proporcionan soporte PTP por hardware; puede confirmar las capacidades de una interfaz determinada con `ethtool -T`:

[,console]
----
# ethtool -T eno16495np0

Capabilities:
        hardware-transmit
        software-transmit
        hardware-receive
        software-receive
        software-system-clock
        hardware-raw-clock
PTP Hardware Clock: 0
Hardware Transmit Timestamp Modes:
        off
        on
Hardware Receive Filter Modes:
        none
        all
----

Compruebe las capacidades `hardware-transmit`, `hardware-receive` y `hardware-raw-clock` y un índice `PTP Hardware Clock` de 0 o superior (un valor de `-1` significa que la interfaz no tiene PHC). Sustituya `eno16495np0` por la interfaz que pretenda utilizar para PTP.

PTP se proporciona mediante el paquete `linuxptp`. Incluye tres programas de espacio de usuario —`ptp4l`, `phc2sys` y `ts2phc`— que se ejecutan como daemons de larga duración gestionados por `systemd` (un servicio dedicado para cada uno: `ptp4l.service`, `phc2sys.service` y `ts2phc.service`). Colectivamente, ejecutan el protocolo y mantienen los relojes sincronizados:

* `ptp4l`: el daemon PTP. Ejecuta el protocolo IEEE 1588 en las interfaces configuradas, aplica el algoritmo Best Master Clock Algorithm (BMCA) para determinar el papel de cada puerto y disciplina el PHC de la NIC. Una única instancia de `ptp4l` puede gestionar varios puertos, que es lo que permite que un nodo actúe como Boundary Clock.
* `phc2sys`: sincroniza dos relojes. Se utiliza normalmente para alinear el reloj del sistema (sistema operativo) con el PHC que `ptp4l` mantiene sincronizado, de modo que la hora del sistema también siga a PTP.
* `ts2phc`: "time stamp to PHC" (marca de tiempo a PHC). Disciplina el PHC a partir de una señal horaria externa, como el PPS suministrado por un receptor GNSS. Se utiliza en un Grandmaster y para mantener múltiples PHC alineados dentro del mismo nodo.

La forma recomendada de instalar PTP en un clúster de sentido descendente es añadir el paquete `linuxptp` a la `packageList` del archivo de definición de Edge Image Builder (EIB), para que se amplíe automáticamente durante el aprovisionamiento. Consulte la xref:../quickstart/eib.adoc#eib-configuring-rpm-packages[documentación de EIB] para obtener más información sobre la instalación de paquetes.

[,yaml,subs="attributes"]
----
apiVersion: {version-eib-api-latest}
image:
  imageType: RAW
  arch: x86_64
  baseImage: {micro-base-rt-image-raw}
  outputImageName: eibimage-slmicrort-telco.raw
operatingSystem:
  systemd:
    enable:
      - ptp4l
      - phc2sys
  packages:
    packageList:
      - linuxptp
    sccRegistrationCode: $SCC_REGISTRATION_CODE
----

[NOTE]
====
El paquete `linuxptp` no habilita `ptp4l`, `phc2sys` o `ts2phc` de forma predeterminada.
Tras desplegar el archivo de configuración, utilice la sección `systemd` del manifiesto para habilitar los daemons de nodo necesarios (consulte los escenarios a continuación).
====

Por último, el perfil PTP en uso determina si los conmutadores de red entre nodos deben configurarse como dispositivos compatibles con PTP:

* *ITU-T G.8275.1 (soporte de temporización completo)*: se ejecuta directamente sobre Ethernet (Capa 2) mediante multidifusión. Cada nodo a lo largo de la vía debe ser compatible con PTP y actuar como Boundary Clock, lo que proporciona la mayor precisión; por tanto, los conmutadores intermedios deben configurarse para PTP. A menos que se indique lo contrario, los escenarios de esta guía utilizan este perfil.
* *ITU-T G.8275.2 (soporte de temporización parcial)*: se ejecuta sobre IP (Capa 3) mediante unidifusión.
Los nodos intermedios no necesitan ser compatibles con PTP, por lo que la sincronización puede atravesar segmentos de red que no sean compatibles con PTP, y los conmutadores no requieren configuración de PTP, a costa de una menor precisión.

[#ptp-scenario-oc]
=== Escenario 1a - Reloj ordinario (solo PTP)

*Explicación*

Esta es la ampliación de PTP más sencilla: un único nodo de clúster consume tiempo de una fuente de sentido ascendente y disciplina sus relojes locales, sin reenviar nunca el tiempo a otro nodo. El nodo funciona como un reloj ordinario (OC) con un único puerto PTP en el rol de receptor de tiempo.

En el nodo OC, la sincronización es gestionada completamente por los daemons `linuxptp`, independientemente del perfil en uso. No se requiere configuración de DPLL ni `ts2phc`, porque el nodo utiliza una única NIC y `ptp4l` disciplina su PHC directamente:

* `ptp4l` ejecuta el protocolo PTP en la interfaz receptora. El algoritmo de mejor reloj maestro (BMCA) selecciona el nodo de sentido ascendente como maestro, el puerto local pasa al estado `SLAVE` y `ptp4l` disciplina el reloj de hardware PTP (PHC) de la NIC.
Establecer `clientOnly 1` restringe el nodo al rol de receptor de tiempo, por lo que nunca puede seleccionarse como maestro.
* `phc2sys` alinea el reloj del sistema (`CLOCK_REALTIME`) con el PHC que `ptp4l` mantiene sincronizado, de modo que la hora del sistema operativo también sigue a PTP.

El escenario puede implementarse con cualquiera de los perfiles de telecomunicaciones. Difieren en el transporte y en lo que debe proporcionar la red intermedia, y se documentan a continuación como dos modelos independientes:

* *<<ptp-scenario-oc-model1,Modelo 1 — ITU-T G.8275.1>>* (multidifusión de capa 2): utilícelo cuando cada salto entre el maestro y el OC sea compatible con PTP. Proporciona la mayor precisión y es el valor predeterminado para las ampliaciones de telecomunicaciones.
* *<<ptp-scenario-oc-model2,Modelo 2 — ITU-T G.8275.2>>* (unicast de capa 3): utilícelo cuando el OC deba llegar al maestro a través de una red que no sea compatible con PTP, a costa de una menor precisión.

[IMPORTANT]
====
Un reloj ordinario ejecuta un único perfil PTP a la vez. Los dos modelos son mutuamente excluyentes: configure solo uno de ellos en un nodo determinado. Cree solo el archivo de configuración del perfil elegido y haga referencia únicamente a ese archivo en `/etc/sysconfig/ptp4l`. No cree `/etc/ptp4l-G.8275.1.conf` ni `/etc/ptp4l-G.8275.2.conf`, y nunca pase ambos archivos a la línea `OPTIONS=`.
====

*Modelo 1 — ITU-T G.8275.1 (multidifusión de capa 2)*

G.8275.1 se ejecuta directamente sobre Ethernet y dirige sus mensajes a la dirección MAC de multidifusión no reenviable `01:80:C2:00:00:0E`, que los puentes estándar no reenvían, por lo que cada dispositivo en la vía debe terminar y regenerar PTP. Los componentes son:

* *Grandmaster (GM)*: la referencia de sentido ascendente para el dominio PTP (dominio `24` para G.8275.1), normalmente bloqueada a una fuente GNSS/PRTC.
* *PTP-aware switch*: actúa como un Boundary Clock. Su puerto hacia el GM es un Time Receiver y su puerto hacia el OC es un Time Transmitter. Ambos puertos deben tener PTP habilitado.
* *Ordinary Clock (OC)*: el nodo del clúster, que recibe la hora en su único puerto PTP.

. [#ptp-scenario-bc-single-nic]
=== Escenario 2a - Reloj de contorno (solo PTP) con NIC única multipuerto, incluida la propagación al servidor de reloj ordinario

*Explicación*

Este escenario amplía la cadena de temporización con un Reloj de contorno (BC) que regenera PTP hacia un Reloj ordinario (OC) en sentido descendente, totalmente a través de ITU-T G.8275.1 (solo PTP, capa 2). El BC utiliza una única NIC multipuerto: una instancia de `ptp4l` gestiona varios puertos en la misma NIC, por lo que no se requiere ni `ts2phc` ni enrutamiento DPLL (a diferencia de los escenarios con múltiples NIC).

El escenario implica los siguientes componentes:

* *Grandmaster (GM)*: la referencia para el dominio PTP (dominio `24`), normalmente bloqueado a una fuente GNSS/PRTC (el banco de pruebas utilizado aquí no tiene GNSS, de ahí el `gm.ClockClass` degradado que se muestra más adelante). Envía la hora en el segmento de sentido ascendente.
* *Switch compatible con PTP*: actúa como un Reloj de contorno (T-BC) en la vía de temporización; cada puerto que transporta PTP tiene `ptp enable`.
* *Reloj de contorno (servidor BC)*: un nodo multipuerto en una única NIC que puentea dos segmentos PTP. Su puerto `eno8403np1` se enfrenta al segmento *sentido ascendente* como receptor de tiempo (SLAVE) y disciplina el PHC de la NIC; `eno8503np2` (y `eno8603np3`) se enfrentan al segmento *sentido descendente* como transmisores de tiempo que regeneran PTP. El BC termina la cadena de temporización de sentido ascendente e inicia una nueva de sentido descendente.
* *Ordinary Clock (servidor OC)*: un nodo de puerto único (`ens6f0np0`) en el segmento *sentido descendente*, donde su único maestro PTP es el BC. Disciplina sus relojes locales a partir del tiempo que regenera el BC.

La temporización es gestionada por los daemon `linuxptp` en cada nodo:

* En el *servidor BC*, una única instancia `ptp4l` gestiona todos sus puertos. El BMCA selecciona al GM como maestro en `eno8403np1`, que pasa a `SLAVE` y disciplina el PHC. `eno8503np2` y `eno8603np3` se ven obligados a `serverOnly 1`, por lo que actúan solo como transmisores de tiempo.
Debido a que todos los puertos comparten el mismo PHC de la NIC, el tiempo recibido está directamente disponible para los puertos de transmisión; un Boundary Clock se implica automáticamente cuando se configura más de un puerto, por lo que no se necesita ningún ajuste `clock_type` o `ts2phc`.
* En el *servidor OC*, `ptp4l` se ejecuta con `clientOnly 1` en `ens6f0np0`, por lo que el puerto solo actúa como receptor de tiempo. `phc2sys` alinea el reloj del sistema con el PHC.
* En el servidor OC, `clientOnly 1` es lo que garantiza que nunca se convierta en maestro. El atributo `localPriority` —utilizado por el BMCA G.8275.x solo como desempate, cuando clockClass, clockAccuracy, variance y priority2 son iguales, donde se prefiere un valor más bajo— refuerza este orden: el servidor BC mantiene el `128` predeterminado, mientras que el servidor OC utiliza el `250` de menor preferencia.

El BC puentea dos segmentos PTP separados: un segmento *sentido ascendente* entre el GM y su puerto `eno8403np1`, y un segmento *sentido descendente* entre su puerto `eno8503np2` y el OC. Estos se mantienen separados, por ejemplo, en diferentes VLAN del switch o en redes independientes. Debido a que el BC es el único maestro en el segmento de sentido descendente, el OC se sincroniza desde el BC y nunca directamente desde el GM.

Como en el <<ptp-scenario-oc,Escenario 1a>>, este escenario utiliza la dirección MAC de multidifusión no reenviable `01:80:C2:00:00:0E`; los puentes estándar no la reenvían, por lo que cada dispositivo compatible con PTP termina y regenera PTP. La misma dirección debe configurarse en cada nodo de la ruta de temporización.

* `grandmasterIdentity` (`d0460c.ffff.05c130`) — la *raíz del árbol de temporización*: el Gran maestro, reenviado sin cambios a través del Reloj de contorno.
+
Los valores `gm.ClockClass`, `gm.ClockAccuracy` y `grandmasterPriority` contienen la calidad anunciada del Gran maestro utilizada por el BMCA. Si las dos identidades fueran iguales, el OC se sincronizaría directamente desde un Gran maestro, sin ningún Reloj de contorno en la ruta.

[#ptp-scenario-bc-multi-nic-dpll]
=== Escenario 3a - Reloj de contorno (solo PTP) con varias NIC y módulo de temporización interno (DPLL basado en GNR-D)

*Explicación*

{product} admite una temporización precisa en una variedad de plataformas, incluidos los últimos diseños basados en Intel Granite Rapids-D (GNR-D). Estos servidores suelen incluir un controlador Ethernet de alta velocidad integrado y una o más tarjetas adicionales (AIC) con un controlador Ethernet para puertos adicionales. A diferencia de las generaciones de plataformas anteriores, también están equipados con un DPLL dedicado que enruta las señales de temporización a través del sistema y las diferentes NIC internamente, por lo que ya no requiere cableado externo para mantener sincronizados todos los PHC de las NIC.
Por tanto, la ampliación general se simplifica, pero se requieren pasos y componentes de software específicos, como la configuración del DPLL y de la señal interna durante el arranque.

Este escenario amplía el <<ptp-scenario-bc-single-nic,Escenario 2a>> a un Reloj de contorno (BC) construido sobre varias NIC, completamente basado en ITU‑T G.8275.1 (solo PTP, capa 2). Un puerto del controlador integrado recibe PTP del Gran maestro y las tarjetas adicionales regeneran PTP en sentido descendente. A diferencia del caso de una sola NIC, cada NIC tiene su propio PHC; el DPLL integrado y `ts2phc` los mantienen alineados, y se ejecuta una instancia de `ptp4l` por cada PHC.

[IMPORTANT]
====
En esta versión {product}, este escenario solo es compatible con la variante de núcleo de Linux «default» (es decir, no «PREEMPT_RT»).
La compatibilidad con la variante de núcleo de Linux «RT» se añadirá en una versión posterior.
====

.Requisitos previos
* Descargad e instalad el controlador de núcleo de Linux más reciente para los _Intel 800 Series Network Devices_ desde el https://www.intel.com/content/www/us/en/download/19630/intel-network-adapter-driver-for-800-series-devices-under-linux.html[sitio web de Intel].
* Seleccionad el archivo zip que contiene los «ice_RPM_Files», descomprimid el archivo e instalad el `ice-kmp-default-*sles16sp0.x86_64.rpm`. Este RPM contiene, por ejemplo, `ice-kmp-default-2.4.5_k6.12.0_160000.5-1.sles16sp0.x86_64.rpm`:
+
[,console]
----
# transactional-update pkg install ice-kmp-default-2.4.5_k6.12.0_160000.5-1.sles16sp0.x86_64.rpm
----
+
Reiniciad el servidor para que el cambio sea persistente y efectivo.

[NOTE]
====
* Se utiliza un sistema Dell PowerEdge XR8720t como sistema de referencia a lo largo de los ejemplos; las interfaces del núcleo de Linux y la configuración de puertos podrían ser diferentes en otro servidor GNR-D. Ajustad los nombres de los dispositivos en consecuencia.
* Se asume una ampliación de telecomunicaciones y el perfil de telecomunicaciones G.8275.1 se utiliza a lo largo de las siguientes secciones.
====

El escenario implica los siguientes componentes:

* *Grandmaster (GM)*: la referencia para el dominio PTP (dominio `24`), en el sentido ascendente.
* *Switch compatible con PTP*: actúa como un Reloj de contorno (T-BC) en la vía de temporización; cada puerto que transporta PTP tiene `ptp enable`. Los segmentos en sentido ascendente y en sentido descendente se mantienen separados en diferentes VLAN del conmutador (una VLAN dedicada para cada segmento).
* *Boundary Clock (BC server)*: el nodo GNR-D. Su controlador integrado recibe PTP del GM en `eno8403np1` y disciplina el PHC integrado (`/dev/ptp1`). El DPLL integrado distribuye esa temporización a las tarjetas adicionales y `ts2phc` mantiene sus PHC (`/dev/ptp2`, `/dev/ptp3`) alineados con `/dev/ptp1`. Cada tarjeta adicional regenera PTP en el sentido descendente (por ejemplo, en `eno16495np0`), actuando como un transmisor de tiempo (Time Transmitter).
* *Ordinary Clock (OC server)*: un nodo de puerto único (`ens6f0np0`) en el segmento descendente, cuyo único maestro PTP es el BC.

La temporización en el *BC server* es gestionada por varios daemons `linuxptp` que trabajan conjuntamente, debido a que los PHC están físicamente separados:

* Una instancia de `ptp4l` en el controlador integrado (`/dev/ptp1`) ejecuta el protocolo PTP en `eno8403np1`. El BMCA selecciona el GM como maestro, el puerto pasa a `SLAVE` y `ptp4l` disciplina `/dev/ptp1`.
* El DPLL integrado está cableado de modo que el PHC integrado lo controla a través de los pines SDP, y el DPLL a su vez controla los relojes de las tarjetas adicionales. Este es el reemplazo interno para el cableado 1PPS externo utilizado en plataformas anteriores.
* `ts2phc` mantiene los PHC de las tarjetas adicionales alineados con `/dev/ptp1` a partir de la señal que distribuye el DPLL.
* Una instancia `ptp4l` separada por tarjeta adicional (`/dev/ptp2`, `/dev/ptp3`) regenera PTP en sus puertos, todos forzados a `serverOnly 1` (Time Transmitters).
* Un Boundary Clock debe reenviar los atributos auxiliares del Grandmaster (clase de reloj, precisión, etc.) además de la hora. Esto ocurre automáticamente solo dentro de una única instancia `ptp4l`, por lo que se utiliza `pmc` para reenviar esos valores desde la instancia integrada a las instancias complementarias (véase el paso 5). `pmc` (cliente de gestión PTP) es la herramienta `linuxptp` que consulta y actualiza el estado de tiempo de ejecución de una instancia `ptp4l` en funcionamiento a través de su socket de gestión.

[NOTE]
====
En el controlador integrado, solo *uno* de sus puertos es el puerto administrativo que gestiona el PHC. Inspeccionad `/sys/class/ptp/ptp1/device/net/` para encontrarlo (por ejemplo, `eno8703np0`); es el puerto utilizado para configurar las señales DPLL, y no es necesariamente el puerto que transporta PTP (`eno8403np1`).
====

[NOTE]
====
La configuración descrita aquí es completamente estática. Si el GM deja de estar disponible, la sincronización en sentido descendente dependerá exclusivamente de las capacidades de mantenimiento de tiempo (holdover) del host; no se realizará ningún cambio automático a una fuente de referencia de tiempo diferente.
====

. Configurad las señales de temporización internas (DPLL).
+
Conectad el PHC integrado a la DPLL y dejad que la DPLL alimente las tarjetas adicionales, utilizando el puerto administrativo que se encuentra arriba (`eno8703np0`) y los índices `ptpN` correctos.
+
[#gnrd-startup-setup]
.`01-gnrd-startup-setup.sh`
====
[source,bash]
----
#!/bin/bash

# The admin port that manages the PHC is under /sys/class/ptp/ptp1/device/net/ (e.g. eno8703np0).
# Only one port of the integrated E825-C NIC exposes it.

# Let the DPLL drive the Ethernet clock on the integrated controller
echo 4 1 > /sys/class/net/eno8703np0/device/tspll_cfg

# Feed the DPLL from the integrated PHC through the SDP pins:
# SDP0 -> 1 pulse per second (1PPS, 1 Hz): enable the pin, then set a 1 s period
echo 2 2 > /sys/class/ptp/ptp1/pins/SDP0
echo 2 0 0 1 0 > /sys/class/ptp/ptp1/period

# SDP2 -> 1000 pulses per second (1kPPS, 1 kHz): enable the pin, then set a 1 ms period
echo 2 1 > /sys/class/ptp/ptp1/pins/SDP2
echo 1 0 0 0 1000000 > /sys/class/ptp/ptp1/period

# Propagate the pulses from the DPLL to the add-in cards (SDP1 on each add-in PHC)
echo 1 1 > /sys/class/ptp/ptp2/pins/SDP1
echo 1 1 > /sys/class/ptp/ptp3/pins/SDP1
----
====
+

[Service]

. Alinead los PHC de las tarjetas adicionales con `ts2phc`.
+
`ts2phc` («marca de tiempo a PHC») alinea los PHC de las tarjetas adicionales con un reloj de referencia. Aquí, la referencia es el PHC de la NIC integrada (`/dev/ptp1`, ya disciplinado por el GM a través de su instancia `ptp4l`), pasado en la línea de comandos con `-s /dev/ptp1`. La DPLL integrada entrega el 1PPS derivado de esa referencia a cada tarjeta adicional en su pin `SDP1`; `ts2phc` registra las marcas de tiempo de esos pulsos de entrada (EXTTS) y ajusta cada PHC adicional en consecuencia, de modo que todos los PHC del nodo terminan compartiendo la misma hora.
+
[NOTE]
====
La alineación de los PHC adicionales requiere dos ajustes complementarios, a diferentes niveles.

* *Hardware*: el pin de entrada `SDP1` de cada PHC adicional debe estar habilitado para que la DPLL integrada le entregue el pulso 1PPS. Esto se realiza en el script de configuración de la DPLL del paso anterior (`echo 1 1 > /sys/class/ptp/ptpN/pins/SDP1`).
* *Software*: se debe indicar a `ts2phc` que registre la marca de tiempo de esa entrada y ajuste el PHC. Esto es lo que hace la configuración siguiente (`ts2phc.channel`, `ts2phc.pin_index`, `ts2phc.extts_polarity`).

Sin habilitar el pin, el pulso nunca llega al PHC; sin la configuración `ts2phc`, el pulso nunca se le aplica. Ambos son necesarios.
====
+
Cread el archivo de configuración:
+
[#gnrd-ts2phc-config]
.`/etc/ts2phc-cf-all.cfg` — Archivo de configuración de `ts2phc`
====
[source,]
----
[global]
use_syslog              0
verbose                 1
logging_level           7
ts2phc.pulsewidth       100000000

[eno16495np0]
ts2phc.channel          1
ts2phc.extts_polarity   rising
ts2phc.pin_index        1

[eno16595np0]
ts2phc.channel          1
ts2phc.extts_polarity   rising
ts2phc.pin_index        1
----
====
+
Cada tarjeta adicional se configura a través de una sección nombrada según su primer puerto (`[eno16495np0]`, `[eno16595np0]`), que identifica el PHC que se debe disciplinar. Los parámetros asignan el pulso de la DPLL a esa tarjeta:
+
* `ts2phc.pin_index` y `ts2phc.channel`: el pin y el canal donde la DPLL entrega el 1PPS (`SDP1` en esta configuración, por tanto `pin_index 1`).
* `ts2phc.extts_polarity`: el flanco del pulso que se debe registrar (`rising`).
* `ts2phc.pulsewidth`: la anchura de pulso de entrada esperada, en nanosegundos (100 ms en este caso).
+

. Reenvíe los parámetros del Grandmaster a través de las instancias `ptp4l`.
+
Un Boundary Clock debe reenviar no solo la hora, sino también los parámetros adicionales del Grandmaster (clase de reloj, precisión, desfase UTC, etcétera). Esto sucede automáticamente entre puertos de la *misma* instancia `ptp4l`, pero no entre las instancias separadas que gestionan diferentes PHCs. Los valores se aplican en tiempo de ejecución con `pmc` sobre el socket UDS de cada instancia (`SET GRANDMASTER_SETTINGS_NP`).
+
[IMPORTANT]
====
Los valores aplicados con `pmc` se mantienen únicamente en el proceso `ptp4l` en ejecución; *no* se escriben en el archivo `.conf` y *no* sobreviven a un reinicio. Si se reinicia una instancia `ptp4l`, vuelve a los valores por defecto del archivo y los valores deben reenviarse nuevamente. Automatice el reenvío (véase más abajo) en lugar de ejecutarlo una vez manualmente.

#!/bin/bash

----

[#gnrd-pmc-forward]
.`04-ptp-forward-GM.sh` — reenvíe los valores del Grandmaster a las instancias complementarias
====
[source,bash]
----
#!/bin/bash

set -euo pipefail

################## Input variables ##################
VERBOSE=1

CONFIG_FILE_NAC=/etc/ptp4l-nac.conf
CONFIG_FILES_AICS=(/etc/ptp4l-aic1.conf /etc/ptp4l-aic2.conf)

#####################################################


# Check the system is synchronized to a GM
GM_PRESENT=$(pmc -f ${CONFIG_FILE_NAC} -u -b 0 'GET TIME_STATUS_NP' | awk '/gmPresent/ {print $2}')

if [ -z "$GM_PRESENT" ]; then
    echo "Failed to get GM value from ptp4l instance for NAC, exiting..."
    exit 1
elif [ "${GM_PRESENT}" != "true" ]; then
    echo "No GM present, exiting..."
    exit 1
fi

# Get the "upstream" Grandmaster values
PDS_GM_VALUES=$(pmc -f ${CONFIG_FILE_NAC} -u -b 0 'GET PARENT_DATA_SET' | awk 'BEGIN {ORS=" "} /gm./ {print $2}')
TPDS_GM_VALUES=$(pmc -f ${CONFIG_FILE_NAC} -u -b 0 'GET TIME_PROPERTIES_DATA_SET' | awk 'BEGIN {ORS=" "} NR>2 {print $2}')

if [ -z "$PDS_GM_VALUES" ]; then
    echo "No PARENT_DATA_SET values retrieved, exiting ..."
    exit 2
elif [ -z "$TPDS_GM_VALUES" ]; then
    echo "No TIME_PROPERTIES_DATA_SET values retrieved, exiting ..."
    exit 2
fi

# Unpack from PARENT_DATA_SET
read CLOCK_CLASS CLOCK_ACCURACY VARIANCE <<< $PDS_GM_VALUES

# Unpack from TIME_PROPERTIES_DATA_SET
read UTC_OFFSET LEAP_61 LEAP_59 UTC_OFFSET_VALID PTP_TIMESCALE T_TRACEABLE F_TRACEABLE T_SOURCE <<< $TPDS_GM_VALUES

if [ "$VERBOSE" -eq 1 ]; then
    echo "Read from PARENT_DATA_SET: clockClass=${CLOCK_CLASS} clockAccuracy=${CLOCK_ACCURACY} offsetScaledLogVariance=${VARIANCE}"
    echo "Read from TIME_PROPERTIES_DATA_SET: currentUtcOffset=${UTC_OFFSET} leap61=${LEAP_61} leap59=${LEAP_59}" \
         "currentUtcOffsetValid=${UTC_OFFSET_VALID} ptpTimescale=${PTP_TIMESCALE} timeTraceable=${T_TRACEABLE}" \
         "frequencyTraceable=${F_TRACEABLE} timeSource=${T_SOURCE}"
fi


# Forward these values to the "downstream" Time Receivers, updating the ptp4l instances
for FILE in "${CONFIG_FILES_AICS[@]}"; do
    if [ "$VERBOSE" -eq 1 ]; then
        echo "Updating GRANDMASTER_SETTINGS_NP (${FILE})"
    fi

    pmc -f ${FILE} -u -b 0 'SET GRANDMASTER_SETTINGS_NP
       clockClass              '${CLOCK_CLASS}'
       clockAccuracy           '${CLOCK_ACCURACY}'
       offsetScaledLogVariance '${VARIANCE}'
       currentUtcOffset        '${UTC_OFFSET}'
       leap61                  '${LEAP_61}'
       leap59                  '${LEAP_59}'
       currentUtcOffsetValid   '${UTC_OFFSET_VALID}'
       ptpTimescale            '${PTP_TIMESCALE}'
       timeTraceable           '${T_TRACEABLE}'
       frequencyTraceable      '${F_TRACEABLE}'
       timeSource              '${T_SOURCE}'' &> /dev/null

    if [ $? -ne 0 ]; then
        echo "Failed to update ptp4l instance using config file \"${FILE}\", exiting ..."
        exit 1
    fi
done
----
====

[#sctp]
== SCTP - Protocolo de control de transmisión de flujo
De https://en.wikipedia.org/wiki/Stream_Control_Transmission_Protocol[Stream Control Transmission Protocol - Wikipedia]

[quote]
____
El Stream Control Transmission Protocol (SCTP) es un protocolo de comunicaciones de redes informáticas en la capa de transporte del conjunto de protocolos de Internet.
Originalmente destinado al transporte de mensajes del Sistema de Señalización 7 (SS7) en telecomunicaciones, el protocolo proporciona la característica orientada a mensajes del Protocolo de Datagramas de Usuario (UDP) mientras garantiza un transporte fiable y en secuencia de mensajes con control de congestión como el Protocolo de Control de Transmisión (TCP).
A diferencia de UDP y TCP, el protocolo admite multihoming y rutas redundantes para aumentar la resiliencia y la fiabilidad.

SCTP está estandarizado por el Internet Engineering Task Force (IETF) en el RFC 9260. La implementación de referencia de SCTP se lanzó como parte de la versión 7 de FreeBSD y desde entonces ha sido ampliamente portada a otras plataformas.
____

En las especificaciones 3GPP 4G (LTE), SCTP (Stream Control Transmission Protocol) actúa como el transporte fundamental de Capa 4 para los mensajes de señalización del plano de control a través del Evolved Packet Core (EPC), incluida la conexión de señalización con el dominio de la Radio Access Network (RAN). Las especificaciones 3GPP 5G han eliminado en su lugar la necesidad de SCTP dentro de la Red Central mediante la introducción de la Service Based Architecture (SBA), que reemplaza todas las interfaces de señalización basadas en Diameter-over-SCTP por HTTP/2. Sin embargo, todavía es necesario dentro del dominio RAN 5G:

* en las interfaces de señalización a través de los elementos de red que componen una instancia de gNodeB "desagregada" (interfaz F1-C entre DU y CU-CP e interfaz E1 entre CU-CP y CU-UP).

* en la interfaz Xn-C que conecta instancias de gNodeB para fines de señalización.

* en el punto de referencia N2 (también conocido como NG-C) utilizado para conectar instancias de gNodeB (dominio RAN) con instancias de AMF (dominio de red central) para fines de señalización.

Debe entonces habilitar el módulo del kernel `sctp` (`lksctp`) en los nodos del clúster en sentido descendente que alojan las cargas de trabajo de telecomunicaciones compatibles con SCTP que lo aprovechan:

* Para cargar manualmente el módulo del kernel `sctp` en un nodo Linux:

[,shell]
----
$ sudo modprobe sctp
----

* Para automatizar la carga del módulo del kernel `sctp` en cada arranque del nodo, cree un archivo llamado `sctp.conf` en el directorio `/etc/modules-load.d/` que contenga simplemente la cadena `sctp` (es decir, el nombre del módulo del kernel que la unidad https://www.freedesktop.org/software/systemd/man/latest/modules-load.d.html[systemd-modules-load.service] debería cargar en el arranque).

[,shell]
----
$ echo "sctp" > /etc/modules-load.d/sctp.conf
$ reboot
----

La forma más fácil y mejor de asegurar que el módulo del kernel `sctp` se cargue en cada arranque del nodo es añadir ese archivo `/etc/modules-load.d/sctp.conf` a la imagen sin procesar creada por Edge Image Builder (EIB) utilizada para aprovisionar los nodos en sentido descendente; consulte la xref:../quickstart/eib.adoc#adding-operating-system-files[documentación de EIB] para obtener más información sobre cómo hacerlo.
