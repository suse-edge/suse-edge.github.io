[#{cluster-type}-day2-fleet-os-upgrade-components]
=== 组件

本节涵盖 `OS upgrade` 过程在默认“第 2 天”<<{cluster-type}-day2-fleet-components,组件>> 之外使用的自定义组件。

[#{cluster-type}-day2-fleet-os-upgrade-components-systemd-service]
==== systemd.service

特定节点上的操作系统升级由 link:https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html[systemd.service] 处理。

根据操作系统从一个 Edge 版本升级到另一个版本所需的升级类型，会创建不同的服务：

* 对于需要相同操作系统版本（例如 `6.1`）的 Edge 版本，将创建 `os-pkg-update.service`。它使用 link:https://kubic.opensuse.org/documentation/man-pages/transactional-update.8.html[事务更新] 来执行 link:https://en.opensuse.org/SDB:Zypper_usage#Updating_packages[常规软件包升级]。

* 对于需要操作系统版本迁移（例如 `6.1` -> `6.2`）的 Edge 版本，将创建 `os-migration.service`。它使用 link:https://kubic.opensuse.org/documentation/man-pages/transactional-update.8.html[事务更新] 来执行：

.. link:https://en.opensuse.org/SDB:Zypper_usage#Updating_packages[常规软件包升级]，确保所有软件包均为最新，以减少迁移过程中因旧软件包版本导致的任何故障。

.. 利用 `zypper migration` 命令进行操作系统迁移。

上述服务通过 `SUC plan` 在每个节点上部署，该服务必须位于需要操作系统升级的 {cluster-type} 集群上。

[#{cluster-type}-day2-fleet-os-upgrade-overview]
=== 概述

{cluster-type} 集群节点的操作系统升级是通过利用 `Fleet` 和 `System Upgrade Controller (SUC)` 完成的。

*Fleet* 用于在目标集群上部署和管理 `SUC plans`。

[NOTE]
====
`SUC plans` 是 link:https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/[自定义资源]，用于描述 `SUC` 为在节点集上执行特定任务所需遵循的步骤。有关 `SUC plan` 外观的示例，请参阅 link:https://github.com/rancher/system-upgrade-controller?tab=readme-ov-file#example-plans[上游储存库]。
====

`OS SUC plans` 通过将 https://fleet.rancher.io/gitrepo-add[GitRepo] 或 https://fleet.rancher.io/bundle-add[Bundle] 资源部署到特定的 Fleet link:https://fleet.rancher.io/namespaces#gitrepos-bundles-clusters-clustergroups[工作区] 来分发到每个集群。Fleet 会检索已部署的 `GitRepo/Bundle` 并将其内容（即 `OS SUC plans`）部署到目标集群。

[NOTE]
====
`GitRepo/Bundle` 资源始终部署在 `management cluster` 上。是否使用 `GitRepo` 或 `Bundle` 资源取决于您的用例，请查看 <<{cluster-type}-day2-fleet-determine-use-case>> 以获取更多信息。
====

`OS SUC plans` 描述了以下工作流程：

. 在操作系统升级之前，请务必 link:https://kubernetes.io/docs/reference/kubectl/generated/kubectl_cordon/[隔离] 节点。

. 请务必先升级 `control-plane` 节点，然后再升级 `worker` 节点。

. 请务必一次只升级一个 *one* 节点。

一旦部署了 `OS SUC plans`，工作流程如下所示：

. SUC 会协调已部署的 `OS SUC plans` 并在 *每个节点* 上创建一个 `Kubernetes Job`。

. `Kubernetes Job` 会为软件包升级或操作系统迁移创建一个 <<{cluster-type}-day2-fleet-os-upgrade-components-systemd-service, `systemd.service`>>。

. 所创建的 `systemd.service` 会触发特定节点上的操作系统升级过程。
+
[IMPORTANT]
====
一旦操作系统升级过程完成，相应的节点将被 `rebooted` 以应用系统更新。
====

=== 要求

_常规：_

. *SCC 注册机器* - 所有 {cluster-type} 集群节点都应注册到 `https://scc.suse.com/`，这是使相应的 `systemd.service` 能够成功连接到所需 RPM 储存库所必需的。
+
[IMPORTANT]
====
对于需要操作系统版本迁移的 Edge 版本（例如 `6.1` -> `6.2`），请确保您的 SCC 密钥支持迁移到新版本。
====

. *确保 SUC Plan 容忍度与节点容忍度匹配* - 如果您的 Kubernetes 集群节点具有自定义 *污点*，请确保在 *SUC Plans* 中为这些污点添加 link:https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/[容忍度]。默认情况下，*SUC Plans* 仅具有针对 *控制平面* 节点的容忍度。默认容忍度包括：

* _CriticalAddonsOnly=true:NoExecute_

* _node-role.kubernetes.io/control-plane:NoSchedule_

* _node-role.kubernetes.io/etcd:NoExecute_
+
[NOTE]
====
任何额外的容忍度必须添加到每个计划的 `.spec.tolerations` 部分下。与操作系统升级相关的*SUC 计划*可以在`fleets/day2/system-upgrade-controller-plans/os-upgrade`下的link:https://github.com/suse-edge/fleet-examples[suse-edge/fleet-examples]储存库中找到。*确保您使用来自有效存储库link:https://github.com/suse-edge/fleet-examples/releases[发布]标签的计划。*

为*控制平面* SUC 计划定义自定义容忍度的示例如下：
[,yaml]
----
apiVersion: upgrade.cattle.io/v1
kind: Plan
metadata:
  name: os-upgrade-control-plane
spec:
  ...
  tolerations:
  # default tolerations
  - key: "CriticalAddonsOnly"
    operator: "Equal"
    value: "true"
    effect: "NoExecute"
  - key: "node-role.kubernetes.io/control-plane"
    operator: "Equal"
    effect: "NoSchedule"
  - key: "node-role.kubernetes.io/etcd"
    operator: "Equal"
    effect: "NoExecute"
  # custom toleration
  - key: "foo"
    operator: "Equal"
    value: "bar"
    effect: "NoSchedule"
...
----
====

_隔离的：_

. *镜像 SUSE RPM 储存库* - 应在本地镜像操作系统 RPM 储存库，以便`systemd.service`可以访问它们。这可以通过使用link:https://documentation.suse.com/sles/15-SP6/html/SLES-all/book-rmt.html[RMT]或link:https://documentation.suse.com/suma/5.0/en/suse-manager/index.html[SUMA]来实现。

[#{cluster-type}-day2-fleet-os-upgrade-plan-deployment]
=== 操作系统升级 - SUC 计划部署

[IMPORTANT]
====
对于之前使用此过程升级过的环境，用户应确保完成以下其中*一*步骤：

* `Remove any previously deployed SUC Plans related to older Edge release versions from the {cluster-type} cluster` - 可以通过从现有的 `GitRepo/Bundle`link:https://fleet.rancher.io/gitrepo-targets#target-matching[目标配置] 中移除所需的集群，或者完全移除 `GitRepo/Bundle` 资源来完成。

* `Reuse the existing GitRepo/Bundle resource` - 可以通过将资源的修订版本指向包含所需 `suse-edge/fleet-examples`link:https://github.com/suse-edge/fleet-examples/releases[release] 的正确 Fleet 的新标签来完成。

这样做是为了避免旧版 Edge 发行版本之间的`SUC Plans`冲突。

如果用户在 {cluster-type} 集群上存在现有的 `SUC Plans` 时尝试升级，他们将看到以下 fleet 错误：

[,bash]
----
Not installed: Unable to continue with install: Plan <plan_name> in namespace <plan_namespace> exists and cannot be imported into the current release: invalid ownership metadata; annotation validation error..
----
====

如 <<{cluster-type}-day2-fleet-os-upgrade-overview>> 中所述，操作系统升级是通过以下方式之一将 `SUC plans` 部署到目标集群来完成的：

* Fleet `GitRepo` 资源 - <<{cluster-type}-day2-fleet-os-upgrade-plan-deployment-gitrepo>>。

* Fleet `Bundle` 资源 - <<{cluster-type}-day2-fleet-os-upgrade-plan-deployment-bundle>>。

要确定应使用哪种资源，请参阅<<{cluster-type}-day2-fleet-determine-use-case>>。

对于希望从第三方 GitOps 工具部署`OS SUC plans`的用例，请参阅<<{cluster-type}-day2-fleet-os-upgrade-plan-deployment-third-party>>

[#{cluster-type}-day2-fleet-os-upgrade-plan-deployment-gitrepo-manual]
===== GitRepo 创建 - 手动

. 拉取 *GitRepo* 资源：
+
[,bash,subs="attributes"]
----
curl -o os-upgrade-gitrepo.yaml https://raw.githubusercontent.com/suse-edge/fleet-examples/refs/tags/{release-tag-fleet-examples}/gitrepos/day2/os-upgrade-gitrepo.yaml
----

ifeval::["{cluster-type}" == "downstream"]
. 编辑 *GitRepo* 配置，在 `spec.targets` 下指定您所需的目标列表。默认情况下，来自 `suse-edge/fleet-examples` 的 `GitRepo` 资源 *不会* 映射到任何下游集群。

** 要匹配所有集群，请将默认 `GitRepo` *目标* 更改为：
+
[,yaml]
----
spec:
  targets:
  - clusterSelector: {}
----

** 或者，如果您需要更细粒度的集群选择，请参阅 link:https://fleet.rancher.io/gitrepo-targets[映射到下游集群]
endif::[]

ifeval::["{cluster-type}" == "management"]
. 编辑 *GitRepo* 配置：

** 删除 `spec.targets` 部分 - 仅下游集群需要。
+
[,bash]
----
# Example using sed
sed -i.bak '/^  targets:/,$d' os-upgrade-gitrepo.yaml && rm -f os-upgrade-gitrepo.yaml.bak

# Example using yq (v4+)
yq eval 'del(.spec.targets)' -i os-upgrade-gitrepo.yaml
----

** 将 `GitRepo` 的命名空间指向 `{fleet-workspace}` 命名空间 - 这样做是为了在管理集群上部署资源。
+
[,bash]
----
# Example using sed
sed -i.bak 's/namespace: fleet-default/namespace: fleet-local/' os-upgrade-gitrepo.yaml && rm -f os-upgrade-gitrepo.yaml.bak

# Example using yq (v4+)
yq eval '.metadata.namespace = "fleet-local"' -i os-upgrade-gitrepo.yaml 
----
endif::[]

. 应用 *GitRepo* 资源到您的 `management cluster`：
+
[,bash]
----
kubectl apply -f os-upgrade-gitrepo.yaml
----

. 在 `{fleet-workspace}` 名称空间下查看已创建的 *GitRepo* 资源：
+
[,bash,subs="attributes"]
----
kubectl get gitrepo os-upgrade -n {fleet-workspace}

# Example output
NAME            REPO                                              COMMIT         BUNDLEDEPLOYMENTS-READY   STATUS
os-upgrade      https://github.com/suse-edge/fleet-examples.git   {release-tag-fleet-examples}  0/0
----

[#{cluster-type}-day2-fleet-os-upgrade-plan-deployment-third-party]
==== SUC 计划部署 - 第三方 GitOps 工作流

在某些用例中，用户可能希望将 `OS SUC plans` 集成到他们自己的第三方 GitOps 工作流（例如 `Flux`）中。

要获取所需的操作系统升级资源，请首先确定您想要使用的 link:https://github.com/suse-edge/fleet-examples[suse-edge/fleet-examples] 储存库的 Edge link:https://github.com/suse-edge/fleet-examples/releases[发布] 标签。

之后，可以在 `fleets/day2/system-upgrade-controller-plans/os-upgrade` 处找到资源，其中：

* `plan-control-plane.yaml` 是用于 *控制平面* 节点的 SUC 计划资源。

* `plan-worker.yaml` 是用于 *工作节点* 的 SUC 计划资源。

* `secret.yaml` 是一个包含 `upgrade.sh` 脚本的 Secret，该脚本负责创建 <<{cluster-type}-day2-fleet-os-upgrade-components-systemd-service, systemd.service>>。

* `config-map.yaml` 是一个 ConfigMap，其中保存了供 `upgrade.sh` 脚本使用的配置。

[IMPORTANT]
====
这些 `Plan` 资源由 `System Upgrade Controller` 进行解释，并应部署在您希望升级的每个下游集群上。有关 SUC 部署信息，请参见 <<components-system-upgrade-controller-install>>。
====

为了更好地了解如何使用 GitOps 工作流来部署用于操作系统升级的 *SUC Plans*，查看 <<{cluster-type}-day2-fleet-os-upgrade-overview,overview>> 会有所帮助。
