このセクションでは、SUSE Telco Cloud経由でデプロイされたクラスターにおけるTelco固有機能の設定について説明します。

<<atip-automated-provisioning,自動プロビジョニング>>セクションで説明されているように、ダイレクトネットワークプロビジョニングのデプロイメント方法が使用されます。

このセクションの構成は次のとおりです。

* <<kernel-image-for-real-time,リアルタイム用カーネルイメージ>>:リアルタイムカーネルで使用するカーネルイメージ。
* <<kernel-args,低レイテンシおよび高性能のためのカーネル引数>>:Telcoワークロードを実行する際のパフォーマンスを最大化し、レイテンシを低減するために使用するカーネル引数。
* <<cpu-pinning-host,ホストでのCPUピニング>>:カーネル引数とTuneDプロファイルによるCPUの分離。
* <<cpu-pinning-k8s,KubernetesでのCPUピニング>>:Kubelet設定によるKubernetes上でのCPUの分離。
* <<network-parameters,ネットワークパラメータ>>:最適なパフォーマンスと低遅延を実現するためのネットワークチューニングパラメータ。
* <<cni-configuration,CNI設定>>:Kubernetesクラスターで使用するCNI設定。
* <<sriov,SR-IOV設定>>:Kubernetesワークロードで使用するSR-IOV設定。
* <<dpdk,DPDK設定>>:システムで使用するDPDK設定。
* <<acceleration,vRANアクセラレーション>>:vRANアクセラレーションカードへのFECアルゴリズム計算のオフロード。
* <<huge-pages,Huge pages>>:Kubernetesワークロードで使用するHuge pages設定。
* <<numa-aware-scheduling,NUMA対応スケジューリング設定>>:Kubernetesワークロードで使用するNUMA対応スケジューリング設定。
* <<metal-lb-configuration,Metal LB設定>>:Kubernetesワークロードで使用するMetal LB設定。
* <<private-registry,プライベートレジストリ設定>>:Kubernetesワークロードで使用するプライベートレジストリ設定。
* <<ptp-configuration,Precision Time Protocol設定>>:PTP Telcoプロファイルを実行するための設定ファイル。
* <<sctp,SCTP設定>>:LinuxカーネルIPスタックでSCTPレイヤーを有効にします。


[#kernel-image-for-real-time]
== リアルタイム用カーネルイメージ

リアルタイムカーネルイメージが標準カーネルより優れているとは限りません。
これは特定のユースケースに合わせて調整された別のカーネルです。リアルタイムカーネルは、スループットを犠牲にして低遅延を実現するように調整されています。リアルタイムカーネルは汎用用途には推奨されませんが、Telcoワークロードにおいて遅延が重要な要因となる場合には、推奨されるカーネルです。

主な機能は4つあります。

* 決定論的実行:
+
予測可能性を高め、システム負荷が高い場合でも、毎回、重要なビジネスプロセスを期限内に確実に完了させ、高品質のサービスを提供します。重要なシステムリソースを高優先度プロセス用に保護することで、時間的制約のあるアプリケーションの予測可能性を高めることができます。
+
* 低ジッタ:
+
高度に決定論的な技術に基づく低ジッタは、アプリケーションを現実世界と同期させるのに役立ちます。これは、継続的かつ反復的な計算を必要とするサービスに役立ちます。
+
* プライオリティの継承:
+
プライオリティの継承とは、優先度の高いプロセスがタスクを完了するために優先度の低いプロセスの終了を必要とする場合に、優先度の低いプロセスが高い優先度を引き継ぐ機能を指します。SUSE Linux Enterprise Real Timeは、ミッションクリティカルなプロセスにおけるこれらの優先度の逆転問題を解決します。
+
* スレッド割り込み:
+
汎用OSにおいて割り込みモードで動作しているプロセスは、プリエンプトされることがありません。SUSE Linux Enterprise Real Timeでは、これらの割り込みがカーネルスレッドによってカプセル化され、これらのカーネルスレッドは割り込み可能なため、ユーザが定義した優先度の高いプロセスによってハード割り込みやソフト割り込みがプリエンプトされるようになります。
+
この場合、`SUSE Linux Micro RT`のようなリアルタイムイメージをインストール済みであれば、カーネルリアルタイムはすでにインストールされています。 https://scc.suse.com/[SUSE Customer Center]から、リアルタイムカーネルイメージをダウンロードできます。
+

[NOTE]
====
リアルタイムカーネルの詳細については、 https://www.suse.com/products/realtime/[SUSE Real Time]を参照してください。
====

[#kernel-args]
== 低レイテンシおよび高性能のためのカーネル引数

適切なカーネル引数を設定することは、パフォーマンスの最適化、低レイテンシの実現、およびTelcoワークロード向けのクラスタ展開を成功させるために不可欠です。一部のパラメータはリアルタイムカーネルが最適に機能するように特別に設計されていますが、このセクションはRTカーネルとデフォルトカーネルの両方の構成に適用されます。さらに、Directed Network Provisioning方式を使用してダウンストリームのクラスタノードを正常に展開するには、特定の引数が必須となります。

* SUSEリアルタイムカーネルを使用する場合は、`kthread_cpus`を削除してください。このパラメータは、どのCPU上でカーネルスレッドが作成されるかを制御します。また、PID 1やカーネルモジュール（kmodユーザスペースヘルパー）の読み込みに使用できるCPUを制御します。このパラメータは認識されず、何の効果もありません。

* `isolcpus`、`nohz_full`、`rcu_nocbs`、および`irqaffinity`を使用してCPUコアを分離します。CPUピン留め技術の包括的な一覧については、<<cpu-pinning-host,CPU Pinning on Host>>の章を参照してください。

* `isolcpus`カーネル引数に`domain,nohz,managed_irq`フラグを追加します。フラグを指定しない場合、`isolcpus`は`domain`フラグのみを指定した場合と同等になります。これにより、カーネルタスクを含むスケジューリングから指定されたCPUが分離されます。`nohz`フラグは指定されたCPUでのスケジューラティックを停止し（CPU上で実行可能なタスクが1つだけの場合）、`managed_irq`フラグは指定されたCPUへの管理対象の外部（デバイス）割り込みのルーティングを回避します。NVMeデバイスのIRQラインはカーネルによって完全に管理されており、その結果、分離されていない（ハウスキーピング）コアにルーティングされることに注意してください。例えば、このセクションの最後に記載されているコマンドラインを実行すると、システムには4つのキュー（および管理/制御キュー）のみが割り当てられます。

+
[,shell]
----
for I in $(grep nvme0 /proc/interrupts | cut -d ':' -f1); do cat /proc/irq/${I}/effective_affinity_list; done | column
39      0       19      20      39
----
+
この動作により、分離されたコア上で実行される時間に敏感なアプリケーションがディスクI/Oによる中断を回避できる一方で、ストレージ向けのワークロードでは慎重な設計が求められる場合があります。

* ティック（カーネルの周期的なタイマー割り込み）を調整します。
** `skew_tick=1`: ティックが同時に発生することがあります。すべてのCPUが同時にタイマーティックを受け取るのではなく、`skew_tick=1`を使用すると、わずかに時間をずらして発生させることができます。これはシステムジッターの低減に役立ち、より一貫した低い割り込み応答時間を実現します（これはレイテンシに敏感なアプリケーションにとって不可欠な要件です）。
** `nohz=on`: アイドル状態のCPUでの周期的なタイマーティックを停止します。
** `nohz_full=<cpu-cores>`:リアルタイムアプリケーション専用の指定されたCPUでの周期的なタイマーティックを停止します。

* `mce=off`を指定して、マシンチェック例外（MCE）処理を無効にします。MCEはプロセッサによって検出されるハードウェアエラーであり、これらを無効にすることで、不要なログ出力を回避できます。

* `nowatchdog`を追加して、タイマーハード割り込みコンテキストで実行されるタイマーとして実装されているソフトロックアップウォッチドッグを無効にします。期限が切れると（つまり、ソフトロックアップが検出されると）、警告が出力され（ハード割り込みコンテキストで）、レイテンシターゲットが実行されます。期限が切れない場合でも、タイマーリストに追加されるため、すべてのタイマー割り込みのオーバーヘッドがわずかに増加します。このオプションはNMIウォッチドッグも無効にするため、NMIが干渉することはありません。

* `nmi_watchdog=0`はNMI（ノンマスカブル割り込み）ウォッチドッグを無効にします。`nowatchdog`が使用されている場合、これは省略可能です。

* RCU（Read-Copy-Update）は、共有データへの同時かつロックフリーなアクセスを多くのリーダーに対して可能にするカーネルメカニズムです。RCUコールバックは「猶予期間」の後にトリガーされる関数であり、以前のすべてのリーダーが終了したことを確認して、古いデータを安全に再利用できるようにします。私たちは、特に機密性の高いワークロードに対してRCUを微調整し、これらのコールバックを専用（固定）CPUからオフロードすることで、カーネル操作が重要で時間的制約のあるタスクに干渉するのを防ぎます。
** RCUコールバックが実行されないように、`rcu_nocbs`で固定CPUを指定します。これは、リアルタイムワークロードのジッターとレイテンシを低減するのに役立ちます。
** `rcu_nocb_poll`は、コールバック処理が必要かどうかを確認するために、ノーコールバックCPUに定期的にポーリングを行わせます。これにより、割り込みオーバーヘッドを削減できます。
** `rcupdate.rcu_cpu_stall_suppress=1`は、負荷の高いリアルタイムシステムで誤検知となることがあるRCU CPUストール警告を抑制します。
** `rcupdate.rcu_expedited=1`はRCU操作の猶予期間を短縮し、読み取り側のクリティカルセクションの応答性を高めます。
** `rcupdate.rcu_normal_after_boot=1` rcu_expeditedと併用すると、システム起動後にRCUを通常（非高速化）の動作に戻すことができます。
** `rcupdate.rcu_task_stall_timeout=0`はRCUタスクストール検出器を無効にし、長時間実行されるRCUタスクによる潜在的な警告やシステム停止を防ぎます。
** `rcutree.kthread_prio=99`はRCUコールバックカーネルスレッドの優先度を最高値（99）に設定し、必要に応じてコールバックを迅速に処理するために確実にスケジュールされるようにします。

* Metal^3^およびCluster APIがクラスターのプロビジョニング/デプロビジョニングを正常に行えるように、`ignition.platform.id=openstack`を追加します。これは、OpenStack Ironicに由来するMetal^3^ Pythonエージェントによって使用されます。

* `net.ifnames=1`を介して https://documentation.suse.com/smart/network/html/network-interface-predictable-naming/index.html[ネットワークインタフェースの予測可能な命名]を有効にします。SUSE Linux Micro 6.2以降では、これがデフォルトで有効になっており、明示的な設定は不要です。6.2より前のバージョンでは、これをカーネル引数として明示的に設定する必要があります。これは、Management ClusterのMetal^3^ Helmチャートの`predictableNicNames`設定と一致しており、ダイレクトネットワークプロビジョニングが正しく機能するために必要です。SR-IOVを利用する場合、一貫したインターフェース命名も重要です。

* `intel_pstate=passive`を削除する。このオプションは、`intel_pstate`が汎用cpufreqガバナーと連携するように設定しますが、これを機能させるために、副作用としてハードウェア管理のP-state（`HWP`）を無効にします。ハードウェアのレイテンシを削減するため、リアルタイムワークロードにはこのオプションは推奨されません。

* `intel_idle.max_cstate=0 processor.max_cstate=1`を`idle=poll`に置き換えます。C-State遷移を回避するために、`idle=poll`オプションを使用してC-State遷移を無効にし、CPUを最高のC-Stateに維持します。`intel_idle.max_cstate=0`オプションは`intel_idle`を無効にするため、`acpi_idle`が使用され、その後`acpi_idle.max_cstate=1`がacpi_idleの最大C-stateを設定します。
{x86-64}アーキテクチャでは、最初のACPI C-Stateは常に`POLL`ですが、`poll_idle()`関数を使用します。この関数は、定期的にクロックを読み取り、タイムアウト後に`do_idle()`でメインループを再起動するため、わずかなレイテンシが発生する可能性があります（これには`TIF_POLL`タスクフラグのクリアと設定も含まれます）。
対照的に、`idle=poll`はタイトなループで実行され、タスクが再スケジュールされるのをビジーウェイトで待機します。これによりアイドル状態からの復帰レイテンシは最小限に抑えられますが、アイドルスレッドでCPUをフルスピードで動作させ続けるという代償が伴います。

* BIOSでC1Eを無効にします。このオプションは、BIOSでC1E状態を無効にし、アイドル時にCPUがC1E状態に入るのを防ぐために重要です。C1E状態は、CPUがアイドル状態のときにレイテンシを引き起こす可能性のある低電力状態です。

このドキュメントの残りの部分では、ヒュージページやIOMMUを含む追加のパラメータについて説明します。

以下は、前述の調整を含む、32コアIntelサーバーのカーネル引数の例です。

[,shell]
----
$ cat /proc/cmdline
BOOT_IMAGE=/boot/vmlinuz-6.4.0-9-rt root=UUID=77b713de-5cc7-4d4c-8fc6-f5eca0a43cf9 skew_tick=1 rd.timeout=60 rd.retry=45 console=ttyS1,115200 console=tty0 default_hugepagesz=1G hugepagesz=1G hugepages=40 hugepagesz=2M hugepages=0 ignition.platform.id=openstack net.ifnames=1 intel_iommu=on iommu=pt irqaffinity=0,31,32,63 isolcpus=domain,nohz,managed_irq,1-30,33-62 nohz_full=1-30,33-62 nohz=on mce=off nosoftlockup nowatchdog nmi_watchdog=0 quiet rcu_nocb_poll rcu_nocbs=1-30,33-62 rcupdate.rcu_cpu_stall_suppress=1 rcupdate.rcu_expedited=1 rcupdate.rcu_normal_after_boot=1 rcupdate.rcu_task_stall_timeout=0 rcutree.kthread_prio=99 security=selinux selinux=1 idle=poll

[#cpu-pinning-host]
== ホストでのCPU固定

CPUピニング（プロセッサアフィニティとも呼ばれます）は、プロセスやスレッドを特定のCPUコアにバインドし、オペレーティングシステムのスケジューラによる移動を防ぐ手法です。プロセスが常に同じコアで実行されるようにすることで、そのコアのキャッシュメモリに残っているデータへのアクセスが高速になるという利点があります。この手法は、ハイパフォーマンスコンピューティング環境で一般的であり、パフォーマンスを劇的に向上させ、オーバーヘッドを削減します。

=== TuneDによるCPUの分離
`tuned`は、さまざまな定義済みプロファイルを使用してパフォーマンスを最適化するためにシステムの状態を監視するシステムチューニングツールです。重要な機能として、リアルタイムアプリケーションなどの特定のワークロードに対してCPUコアを分離する機能があります。これにより、OSがこれらのコアを使用することを防ぎ、レイテンシが増加する可能性を抑えます。

この機能を有効にして設定するには、まず分離したいCPUコア用のプロファイルを作成する必要があります。この例では、64個のコアのうち、60個のコア（`1-30,33-62`）をアプリケーション専用とし、残りの4個のコアをハウスキーピング用に使用します。分離されたCPUの設計は、リアルタイムアプリケーションに大きく依存することに注意してください。

[,shell]
----
$ echo "export tuned_params" >> /etc/grub.d/00_tuned

$ echo "isolated_cores=1-30,33-62" >> /etc/tuned/cpu-partitioning-variables.conf

$ tuned-adm profile cpu-partitioning
Tuned (re)started, changes applied.
----

=== カーネル引数によるCPUの分離
次に、CPUコアを分離し、CPU使用率に関するその他の重要なパラメータを設定するために、GRUBオプションを変更する必要があります。
以下のオプションは、現在のハードウェア仕様に合わせてカスタマイズすることが重要です。

[,shell]

|===
| パラメータ」 | 値 | description

| isolcpus
| domain,nohz,managed_irq,1-30,33-62
| コア1～30および33～62を分離します。`domain`は、これらのCPUが分離ドメインの一部であることを示します。`nohz`は、これらの分離されたCPUがアイドル状態のときにティックレス動作を有効にし、割り込みを削減します。`managed_irq`は、固定されたCPUがIRQのターゲットにならないように分離します。これは、すでにほとんどのIRQをハウスキーピングコアに振り向けている`irqaffinity=0-7`を考慮に入れています。

| skew_tick
| 1
| このオプションにより、カーネルは分離されたCPU間でタイマー割り込みをスキュー（ずらすこと）できます。

| nohz
| on
| 有効にすると、カーネルの周期的なタイマー割り込み（「ティック」）が、アイドル状態になった任意のCPUコアで停止します。これは主にハウスキーピングCPU（`0,31,32,63`）にメリットがあり、電力を節約し、それらの汎用コアでの不要なウェイクアップを削減します。

| nohz_full
| 1-30,33-62
| 分離されたコアの場合、これはCPUが単一のアクティブなタスクを実行しているときでもティックを停止します。これは、CPUをフルティックレスモード（または「dyntick」）で実行することを意味します。カーネルは、実際に必要な場合にのみタイマー割り込みを発生させます。

| rcu_nocbs
| 1-30,33-62
| このオプションは、指定されたCPUコアからRCUコールバック処理をオフロードします。

| rcu_nocb_poll
| 
| このオプションが設定されている場合、no-RCU-callback CPUは、他のCPUによって明示的にウェイクアップされるのではなく、コールバック処理が必要かどうかを定期的にポーリングして確認します。これにより、割り込みオーバーヘッドを削減できます。

| irqaffinity
| 0,31,32,63
| このオプションにより、カーネルはハウスキーピングコアに対して割り込みを実行できるようになります。

| アイドル
| ポーリング
| これによりアイドル状態からの復帰レイテンシは最小限に抑えられますが、アイドルスレッドでCPUをフルスピードで動作させ続けるという代償が伴います。

| nmi_watchdog
| 0
| このオプションはNMIウォッチドッグのみを無効にします。`nowatchdog`が設定されている場合は、これを省略できます。

| nowatchdog
|
| このオプションは、タイマーハード割り込みコンテキストで実行されるタイマーとして実装されているソフトロックアップウォッチドッグを無効にします。
|===

次のコマンドはGRUB設定を変更し、前述の変更を次回の起動時に適用します。

[#cpu-pinning-k8s]
== KubernetesにおけるCPUピニング

=== RKE2 Versions < v1.32
RKE2設定ファイルを編集して、RKE2クラスターでCPUピニングを有効にします。`/etc/rancher/rke2/config.yaml`ファイルに以下のkubelet引数を追加します。`kubelet-reserved`および`system-reserved`引数でハウスキーピングCPUコアを必ず指定してください：

[,yaml]
----
kubelet-arg:
- "cpu-manager-policy=static"
- "cpu-manager-policy-options=full-pcpus-only=true"
- "cpu-manager-reconcile-period=0s"
- "kubelet-reserved=cpu=0,31,32,63"
- "system-reserved=cpu=0,31,32,63"
----

=== RKE2 Versions >= v1.32
RKE2のバージョンがv1.32以上の場合、アップストリームのKubernetesの慣行に従い、コマンドライン引数を使用してkubeletを設定することはできません。CPUピニングを設定するには、kubelet設定ファイルを作成する必要があります。 https://documentation.suse.com/cloudnative/rke2/latest/en/install/configuration.html#_kubelet_configuration[RKE2ドキュメント]を参照してください。

`01-cpu-pinning.conf`のような新しいkubelet設定ファイルを作成し、`/var/lib/rancher/rke2/agent/etc/kubelet.conf.d/`ディレクトリに配置します：

[,yaml]
----
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
cpuManagerPolicy: static
reservedSystemCPUs: 0,31,32,63
topologyManagerPolicy: single-numa-node
----

設定変更を有効にするには、適切なRKE2サービス（サーバーまたはエージェント）の再起動が必要です。この操作により、ホスト上のRKE2サービスが一時的に中断されます。ノードタイプに応じて、以下のコマンドのいずれかのみを実行してください：

[,shell]
----
# If the node is RKE2 agent
systemctl restart rke2-agent
# Else if the node is RKE2 server
systemctl restart rke2-server
----

=== CPUピニングを活用したワークロードのデプロイ

ワークロードで定義するリクエストと制限に応じて、kubeletで定義された`Static Policy`を使用してこの機能を使用する方法は3つあります。

1. `BestEffort` QoSクラス:`CPU`のリクエストまたは制限を定義しない場合、ポッドはシステムで使用可能な最初の`CPU`にスケジュールされます。
+
`BestEffort` QoSクラスを使用する例は次のとおりです。
+
[,yaml]
----
spec:
  containers:
  - name: nginx
    image: nginx
----
+
2. `Burstable` QoSクラス:CPUのリクエストを定義したが制限と等しくない場合、またはCPUリクエストがない場合。
+
`Burstable` QoSクラスを使用する例は次のとおりです。
+
[,yaml]
----
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
      requests:
        memory: "100Mi"
----
+
または
+
[,yaml]
----
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "2"
      requests:
        memory: "100Mi"
        cpu: "1"
----
+
3.  `Guaranteed` QoSクラス:CPUのリクエストを定義し、それが制限と等しい場合。
+
`Guaranteed` QoSクラスを使用する例は次のとおりです。
+
[,yaml]
----
spec:
  containers:
    - name: nginx
      image: nginx
      resources:
        limits:
          memory: "200Mi"
          cpu: "2"
        requests:
          memory: "200Mi"
          cpu: "2"
----


[#network-parameters]
== ネットワークパラメータ

ネットワークのチューニングは、通信ワークロードで最適なパフォーマンスを実現するために不可欠です。performance-settings.shスクリプトには、バッファサイズ、パケット処理、およびUDPパフォーマンスを最適化するために、さまざまなカーネルネットワークパラメータを設定する`configure_network_tuning`関数が含まれています。

[NOTE]
====
提供されているネットワークチューニング値は、テストおよび検証済みの例です。ただし、これらは特定のユースケース、ワークロード要件、およびハードウェア構成に合わせて調整する必要があります。
====

次のネットワークパラメータがスクリプトによって構成されます。

=== コアネットワークパラメータ

* `net.core.rmem_max` (1342177280バイト):最大受信ソケットバッファサイズ。このパラメータは、任意のソケットでデータを受信するために割り当て可能なメモリの最大量を設定します。

* `net.core.wmem_max` (516777216バイト):送信ソケットバッファの最大サイズ。このパラメータは、任意のソケットでデータを送信するために割り当てることができるメモリの最大量を設定します。

* `net.core.rmem_default` (10000000バイト):受信ソケットバッファのデフォルトサイズ。これは、新しいソケットでデータを受信するための初期バッファサイズです。

* `net.core.wmem_default` (10000000バイト):送信ソケットバッファのデフォルトサイズ。これは、新しいソケットでデータを送信するための初期バッファサイズです。

* `net.core.netdev_max_backlog` (416384パケット):インターフェースがカーネルの処理能力を超える速度でパケットを受信したときに、入力側でキューに入れられるパケットの最大数。この値を増やすと、トラフィックのバースト時にパケットがドロップするのを防ぐのに役立ちます。

* `net.core.optmem_max` (25165824 bytes):ソケットごとに許可される補助バッファの最大サイズ。これは、オプションメモリバッファのサイズに影響します。

* `net.core.netdev_budget` (1024パケット):1回のsoftirq実行で処理できるパケットの最大数。これは、パケット処理中のCPU使用率を制御するのに役立ちます。

=== UDP固有のパラメータ

* `net.ipv4.udp_mem` (11416320 15221760 22832640 ページ):UDPによって使用されるメモリ量（ページ単位）を制御します。3つの値は以下を表します：
** 最小しきい値これより下では、UDPに負荷はかかりません
** 負荷しきい値:UDPがメモリ負荷の適用を開始します
** 最大しきい値UDPの最大メモリページ数

* `net.ipv4.udp_rmem_min` (16384バイト):UDPソケットの最小受信バッファサイズ。UDP受信のベースラインバッファサイズを確保します。

* `net.ipv4.udp_wmem_min` (16384バイト):UDPソケットの最小送信バッファサイズ。UDP送信のベースラインバッファサイズを確保します。

=== リアルタイムスケジューリング

* `kernel.sched_rt_runtime_us` (-1):リアルタイムスロットリングメカニズムを無効にします。これを-1に設定すると、リアルタイムタスクに無制限のCPU時間が許可されます。これは、決定論的なレイテンシを必要とする通信ワークロードに不可欠です。

[IMPORTANT]
====
これらのパラメータは、SUSE Telco Cloud Examplesリポジトリのperformance-settings.shスクリプトを使用すると自動的に構成されます。このスクリプトは、<<atip-automated-provisioning,Automated Provisioning>>セクションで説明されているように、イメージビルドプロセスに統合する必要があります。
====

=== Bond CNI
一般的に、ボンディングは複数のネットワークインタフェースを単一の論理的な「ボンドインタフェース」に集約する方法を提供します。これは通常、冗長なネットワークパスを導入してサービスの可用性を高めるために使用されますが、特定のボンドモードでは帯域幅を増やすためにも使用できます。
Bond CNIプラグインとMultusを組み合わせて使用する場合、以下のCNIプラグインがサポートされています。

* MACVLAN
* ホストデバイス
* SR-IOV

==== MACVLANを使用したBond CNI
MACVLANでBond CNIプラグインを使用するには、コンテナ内に2つの空きネットワークインタフェースが必要です。以下の例では「enp8s0」と「enp9s0」を使用します。まず、それらのネットワークアタッチメント定義を作成します。

*NetworkAttachmentDefinition enp8s0*

[,shell,subs="attributes"]
----
apiVersion: "k8s.cni.cncf.io/v1"
kind: NetworkAttachmentDefinition
metadata:
  name: enp8s0-conf
spec: 
  config: '{
      "cniVersion": "0.3.1",
      "plugins": [
        {
          "type": "macvlan",
          "capabilities": { "ips": true },
          "master": "enp8s0",
          "mode": "bridge",
          "ipam": {}
        }, {
          "capabilities": { "mac": true },
          "type": "tuning"
        }
      ]
    }'
----

*NetworkAttachmentDefinition enp9s0*

[,shell,subs="attributes"]
----
apiVersion: "k8s.cni.cncf.io/v1"
kind: NetworkAttachmentDefinition
metadata:
  name: enp9s0-conf
spec: 
  config: '{
      "cniVersion": "0.3.1",
      "plugins": [
        {
          "type": "macvlan",
          "capabilities": { "ips": true },
          "master": "enp9s0",
          "mode": "bridge",
          "ipam": {}
        }, {
          "capabilities": { "mac": true },
          "type": "tuning"
        }
      ]
    }'
----

次に、ボンド自体のネットワークアタッチメント定義を追加します。

*NetworkAttachmentDefinition bond*

[,shell,subs="attributes"]
----
apiVersion: "k8s.cni.cncf.io/v1"
kind: NetworkAttachmentDefinition
metadata:
  name: bond-net1
spec:
  config: '{
  "type": "bond",
  "cniVersion": "0.3.1",
  "name": "bond-net1",
  "mode": "active-backup",
  "failOverMac": 1,
  "linksInContainer": true,
  "miimon": "100",
  "mtu": 1500,
  "links": [
     {"name": "net1"},
     {"name": "net2"}
  ],
  "ipam": {
    "type": "static",
    "addresses": [
      {
        "address": "192.168.200.100/24",
        "gateway": "192.168.200.1"
      }
    ],
    "subnet": "192.168.200.0/24",
    "routes": [{
      "dst": "0.0.0.0/0"
    }]
  }
}'
----

ここでのIPアドレス割り当ては静的であり、ボンドのアドレスを/24ネットワーク上の「192.168.200.100」と定義し、ゲートウェイはネットワークの最初に使用可能なアドレスに配置されます。ボンドのネットワークアタッチメントでは、必要なボンドのタイプも定義します。この場合はアクティブバックアップです。

このボンドを使用するには、Podがすべてのネットワークインタフェースを認識している必要があります。Pod定義の例は次のようになります。

[,shell,subs="attributes"]
----
apiVersion: v1
kind: Pod
metadata:
  name: test-pod
  annotations:
        k8s.v1.cni.cncf.io/networks: '[
{"name": "enp8s0-conf",
"interface": "net1"
},
{"name": "enp9s0-conf",
"interface": "net2"
},
{"name": "bond-net1",
"interface": "bond0"
}]'
spec:
  restartPolicy: Never
  containers:
  - name: bond-test
    image: alpine:latest
    command:
      - /bin/sh
      - "-c"
      - "sleep 60m"
    imagePullPolicy: IfNotPresent
----

アノテーションがどのようにすべてのネットワークを参照し、インターフェース「enp8s0 -> net1」と「enp9s0->net2」の間のマッピングを定義しているかに注目してください。

==== SR-IOVでのボンドCNI
SR-IOVでボンドCNIを使用するのは非常に簡単です。SR-IOVのセットアップ方法の詳細については、<<sriov>>を参照してください。そこに記載されているように、`SriovNetworkNodePolicies`を作成して、`resourceNames`や仮想関数の数などを定義する必要があります。`resourceNames`は、ポッド定義でインターフェースとして使用される`SriovNetwork`によって使用されます。ボンドの定義は、MACVLANおよびホストデバイスの場合とまったく同じです。

[NOTE]
====
SR-IOVでのボンドCNIは、カーネルドライバーを使用するSR-IOV仮想関数（VF）にのみ適用されます。DPDKワークロードで使用されるようなユーザースペースドライバーVFは、ボンドCNIでボンディングすることはできません。

[#sriov]
== SR-IOV

SR-IOV（Single Root I/O Virtualization）を使用すると、ネットワークアダプターなどの単一の物理デバイスが、そのリソースを複数の`PCIe`ハードウェア関数に分離できます。これにより、さまざまなアプリケーションがリソースに直接アクセスできるようになります。

クラスターに`SR-IOV`をデプロイするために、2つの異なる方法を提供しています。

* <<option1-sriov-deviceplugin>>:このメソッドは、ネットワークデバイスとvRANアクセラレータの両方をサポートしています。
* <<option2-sriov-helm>>:この自動化されたメソッドにより、デプロイメントが簡素化されます。このメソッドはネットワークデバイス専用です。

ネットワークデバイスにNetwork Operatorを使用し、vRANアクセラレータにDevice Pluginを使用するというように、両方のソリューションが必要な稀なケースでは、それらを別々のKubernetesネームスペースにデプロイする必要があります。この分離は、2つのデプロイメント間の競合を防ぐために不可欠です。

[#option1-sriov-deviceplugin]
=== オプション1:SR-IOV Network Device Plugin DaemonsetおよびconfigMap

https://github.com/k8snetworkplumbingwg/sriov-network-device-plugin[SR-IOV Network Device Plugin]は、PCI物理機能（PF）やその仮想機能（VF）などのネットワークリソースをKubernetesホスト上で検出し、アドバタイズします。

* デバイスプラグイン用のconfig mapを準備します

SR-IOVリソースプールを定義するconfig mapを作成する必要があります。`lspci`コマンドを実行して情報を取得します。

[,shell]
----
$ lspci | grep -i acc
07:00.0 Processing accelerators: Intel Corporation Device 57c2

SR-IOV Device Pluginは、Kubernetesが公開すべきハードウェアリソースを定義するJSONファイルを含むconfigMapを使用します。この構成は、2つのコアとなる概念、`selectors`（ハードウェア検出用）と`resources`（Kubernetes公開用）に基づいています。

`resource`とは、Podが消費する名前付きエンティティです（例: `rancher.io/intel_fec_5g`）。リソースは、次の2つのタイプのいずれかとして定義できます。

* `accelerator`:vRANアクセラレータカード（ACC100/vRAN Boostなど）に使用されます。
* `netdevice`:標準のネットワークインタフェース（NIC）に使用されます。

ノード上のハードウェアをフィルタリングするために`selectors`を使用してターゲットデバイスを定義します。

* `vendors`:`8086` (Intel)
* `devices`:`57c3` (FEC VF)、`1889` (NIC VF)
* `drivers`: `vfio-pci`
* `pfNames`: `eno16595np0` (物理インターフェイス名)

ネットワークカードの場合、物理機能（PF）から仮想機能（VF）のサブセットを選択することもできます。

* `pfNames`: `["eth1#1,2,3,4,5,6"]` または `[eth1#1-6]`

ポッドがデバイスを要求できるようにするには、各リソースに名前を付ける必要があります。この名前は、プレフィックスと名前で構成されます。

* `resourceName`: `pci_sriov_net_bh_dpdk`
* `resourcePrefix`: `rancher.io`

ポッドは、結合されたリソース名 `rancher.io/pci_sriov_net_bh_dpdk` を要求します。

[NOTE]
====
このドキュメントには、すべての可能なセレクターが記載されているわけではありません。リソースの種類によって、使用するセレクターのセットが異なります。詳細については、 https://github.com/k8snetworkplumbingwg/sriov-network-device-plugin[SR-IOV Network Device Pluginリポジトリ]を参照してください。
====

[#dpdk]
== DPDK

`DPDK`（Data Plane Development Kit）は、高速なパケット処理のためのライブラリおよびドライバーのセットです。これは、さまざまなCPUアーキテクチャで実行されるパケット処理ワークロードを高速化するために使用されます。
DPDKには、データプレーンライブラリと、以下に対する最適化されたネットワークインタフェースコントローラ（`NIC`）ドライバーが含まれています。

1. キューマネージャーは、ロックレスキューを実装します。
2. バッファーマネージャーは、固定サイズのバッファーを事前割り当てします。
3. メモリーマネージャーは、メモリー内のオブジェクトプールを割り当て、リングを使用して空きオブジェクトを格納します。また、オブジェクトがすべての `DRAM` チャネルに均等に分散されるようにします。
4. ポーリングモードドライバー（`PMD`）は、非同期通知なしで動作するように設計されており、オーバーヘッドを削減します。
5. パケットフレームワークは、パケット処理の開発を支援するライブラリのセットです。

以下の手順では、`DPDK`を有効にする方法と、`DPDK`インターフェイスで使用する`NICs`から`VFs`を作成する方法を説明します。

* `DPDK`パッケージをインストールします。

[,shell]
----
$ transactional-update pkg install dpdk dpdk-tools libdpdk-25
$ reboot
----


* カーネルパラメータ:

DPDKを使用するには、いくつかのドライバーを使用してカーネル内の特定のパラメーターを有効にします。

|===
| パラメータ」 | 値 | description

| iommu
| pt
| このオプションは、DPDKインターフェイス用の`vfio`ドライバーの使用を有効にします。

| intel_iommu or amd_iommu
| on
| このオプションは、`vfio`用の`VFs`の使用を有効にします。
|===

パラメーターを有効にするには、それらを`/etc/default/grub`ファイルに追加します。

[,shell]
----
GRUB_CMDLINE_LINUX="BOOT_IMAGE=/boot/vmlinuz-6.4.0-9-rt root=UUID=77b713de-5cc7-4d4c-8fc6-f5eca0a43cf9 skew_tick=1 rd.timeout=60 rd.retry=45 console=ttyS1,115200 console=tty0 default_hugepagesz=1G hugepagesz=1G hugepages=40 hugepagesz=2M hugepages=0 ignition.platform.id=openstack net.ifnames=1 intel_iommu=on iommu=pt irqaffinity=0,31,32,63 isolcpus=domain,nohz,managed_irq,1-30,33-62 nohz_full=1-30,33-62 nohz=on mce=off nosoftlockup nowatchdog nmi_watchdog=0 quiet rcu_nocb_poll rcu_nocbs=1-30,33-62 rcupdate.rcu_cpu_stall_suppress=1 rcupdate.rcu_expedited=1 rcupdate.rcu_normal_after_boot=1 rcupdate.rcu_task_stall_timeout=0 rcutree.kthread_prio=99 security=selinux selinux=1 idle=poll"
----

GRUB構成を更新し、システムを再起動して変更を適用します。

[,shell]
----
$ transactional-update grub.cfg
$ reboot
----

* `vfio-pci`カーネルモジュールをロードし、NICで`SR-IOV`を有効にします。最初の引数はSR-IOVをサポートする`vfio-pci`ドライバーを示し、2番目の引数はPCIデバイスがアイドル状態のときに低電力状態になるのを防ぎます。

[,shell]
----
$ modprobe vfio-pci enable_sriov=1 disable_idle_d3=1
----

* `NICs`からいくつかの仮想機能（`VFs`）を作成します。

`VFs`用に、例えば2つの異なる`NICs`用に作成するには、以下のコマンドが必要です。

[,shell]
----
$ echo 4 > /sys/bus/pci/devices/0000:51:00.0/sriov_numvfs
$ echo 4 > /sys/bus/pci/devices/0000:51:00.1/sriov_numvfs
----

* 新しいVFを`vfio-pci`ドライバーにバインドします。

[,shell]
----
$ dpdk-devbind.py -b vfio-pci 0000:51:01.0 0000:51:01.1 0000:51:01.2 0000:51:01.3 \
                              0000:51:11.0 0000:51:11.1 0000:51:11.2 0000:51:11.3
----

* 構成が正しく適用されていることを確認します。

[#acceleration]
== vRANアクセラレーション（`Intel ACC100/VRB1/VRB2`）

通信サービスプロバイダーが4Gから5Gネットワークへ移行するにつれ、多くのプロバイダーが、より高いチャネル容量と、エッジベースのサービスやアプリケーションの容易な展開を実現するために、仮想化無線アクセスネットワーク（vRAN）アーキテクチャを採用しています。vRANソリューションは、リアルタイムトラフィックの量やネットワーク上の需要に基づいて容量を増減できる柔軟性を備え、低遅延サービスを提供するのに理想的な位置にあります。

最も計算集約的な4Gおよび5Gワークロードの1つが、RAN階層1（`L1`）`FEC`であり、これは信頼性の低い、またはノイズの多い通信チャネルでのデータ伝送エラーを解決します。`FEC`テクノロジーは、4Gまたは5Gデータ内の限られた数のエラーを検出および修正し、再送信の必要性を排除します。`FEC`アクセラレーショントランザクションにはセル状態情報が含まれていないため、簡単に仮想化でき、プーリングの利点と容易なセル移行が可能になります。

歴史的に、Intelはレイヤー1 FECアルゴリズムを迅速に実行し、メインCPUのホスト処理能力を解放するために、ACC100 vRANアクセラレータカードを提供してきました。Intelはその後、Sapphire Rapidsを皮切りに、このテクノロジーを`Intel vRAN Boost`（VRB）という名称で新しいCPUに直接統合しました。Intel vRAN BoostはCPU自体でオフロードアクセラレーターとして機能し、個別のハードウェアカードを不要にします。本セクションでは、ワークロードがACC100またはIntel vRAN Boostを活用するためのSUSE Telco Cloudの構成について詳しく説明します。

[#huge-pages]
== ヒュージページ

プロセスが`RAM`を使用する場合、`CPU`はそのプロセスによって利用される正確な部分をマークします。効率を達成するために、`CPU`は`RAM`を`pages`と呼ばれるブロックで割り当てます。多くのプラットフォームでのデフォルトの`page`サイズは`4 KB`です。ページはディスクにスワップされることがあります（他の操作の中でも）。

プロセスのアドレス空間は仮想であるため、`CPU`とオペレーティングシステムは、どの`pages`が各プロセスに属し、それぞれがどこに格納されているかを追跡する必要があります。`pages`の数が多いほど、メモリマッピングの検索に時間がかかります。例えば、`1 GB`のメモリを使用するプロセスでは、262,144個のエントリを確認する必要があります（1 GB / 4 KB）。各`page table entry`が8バイトを占める場合、参照するデータの合計は`2 MB`（262,144 * 8）になります。

現在のほとんどの`CPU`アーキテクチャでは、デフォルトの`4 KB`値よりも大きいサイズの`pages`ブロックを定義できます（`1 GB`や`2 MB`が一般的なサポート値です）。これは`huge pages`として知られており、`CPU/Operating System`が参照しなければならないエントリの数を減らします。

* カーネルパラメータ

`huge pages`を有効にするには、以下のカーネルパラメータを追加する必要があります。この例では、`1 GB`サイズのページを40ページ、`2 MB`サイズのページを0ページ設定しますが、サポートする巨大なページサイズと各ページの正確な数は、アプリケーションのメモリ要件に応じて調整してください。

|===
| パラメータ」 | 値 | description

| hugepagesz
| 1G
| このオプションを使用すると、「ヒュージページ」のサイズを1 GBに設定できます。

| ヒュージページ
| 40
| これは、直前に定義されたサイズ (1 GB) に対して、起動時に割り当てるよう要求される「ヒュージページ」の数です。

| hugepagesz
| 2M
| このオプションを使用すると、「ヒュージページ」のサイズを2 MBに設定できます。

| ヒュージページ
| 0
| これは、直前に定義されたサイズ (2 MB) に対して、起動時に割り当てるよう要求される「ヒュージページ」の数です。

| default_hugepagesz
| 1G
| これは、「ヒュージページ」サイズのデフォルト値です。
|===

GRUBファイル`/etc/default/grub`を変更し、`GRUB_CMDLINE_LINUX`にこれらのパラメーターを追加します。

[,shell]
----
default_hugepagesz=1G hugepagesz=1G hugepages=40 hugepagesz=2M hugepages=0
----

GRUB設定を更新し、システムを再起動して変更を適用します。

[,shell]
----
$ transactional-update grub.cfg
$ reboot
----

再起動後にパラメーターが適用されたことを確認するには、コマンドラインを確認します。

[,shell]
----
$ cat /proc/cmdline
----

* ヒュージページの使用

ヒュージページを使用するには、それらをマウントする必要があります。

[,shell]
----
$ mkdir -p /hugepages
$ mount -t hugetlbfs nodev /hugepages
----

Kubernetesワークロードをデプロイし、リソースとボリュームを作成します。

[,yaml]
----
...

   requests:
     memory: "24Gi"

   limits:
     memory: "24Gi"
     hugepages-1Gi: 16Gi
     intel.com/intel_sriov_oru: '4'
...
----

[,yaml]
----
...

  - name: hugepage
    mountPath: /hugepages
...

    emptyDir:
      medium: HugePages

[#numa-aware-scheduling]
== NUMA対応スケジューリング

Non-Uniform Memory Access（不均一メモリアクセス）またはNon-Uniform Memory Architecture（`NUMA`）は、`SMP`（マルチプロセッサ）アーキテクチャで使用される物理メモリ設計であり、メモリへのアクセス時間はプロセッサに対するメモリの場所によって異なります。`NUMA`では、プロセッサは非ローカルメモリ（別のプロセッサのローカルメモリやプロセッサ間で共有されるメモリ）よりも、自身のローカルメモリに高速にアクセスできます。

=== NUMAノードの特定

`NUMA`ノードを特定するには、システム上で次のコマンドを使用します。

[,shell]
----
$ lscpu | grep NUMA
NUMA node(s):                       1
NUMA node0 CPU(s):                  0-63
----

[NOTE]
====
この例では、64個の`CPUs`を表示する`NUMA`ノードが1つだけあります。

`NUMA`は`BIOS`で有効にする必要があります。`dmesg`に起動時のNUMA初期化の記録がない場合、カーネルリングバッファ内の`NUMA`関連のメッセージが上書きされている可能性があります。
====



[#metal-lb-configuration]
== Metal LB

`MetalLB`は、`L2`や`BGP`などの標準的なルーティングプロトコルをアドバタイズメントプロトコルとして使用する、ベアメタルKubernetesクラスター向けのロードバランサー実装です。これは、ベアメタル環境でKubernetesサービスのタイプ`LoadBalancer`を使用する必要があるため、Kubernetesクラスター内のサービスを外部に公開するために使用できるネットワークロードバランサーです。

`RKE2`クラスターで`MetalLB`を有効にするには、次の手順が必要です。

* 次のコマンドを使用して`MetalLB`をインストールします。

[,shell,subs="attributes,specialchars"]
----
$ kubectl apply <<EOF -f
apiVersion: helm.cattle.io/v1
kind: HelmChart
metadata:
  name: metallb
  namespace: kube-system
spec:
  chart: oci://registry.suse.com/edge/charts/metallb
  targetNamespace: metallb-system
  version: {version-metallb-chart}
  createNamespace: true
---
apiVersion: helm.cattle.io/v1
kind: HelmChart
metadata:
  name: endpoint-copier-operator
  namespace: kube-system
spec:
  chart: oci://registry.suse.com/edge/charts/endpoint-copier-operator
  targetNamespace: endpoint-copier-operator
  version: {version-endpoint-copier-operator-chart}
  createNamespace: true
EOF
----

* `IpAddressPool`と`L2advertisement`の設定を作成します。

[,yaml]
----
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: kubernetes-vip-ip-pool
  namespace: metallb-system
spec:
  addresses:
    - 10.168.200.98/32
  serviceAllocation:
    priority: 100
    namespaces:
      - default
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: ip-pool-l2-adv
  namespace: metallb-system
spec:
  ipAddressPools:
    - kubernetes-vip-ip-pool
----

* `VIP`を公開するためのエンドポイントサービスを作成します。

[,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: kubernetes-vip
  namespace: default
spec:
  internalTrafficPolicy: Cluster
  ipFamilies:
  - IPv4
  ipFamilyPolicy: SingleStack
  ports:
  - name: rke2-api
    port: 9345
    protocol: TCP
    targetPort: 9345
  - name: k8s-api
    port: 6443
    protocol: TCP
    targetPort: 6443
  sessionAffinity: None
  type: LoadBalancer
----

* `VIP`が作成され、`MetalLB`ポッドが実行されていることを確認します。

[,shell]
----
$ kubectl get svc -n default
$ kubectl get pods -n default
----

[#private-registry]
== プライベートレジストリの設定

`Containerd`は、プライベートレジストリに接続し、それを使用して各ノードでプライベートイメージをプルするように設定できます。

起動時に、`RKE2`は`/etc/rancher/rke2/`に`registries.yaml`ファイルが存在するかどうかを確認し、ファイルで定義されているレジストリを使用するように`containerd`に指示します。プライベートレジストリを使用する場合は、レジストリを使用する各ノードでルートユーザーとしてこのファイルを作成してください。

プライベートレジストリを追加するには、次の内容でファイル`/etc/rancher/rke2/registries.yaml`を作成します。

[,yaml]
----
mirrors:
  docker.io:
    endpoint:
      - "https://registry.example.com:5000"
configs:
  "registry.example.com:5000":
    auth:
      username: xxxxxx # this is the registry username
      password: xxxxxx # this is the registry password
    tls:
      cert_file:            # path to the cert file used to authenticate to the registry
      key_file:             # path to the key file for the certificate used to authenticate to the registry
      ca_file:              # path to the ca file used to verify the registry's certificate
      insecure_skip_verify: # may be set to true to skip verifying the registry's certificate
----

または認証なしの場合:

[,yaml]
----
mirrors:
  docker.io:
    endpoint:
      - "https://registry.example.com:5000"
configs:
  "registry.example.com:5000":
    tls:
      cert_file:            # path to the cert file used to authenticate to the registry
      key_file:             # path to the key file for the certificate used to authenticate to the registry
      ca_file:              # path to the ca file used to verify the registry's certificate
      insecure_skip_verify: # may be set to true to skip verifying the registry's certificate
----

レジストリの変更を有効にするには、ノードでRKE2を開始する前にこのファイルを設定するか、構成済みの各ノードでRKE2を再起動する必要があります。

[NOTE]
====
これに関する詳細については、 https://documentation.suse.com/cloudnative/rke2/latest/en/install/containerd_registry_configuration.html#_registries_configuration_file[containerd registry configuration rke2]を確認してください。

[#ptp-introduction]
=== 概要

IEEE 1588標準で定義されている高精度時刻同期プロトコル (PTP) は、パケットネットワーク上で高精度の時刻を配信します。ネットワークインタフェース (NIC) がハードウェアでPTPパケットにタイムスタンプを付与すると、NTPが提供できる範囲をはるかに超えるサブマイクロ秒の精度に達します。通信事業者の環境において、PTPは5G無線アクセスネットワーク (RAN) の中核となる構成要素であり、無線ユニットが正しく送信を行うには厳密な位相と時刻の同期が必要です。SUSE Telco Cloudは、`linuxptp`パッケージを通じてPTPを実装しており、以下に説明する通信事業者向けプロファイルITU-T G.8275.1およびITU-T G.8275.2を対象としています。

PTPドメインは、少数のクロック役割で構成されます。

* *グランドマスター (GM)*: ドメインの主要な時刻源です。通常、GNSS受信機によって駆動されるプライマリリファレンスタイムクロック (PRTC) に同期し、下流のノードに時刻を送信します。GMの精度が、ドメイン全体の品質上限を決定します。
* *オーディナリークロック (OC)*: 単一のPTPポートを持つエンドノードです。通信事業者のデプロイメントでは、タイムレシーバーとして機能し、上流のグランドマスターまたはバウンダリークロックからローカルクロックを調整します。無線ワークロードを実行するコンピュートノードは、典型的なOCです。
* *バウンダリークロック (BC)*: 1つのポートで時刻を受信し (タイムレシーバー)、残りのポートで他のノードに向けて時刻を再生成する (タイムトランスミッター) マルチポートノードです。パス上にバウンダリークロックを挿入することで、各OCとリファレンス間のチェーンが短縮され、ネットワークでホップごとに蓄積される誤差が制限されます。

トポロジーを設計する際、オーディナリークロックとバウンダリークロックの区別が重要になります。

* *オーディナリークロック (OC)*は、*単一*のPTPポートを持ち、ドメインの端に配置されます。
自身のクロックを制御するためにのみ時刻を消費し、他のノードに時刻を転送することはありません。
* *バウンダリークロック (BC)*は、*複数*のPTPポートを持ちます。Time Receiverポートで時刻を消費し、Time Transmitterポートでそれを*再生成*することで、アップストリームのタイミングチェーンを終端し、ダウンストリームで新しいタイミングチェーンを開始します。この再生成により、長いノードチェーン全体で誤差が蓄積されるのを防ぎます。

以下のハードウェアおよびシグナリング要素がこれらの役割をサポートします。

* *PTP Hardware Clock (PHC)*：PTPが実際に同期を行う、NICに組み込まれたクロックです。オペレーティングシステムのクロックをPHCに合わせることは、専用のデーモンによって処理される別のステップです。
* *Synchronous Ethernet (SyncE)*：物理層の周波数同期です。PTPはパケット内で位相と時刻を伝送しますが、SyncEはイーサネット信号から直接安定した周波数を復元します。SyncEは*オプションの拡張機能*です。PTP単体でもすでに位相と時刻を提供しており、SyncEは、ノードがより強力な周波数安定性を必要とする場合や、PTP時刻ソースが一時的に失われた場合に備えてより長いホールドオーバーが必要な場合に追加されます。
* *Digital Phase-Locked Loop (DPLL)*：基準信号に同期し、それをフィルタリングして安定したクリーンなクロックを出力するハードウェアタイミングブロックです。これは、利用可能な入力からPHCを制御し、複数のNICを持つプラットフォームでは、異なるNICクロックを調整する役割を果たします。

各ノードにおいて、これらの機能は`linuxptp`デーモンによって実行されます。`ptp4l`はPTPプロトコルを実行してPHCを制御し、`phc2sys`はシステムクロックをPHCに合わせます。グランドマスターでは、`ts2phc`がさらにGNSS基準からPHCを制御します。それらの役割とインストールについては<<ptp-prerequisites>>で説明されています。

ハードウェアクロック自体は、LinuxカーネルのDPLLサブシステムとネットワークドライバによって処理されます。タイミング制御の度合い、およびマルチNICノード内でのタイミングの分散方法は、管理可能なDPLLがどこに配置されているかによって異なります。

* *NIC with an integrated DPLL*：DPLLはNICに組み込まれており、Linux DPLLサブシステムを通じて構成されます。選択されたリファレンスにロックし、PHCを制御することで、周波数とホールドオーバーを完全に管理します。
* *統合DPLLのないNIC*：NICは構成可能なDPLLを備えておらず、`ptp4l`はPHCを直接制御します。サブシステムはロックステータスを（読み取り専用で）報告するにとどまり、高度な周波数処理は外部のタイミングソースに依存します。
* *複数のNIC間で共有されるオンボードDPLL*：DPLLは単一のNICに組み込まれているのではなく、NICの外部にあるプラットフォーム上に配置されています。これは、共通のリファレンスから複数のNICのPHCを制御して同期を維持するため、ノード内のすべてのNICが同じ時刻を共有します。この構成は、外部ケーブルに頼らずに内部でタイミングを配信するマルチNICプラットフォームで使用されます。

* *ITU-T G.8275.1*（フルタイミングサポート）：マルチキャストを使用してイーサネット（レイヤー2）上で直接実行されます。パス上のすべてのノードはPTPに対応し、<em>バウンダリークロック</em>として機能する必要があり、これにより最高の精度が得られます。特に明記されていない限り、このガイドのシナリオではこのプロファイルを使用します。

[#ptp-prerequisites]
=== 前提条件

本ガイドでは通信事業者固有のプロファイルのみを扱うため、ハードウェアタイムスタンプおよびNIC内のPTPハードウェアクロック（PHC）が前提となります。通信事業者グレードのNICはハードウェアでPTPをサポートしています。特定のインターフェースの機能は、`ethtool -T`で確認できます。

[,console]
----
# ethtool -T eno16495np0
Time stamping parameters for eno16495np0:
Capabilities:
        hardware-transmit
        software-transmit
        hardware-receive
        software-receive
        software-system-clock
        hardware-raw-clock
PTP Hardware Clock: 0
Hardware Transmit Timestamp Modes:
        off
        on
Hardware Receive Filter Modes:
        none
        all
----

`hardware-transmit`、`hardware-receive`、`hardware-raw-clock`の機能と、0以上の`PTP Hardware Clock`インデックスを確認してください（`-1`という値は、インターフェースにPHCがないことを意味します）。`eno16495np0`を、PTPに使用する予定のインターフェースに置き換えてください。

PTPは、`linuxptp`パッケージによって提供されます。これには、`systemd`によって管理される長時間実行デーモンとして実行される3つのユーザスペースプログラム（`ptp4l`、`phc2sys`、`ts2phc`）が含まれています（それぞれ専用のサービス：`ptp4l.service`、`phc2sys.service`、`ts2phc.service`）。これらは集合的にプロトコルを実行し、クロックを同期させ続けます。

* `ptp4l`: PTPデーモン。これは、構成されたインターフェース上でIEEE 1588プロトコルを実行し、Best Master Clock Algorithm (BMCA) を適用して各ポートの役割を決定し、NICのPHCを調整します。単一の `ptp4l` インスタンスは複数のポートを管理でき、これによってノードがバウンダリクロックとして機能できるようになります。
* `phc2sys`: 2つのクロックを同期させます。これは通常、システム（オペレーティングシステム）クロックを `ptp4l` が同期し続けるPHCに合わせるために使用され、システム時刻もPTPに従うようにします。
* `ts2phc`: 「PHCへのタイムスタンプ」。これは、GNSS受信機によって配信されるPPSなどの外部時刻信号からPHCを調整します。これは、グランドマスターで使用され、同じノード内の複数のPHCを同期させるために使用されます。

ダウンストリームクラスターにPTPをインストールする推奨される方法は、Edge Image Builder (EIB) 定義ファイルの `packageList` に `linuxptp` パッケージを追加し、プロビジョニング中に自動的にデプロイされるようにすることです。パッケージのインストールに関する詳細については、xref:../quickstart/eib.adoc#eib-configuring-rpm-packages[EIB documentation] を参照してください。

[,yaml,subs="attributes"]
----
apiVersion: {version-eib-api-latest}
image:
  imageType: RAW
  arch: x86_64
  baseImage: {micro-base-rt-image-raw}
  outputImageName: eibimage-slmicrort-telco.raw
operatingSystem:
  systemd:
    enable:
      - ptp4l
      - phc2sys
  packages:
    packageList:
      - linuxptp
    sccRegistrationCode: $SCC_REGISTRATION_CODE
----

[NOTE]
====
`linuxptp`パッケージは、デフォルトでは `ptp4l`、`phc2sys`、または `ts2phc` を有効にしません。
設定ファイルをデプロイした後、マニフェストの `systemd` セクションを使用して、必要なノードデーモンを有効にします（以下のシナリオを参照してください）。
====

最後に、使用するPTPプロファイルによって、ノード間のネットワークスイッチをPTP対応デバイスとして構成する必要があるかどうかが決まります。

* *ITU-T G.8275.1 (full timing support)*: マルチキャストを使用してイーサネット（レイヤー2）上で直接実行されます。パス上のすべてのノードはPTP対応であり、バウンダリクロックとして機能する必要があります。これにより最高の精度が得られます。したがって、介在するスイッチはPTP用に構成する必要があります。特に明記されていない限り、このガイドのシナリオではこのプロファイルを使用します。
* *ITU-T G.8275.2 (partial timing support)*: ユニキャストを使用してIP（レイヤー3）上で実行されます。
中間ノードはPTPをサポートする必要がないため、タイミングはタイミング非対応のネットワーク
セグメントを通過でき、スイッチにPTP設定は不要ですが、その代償として精度が低下します。

[#ptp-scenario-oc]
=== シナリオ1a - オーディナリークロック（PTPのみ）

*説明*

これは最も単純なPTPデプロイメントです。単一のクラスタノードがアップストリームソースから時刻を取得し、ローカルクロックを調整しますが、別のノードに時刻を転送することはありません。このノードは、タイムレシーバーの役割を持つ単一のPTPポートを備えたオーディナリークロック（OC）として動作します。

OCノードでは、使用するプロファイルに関係なく、タイミングはすべて`linuxptp`デーモンによって処理されます。ノードは単一のNICを使用し、`ptp4l`が直接PHCを調整するため、DPLL設定や`ts2phc`は不要です。

* `ptp4l`は受信インターフェース上でPTPプロトコルを実行します。ベストマスタークロックアルゴリズム（BMCA）がアップストリームノードをマスターとして選択し、ローカルポートが`SLAVE`状態に遷移し、`ptp4l`がNICのPTPハードウェアクロック（PHC）を調整します。
`clientOnly 1`を設定すると、ノードはタイムレシーバーの役割に制限されるため、マスターとして選択されることはありません。
* `phc2sys`はシステムクロック(`CLOCK_REALTIME`)を`ptp4l`が同期を維持するPHCに合わせるため、オペレーティングシステムの時刻もPTPに従います。

このシナリオはどちらかの通信事業者向けプロファイルで実装可能です。これらはトランスポート
や介在するネットワークが提供すべき内容が異なり、以下に2つの独立したモデルとして文書化されています。

* *<<ptp-scenario-oc-model1,モデル1 — ITU-T G.8275.1>>*（レイヤー2マルチキャスト）：マスターとOC間のすべてのホップがPTP対応である場合に使用します。これは最高の精度を提供し、通信事業者向けデプロイメントのデフォルトです。
* *<<ptp-scenario-oc-model2,モデル2 — ITU-T G.8275.2>>*（レイヤー3ユニキャスト）：OCがPTP非対応のネットワークを介してマスターに到達する必要がある場合に使用しますが、精度が低下します。

[IMPORTANT]
====
オーディナリークロックは、一度に1つのPTPプロファイルのみを実行します。これら2つのモデルは相互排他的です。特定のノードには、どちらか一方のみを設定してください。選択したプロファイルの設定ファイルのみを作成し、`/etc/sysconfig/ptp4l`ではそのファイルのみを参照してください。`/etc/ptp4l-G.8275.1.conf`と`/etc/ptp4l-G.8275.2.conf`の両方を作成しないでください。また、`OPTIONS=`行に両方のファイルを渡さないでください。
====

[[ptp-scenario-oc-model1]]
*モデル1 — ITU-T G.8275.1（レイヤー2マルチキャスト）*

G.8275.1はイーサネット上で直接実行され、そのメッセージを転送不可能なマルチキャストMAC `01:80:C2:00:00:0E`に送信します。標準的なブリッジはこれを転送しないため、パス上のすべてのデバイスがPTPを終端および再生成する必要があります。コンポーネントは以下の通りです。

* *Grandmaster (GM)*: PTPドメイン（G.8275.1の場合はドメイン `24`）のアップストリームリファレンスで、通常はGNSS/PRTCソースにロックされています。
* *PTP-aware switch*: Boundary Clockとして機能します。GMに向かうポートはTime Receiverであり、OCに向かうポートはTime Transmitterです。両方のポートでPTPを有効にする必要があります。
* *Ordinary Clock (OC)*: クラスターノードであり、単一のPTPポートで時刻を受信します。

.Ordinary Clock (OC) — G.8275.1 (レイヤー2マルチキャスト)
image::product-atip-ptp-scenario-oc.png[シナリオ1a - G.8275.1を使用したオーディナリークロック（PTPのみ）,scaledwidth=100%]

ノードを以下のように設定します。

. PTPに使用するインターフェースのPHCインデックス `<N>`（ここでは `eno8403np1`）を特定します。出力されたフィールド `PTP Hardware Clock`（`Hardware timestamp provider index`と表示される場合もあります）の値は、`/dev/ptp<N>`デバイスを示し、`ptp4l`がこれを調整し、`phc2sys`がソースとして読み取るものです。
+
[,console]
----
# ethtool -T eno8403np1
Time stamping parameters for eno8403np1:
Capabilities:
        hardware-transmit
        hardware-receive
        hardware-raw-clock
PTP Hardware Clock: 1
...
----
+
この例では、`eno8403np1`のPHCは `/dev/ptp1` です。

. `ptp4l`設定ファイル`/etc/ptp4l-G.8275.1.conf`を作成します。インターフェースはセクション（`[eno8403np1]`）として宣言されるため、デーモンに`-i`フラグは不要です。
+
[#ptp-conf-oc-g8275-1]
.オーディナリークロック設定 — ITU-T G.8275.1
====
[source,]
----
# Telecom G.8275.1 — Ordinary Clock (Time Receiver)
[global]
domainNumber                    24
priority2                       255
dataset_comparison              G.8275.x
G.8275.portDS.localPriority     128
G.8275.defaultDS.localPriority  128
maxStepsRemoved                 255
logAnnounceInterval             -3
logSyncInterval                 -4
logMinDelayReqInterval          -4
announceReceiptTimeout          3
clientOnly                      1
ptp_dst_mac                     01:80:C2:00:00:0E
network_transport               L2
summary_interval                3
message_tag                     "ptp4l"
uds_address                     /var/run/ptp4l
uds_ro_address                  /var/run/ptp4lro

[eno8403np1]
----
====
+
`ptp_dst_mac`の値はG.8275.1で固定されています。これは、PTPを単一のリンクに限定する転送不可能なマルチキャストアドレス`01:80:C2:00:00:0E`であり、これがパス上のすべてのデバイスがPTP対応でなければならない理由です。`uds_address`は、`phc2sys`がポート状態を追跡するために使用する管理ソケットを公開します。

. `ptp4l`で`/etc/sysconfig/ptp4l`がこのファイルを指すようにします。
+
[source,]
----
OPTIONS="-f /etc/ptp4l-G.8275.1.conf"
----

. `/etc/sysconfig/phc2sys`で`phc2sys`を設定し、PTPインターフェース（`/dev/ptp1`）のPHCからシステムクロックを制御します。`--uds_address`と`--domainNumber`の値は、`ptp4l`の設定と一致している必要があります。
+
[source,]
----
OPTIONS="-s /dev/ptp1 -w -m --uds_address /var/run/ptp4l --domainNumber 24"
----
+
`-s /dev/ptp1`はPHCをソースクロックとして選択し、`-w`は`ptp4l`が同期するのを待ってからシステムクロックをステップし、`-m`はサーボステータスをログに出力します。

. 両方のサービスを有効にして開始します。
+
[,console]
----
# systemctl enable --now ptp4l phc2sys
----

=== シナリオ2a - バウンダリクロック (PTPのみ)、マルチポートシングルNICを使用し、オーディナリクロックサーバーへの伝搬を含む

*説明*

このシナリオでは、ITU-T G.8275.1 (PTPのみ、レイヤー2) を介して、ダウンストリームのオーディナリクロック(OC) に向けてPTPを再生成するバウンダリクロック(BC)を用いてタイミングチェーンを拡張します。BCは単一のマルチポートNICを使用します。1つの`ptp4l`インスタンスが同じNIC上の複数のポートを管理するため、`ts2phc`もDPLLルーティングも必要ありません (マルチNICシナリオとは異なります)。

このシナリオには、以下のコンポーネントが含まれます。

* *グランドマスター (GM)*: PTPドメイン (ドメイン`24`) のリファレンスであり、通常はGNSS/PRTCソースにロックされています (ここで使用するテストベンチにはGNSSがないため、後述する`gm.ClockClass`の劣化が生じます)。アップストリームセグメントに時刻を送信します。
* *PTP対応スイッチ*: タイミングパス上でバウンダリクロック (T-BC) として機能します。PTPを伝送するすべてのポートには`ptp enable`が設定されています。
* *バウンダリクロック (BCサーバー)*: 2つのPTPセグメントをブリッジする、単一NIC上のマルチポートノードです。その`eno8403np1`ポートはタイムレシーバー (SLAVE) として*アップストリーム*セグメントに向き、NICのPHCを制御します。`eno8503np2` (および`eno8603np3`) はタイムトランスミッターとして*ダウンストリーム*セグメントに向き、PTPを再生成します。BCはアップストリームのタイミングチェーンを終端し、ダウンストリーム側で新しいタイミングチェーンを開始します。
* *オーディナリークロック（OCサーバー）*：*ダウンストリーム*セグメント上にあるシングルポートノード（`ens6f0np0`）であり、その唯一のPTPマスターはBCです。BCが再生成した時点からローカルクロックを調整します。

タイミングは、各ノードの`linuxptp`デーモンによって処理されます。

* *BCサーバー*では、単一の`ptp4l`インスタンスがすべてのポートを管理します。BMCAは`eno8403np1`上でGMをマスターとして選択し、それが`SLAVE`に移行してPHCを調整します。`eno8503np2`と`eno8603np3`は`serverOnly 1`に強制されるため、タイムトランスミッターとしてのみ機能します。
すべてのポートが同じNIC PHCを共有しているため、受信した時刻は送信ポートですぐに利用可能です。ポートが複数構成されている場合はバウンダリクロックが自動的に暗示されるため、`clock_type`や`ts2phc`の設定は不要です。
* *OCサーバー*では、`ptp4l`が`clientOnly 1`上の`ens6f0np0`で実行されるため、ポートは常にタイムレシーバーとしてのみ機能します。`phc2sys`はシステムクロックをPHCに合わせます。
* OCサーバーにおいて、`clientOnly 1`はそれがマスターになることを決して許さないための保証となります。`localPriority`属性（G.8275.x BMCAにおいて、clockClass、clockAccuracy、variance、priority2が等しい場合のタイブレーカーとしてのみ使用され、値が小さい方が優先される）は、この順序付けを強化します。BCサーバーはデフォルトの`128`を維持し、OCサーバーは優先度の低い`250`を使用します。

BCは、GMと`eno8403np1`ポート間の*アップストリーム*セグメントと、`eno8503np2`ポートとOC間の*ダウンストリーム*セグメントという、2つの独立したPTPセグメントをブリッジします。これらは、例えばスイッチの異なるVLAN上や別々のネットワーク上で、分離された状態に保たれます。BCはダウンストリームセグメントにおける唯一のマスターであるため、OCはBCから同期し、GMから直接同期することはありません。

<<ptp-scenario-oc,シナリオ1a>>と同様に、このシナリオでは転送不可能なマルチキャストMAC`01:80:C2:00:00:0E`を使用します。標準的なブリッジはこれを転送しないため、すべてのPTP対応デバイスがPTPを終端および再生成します。タイミングパスのすべてのノードで同じアドレスを設定する必要があります。

[,console]
----

        parentPortIdentity                    000000.fffe.001101-2
        parentStats                           0
        observedParentOffsetScaledLogVariance 0xffff
        observedParentClockPhaseChangeRate    0x7fffffff
        grandmasterPriority1                  128

+
* `parentPortIdentity` (`000000.fffe.001101-2`) — *直接のマスター*：境界クロックの送信ポートであり、OCが実際に時刻を受信するクロックです。
* `grandmasterIdentity` (`d0460c.ffff.05c130`) — *タイミングツリーのルート*：グランドマスターであり、境界クロックを介して変更されずに転送されます。
+
`gm.ClockClass`、`gm.ClockAccuracy`、および`grandmasterPriority`の値は、BMCAによって使用されるグランドマスターのアドバタイズされた品質を示しています。もし2つの識別子が等しい場合、OCはパス上に境界クロックが存在せず、グランドマスターから直接同期することになります。

=== シナリオ3a - 境界クロック（PTPのみ）マルチNIC構成（内部タイミングモジュール付き、DPLL GNR-Dベース）

*説明*

{product}は、最新のIntel Granite Rapids-Dベースの設計（GNR-D）を含む、さまざまなプラットフォームで高精度なタイミングをサポートしています。これらのサーバーには通常、組み込みの高速イーサネットコントローラーと、追加ポート用のイーサネットコントローラーを備えた1つ以上の追加カード（AIC）が含まれています。以前のプラットフォーム世代とは異なり、システム全体および異なるNIC間でタイミング信号を内部的にルーティングできる専用のDPLLも装備されており、すべてのNIC PHCを同期させるための外部ケーブル接続は不要になりました。
したがって、全体的な展開は簡素化されますが、起動時のDPLLや内部信号設定など、特定の手順とソフトウェアコンポーネントが必要になります。

このシナリオは、<<ptp-scenario-bc-single-nic,シナリオ2a>>を拡張したもので、ITU-T G.8275.1（PTPのみ、レイヤー2）に完全に準拠した、複数のNIC上に構築される境界クロック（BC）を対象としています。統合コントローラーの1つのポートがグランドマスターからPTPを受信し、追加カードがダウンストリームでPTPを再生成します。シングルNICの場合とは異なり、各NICは独自のPHCを備えています。オンボードのDPLLと`ts2phc`がそれらを調整し、PHCごとに1つの`ptp4l`インスタンスが実行されます。

[IMPORTANT]
====
この {product} リリースでは、このシナリオは「デフォルト」（つまり「PREEMPT_RT」ではない）カーネルフレーバーでのみサポートされています。
「RT」カーネルフレーバーのサポートは、今後のリリースで追加される予定です。
====

.前提条件
* _Intel 800シリーズネットワークデバイス_用の最新のカーネルドライバーを、 https://www.intel.com/content/www/us/en/download/19630/intel-network-adapter-driver-for-800-series-devices-under-linux.html[IntelのWebサイト]からダウンロードしてインストールしてください。
* 「ice_RPM_Files」を含むzipファイルを選択し、アーカイブを解凍して`ice-kmp-default-*sles16sp0.x86_64.rpm`をインストールしてください。このRPMには、例えば `ice-kmp-default-2.4.5_k6.12.0_160000.5-1.sles16sp0.x86_64.rpm` が含まれています。
+
[,console]
----
# transactional-update pkg install ice-kmp-default-2.4.5_k6.12.0_160000.5-1.sles16sp0.x86_64.rpm
----
+
変更を永続的かつ有効にするために、サーバーを再起動してください。

[NOTE]
====
* 例を通してDell PowerEdge XR8720tシステムをリファレンスシステムとして使用しますが、カーネルインターフェイスとポート構成は、別のGNR-Dサーバーでは異なる場合があります。デバイス名は適宜調整してください。
* Telcoデプロイメントが想定されており、以下のセクション全体でTelcoプロファイルG.8275.1が使用されます。
====

このシナリオには、以下のコンポーネントが含まれます。

* *Grandmaster (GM)*: アップストリームセグメント上の、PTPドメイン（ドメイン `24`）のリファレンス。
* *PTP対応スイッチ*: タイミングパス上でバウンダリクロック (T-BC) として機能します。PTPを伝送するすべてのポートには`ptp enable`が設定されています。アップストリームセグメントとダウンストリームセグメントは、スイッチの異なるVLAN上で分離されています（各セグメントに専用のVLANを使用）。
* *Boundary Clock (BC server)*: GNR-Dノード。その統合コントローラーは `eno8403np1` 上のGMからPTPを受信し、統合PHC (`/dev/ptp1`) を制御します。オンボードDPLLはそのタイミングをアドインカードに分配し、`ts2phc` はそれらのPHC (`/dev/ptp2`、`/dev/ptp3`) を `/dev/ptp1` に同期させ続けます。各アドインカードはPTPをダウンストリーム側で再生成し（例えば `eno16495np0` 上で）、タイムトランスミッターとして機能します。
* *Ordinary Clock (OC server)*: ダウンストリームセグメント上のシングルポートノード (`ens6f0np0`) で、その唯一のPTPマスターはBCです。

*BC server* のタイミングは、PHCが物理的に分離されているため、連携して動作する複数の `linuxptp` デーモンによって処理されます。

* 統合コントローラー (`/dev/ptp1`) 上の `ptp4l` インスタンスが `eno8403np1` でPTPプロトコルを実行します。BMCAがGMをマスターとして選択し、ポートは`SLAVE`に移行し、`ptp4l`が`/dev/ptp1`を同期させます。
* オンボードDPLLは、統合PHCがSDPピンを介してそれを駆動し、DPLLが今度はアドインカードのクロックを駆動するように配線されています。これは、以前のプラットフォームで使用されていた外部1PPSケーブル配線の内部的な代替手段です。
* `ts2phc`は、DPLLが分配する信号から、アドインカードのPHCを`/dev/ptp1`に同期させ続けます。
* アドインカードごとの個別の`ptp4l`インスタンス（`/dev/ptp2`、`/dev/ptp3`）が、そのポート上でPTPを再生成し、すべて`serverOnly 1`（タイムトランスミッター）に強制されます。
* バウンダリクロックは、時刻に加えて、グランドマスターの補助属性（クロッククラス、精度など）を転送する必要があります。これは単一の`ptp4l`インスタンス内でのみ自動的に行われるため、統合インスタンスからアドインインスタンスへそれらの値を転送するために`pmc`が使用されます（ステップ5を参照）。`pmc`（PTP管理クライアント）は、管理ソケットを介して実行中の`ptp4l`インスタンスのランタイム状態を照会および更新する`linuxptp`ツールです。

[NOTE]
====
統合コントローラーでは、そのポートのうち*1つ*のみがPHCを管理する管理ポートです。`/sys/class/ptp/ptp1/device/net/`を調べてそれを見つけます（例: `eno8703np0`）。これはDPLL信号の設定に使用されるポートであり、必ずしもPTP（`eno8403np1`）を伝送するポートではありません。
====

[NOTE]
====
ここで説明する設定は完全に静的なものです。GMが利用できなくなった場合、ダウンストリームの同期はホストのホールドオーバー機能のみに依存します。別の時刻参照ソースへの自動切り替えは実行されません。
====

. 内部タイミング信号（DPLL）を設定します。
+
統合PHCをDPLLに接続し、前述の管理ポート（`eno8703np0`）と正しい`ptpN`インデックスを使用して、DPLLがアドインカードに信号を供給できるようにします。
+
[#gnrd-startup-setup]
.`01-gnrd-startup-setup.sh`
====
[source,bash]
----
#!/bin/bash

# The admin port that manages the PHC is under /sys/class/ptp/ptp1/device/net/ (e.g. eno8703np0).
# Only one port of the integrated E825-C NIC exposes it.

# Let the DPLL drive the Ethernet clock on the integrated controller
echo 4 1 > /sys/class/net/eno8703np0/device/tspll_cfg

# Feed the DPLL from the integrated PHC through the SDP pins:
# SDP0 -> 1 pulse per second (1PPS, 1 Hz): enable the pin, then set a 1 s period
echo 2 2 > /sys/class/ptp/ptp1/pins/SDP0
echo 2 0 0 1 0 > /sys/class/ptp/ptp1/period

# SDP2 -> 1000 pulses per second (1kPPS, 1 kHz): enable the pin, then set a 1 ms period
echo 2 1 > /sys/class/ptp/ptp1/pins/SDP2
echo 1 0 0 0 1000000 > /sys/class/ptp/ptp1/period

# Propagate the pulses from the DPLL to the add-in cards (SDP1 on each add-in PHC)
echo 1 1 > /sys/class/ptp/ptp2/pins/SDP1
echo 1 1 > /sys/class/ptp/ptp3/pins/SDP1
----
====
+
これらの設定は再起動時に失われるため、`ts2phc`および`ptp4l`の前に順序付けられたoneshot型の`systemd`ユニットから起動時にスクリプトを実行してください。
+
[source,ini]
----
# /etc/systemd/system/gnrd-ptp-dpll-setup.service
[Unit]
Description=GNR-D PTP DPLL and internal signal setup
Before=ts2phc.service ptp4l@nac.service ptp4l@aic1.service ptp4l@aic2.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/bin/01-gnrd-startup-setup.sh

[Install]
WantedBy=multi-user.target
----

. アドインカードのPHCを`ts2phc`に合わせます。
+
`ts2phc`（「PHCへのタイムスタンプ」）は、アドインカードのPHCを基準クロックに合わせます。ここでは、基準は統合NICのPHC（`/dev/ptp1`、GMによってその`ptp4l`インスタンスを通じてすでに調整済み）であり、コマンドラインで`-s /dev/ptp1`とともに渡されます。オンボードのDPLLは、その基準から導出された1PPSを各アドインカードの`SDP1`ピンに供給します。`ts2phc`はそれらの入力パルス（EXTTS）をタイムスタンプし、それに応じて各アドインPHCをステップさせるため、ノード内のすべてのPHCが最終的に同じ時間を共有することになります。
+
[NOTE]
====
アドインPHCの調整には、異なるレベルでの2つの補完的な設定が必要です。

* *ハードウェア*: オンボードのDPLLが1PPSパルスを供給できるように、各アドインPHCの`SDP1`入力ピンを有効にする必要があります。これは、前のステップ（`echo 1 1 > /sys/class/ptp/ptpN/pins/SDP1`）のDPLLセットアップスクリプトで行われます。
* *ソフトウェア*: `ts2phc`に対して、その入力をタイムスタンプし、PHCをステップさせるよう指示する必要があります。これは、以下の構成（`ts2phc.channel`、`ts2phc.pin_index`、`ts2phc.extts_polarity`）で行われます。

ピンを有効にしないとパルスはPHCに到達せず、`ts2phc`構成を行わないとパルスは適用されません。両方が必要です。
====
+
設定ファイルを作成します。
+
[#gnrd-ts2phc-config]
.`/etc/ts2phc-cf-all.cfg` — `ts2phc`設定ファイル
====
[source,]
----
[global]
use_syslog              0
verbose                 1
logging_level           7
ts2phc.pulsewidth       100000000

[eno16495np0]
ts2phc.channel          1
ts2phc.extts_polarity   rising
ts2phc.pin_index        1

[eno16595np0]
ts2phc.channel          1
ts2phc.extts_polarity   rising
ts2phc.pin_index        1
----
====
+
各アドインカードは、その最初のポート（`[eno16495np0]`、`[eno16595np0]`）にちなんで名付けられたセクションを通じて構成され、これにより調整対象のPHCが識別されます。パラメータは、DPLLパルスをそのカードにマッピングします。
+
* `ts2phc.pin_index`および`ts2phc.channel`: DPLLが1PPSを供給するピンとチャネル（このセットアップでは`SDP1`、したがって`pin_index 1`）。
* `ts2phc.extts_polarity`: タイムスタンプするパルスエッジ（`rising`）。
* `ts2phc.pulsewidth`: 期待される入力パルス幅（ナノ秒単位、ここでは100 ms）。
+
手動で`ts2phc -f /etc/ts2phc-cf-all.cfg -s /dev/ptp1 -m`を実行するか、または`systemd`に`/etc/sysconfig/ts2phc`を通じて管理させるようにしてください。
+
[source,]
----
# /etc/sysconfig/ts2phc
OPTIONS="-f /etc/ts2phc-cf-all.cfg -s /dev/ptp1 -m"
----

. PHCごとに`ptp4l`インスタンスを1つ実行してください。
+
統合コントローラーはBMCA駆動のインスタンス（レシーバー）を実行し、各アドインカードはすべてのポートが`serverOnly 1`に強制されたインスタンスを実行します。各インスタンスは、異なる制御ソケットと読み取り専用ソケットを使用する必要があります。3つの設定ファイルを作成してください：
+
[#gnrd-ptp4l-config-nac]

====
[source,]
----

[global]

uds_ro_address                  /var/run/ptp4lro-nac

[eno8403np1]
----
====
+
統合インスタンスは、GMからPTPを受信するポートである`eno8403np1`のみを宣言し、それに対して`serverOnly`や`clientOnly`を設定しません。役割の割り当てはBMCAに依存します。`eno8403np1`でGMに到達可能な場合、BMCAはそれをタイムレシーバー（`SLAVE`）として選択し、`/dev/ptp1`を制御します。統合コントローラーの他のポートは宣言されません。なぜなら、このノードではダウンストリームの再生成は統合コントローラーではなくアドインカードによって実行されるからです。対照的に、アドインカードは常にタイムトランスミッターである必要があるため、`serverOnly 1`を強制します。これらはPTPを受信して時刻を取得するのではなく、DPLLと`ts2phc`から時刻を取得するため、レシーバーとして選出されてはなりません。より厳密な制御が必要な場合は、インターフェースの下に`serverOnly`または`clientOnly`フラグを明示的に追加してください。
+
`G.8275.portDS.localPriority`および`G.8275.defaultDS.localPriority`の値（統合インスタンスでは`128`、アドインカードでは`250`）は、G.8275.x BMCAのタイブレーカーとして機能します。これらは`clockClass`、`clockAccuracy`、分散、`priority2`の後にのみ比較され、値が小さい方が優先されます。統合インスタンスでデフォルトの`128`を維持すると、アドインインスタンス（`250`）よりも優先順位が高くなります。これにより、ノード内のタイムトランスミッター/タイムレシーバーの順序が決定論的に保たれ、`ptp4l`によって報告されるポート状態に反映されるように、BMCAがどのポートを選択するかが決まります。
+

. グランドマスターのパラメータを`ptp4l`インスタンス間で転送してください。
+
境界クロックは、時刻だけでなく、グランドマスターの補助パラメータ（クロッククラス、精度、UTCオフセットなど）も転送しなければなりません。これは*同じ*`ptp4l`インスタンスのポート間で自動的に行われますが、異なるPHCを管理する個別のインスタンス間では行われません。値は、各インスタンスのUDSソケット(`SET GRANDMASTER_SETTINGS_NP`)を介して、ランタイムで`pmc`を使って適用されます。
+
[IMPORTANT]
====
`pmc`で適用された値は実行中の`ptp4l`プロセス内にのみ保持されます。これらは*書き込まれず*、`.conf`ファイルには保存されず、再起動しても保持され*ません*。`ptp4l`インスタンスが再起動されると、ファイルデフォルト値に戻るため、値を再度転送する必要があります。手動で一度実行するのではなく、転送を自動化してください（下記参照）。
====
+
統合コントローラーがGMにロックされたら、グランドマスターの値をクエリします。以下のヘルパーは、クエリするインスタンスの設定ファイルを引数として受け取ります。
+
[#gnrd-get-pmc-values]
.`get_pmc_values.sh` — `ptp4l`インスタンスからグランドマスターの値をクエリする
====
[source,bash]
----
#!/bin/bash
# Retrieve Grandmaster information via pmc for the given ptp4l config file
set -euo pipefail

echo "PARENT_DATA_SET (Grandmaster clock values):"
pmc -f "$1" -u -b 0 'GET PARENT_DATA_SET' | grep gm

echo "TIME_PROPERTIES_DATA_SET:"
pmc -f "$1" -u -b 0 'GET TIME_PROPERTIES_DATA_SET'
----
====
+
次に、それらの値をアドインインスタンスに転送します。以下のスクリプトは、統合インスタンスから値を読み取り、各アドインインスタンスに適用します。「Input variables」セクションを編集して設定ファイル名と一致させ、システムがGMに同期されたら実行してください。
+
[#gnrd-pmc-forward]
.`04-ptp-forward-GM.sh` — グランドマスターの値をアドインインスタンスに転送する
====
[source,bash]
----
#!/bin/bash

set -euo pipefail

################## Input variables ##################
VERBOSE=1

CONFIG_FILE_NAC=/etc/ptp4l-nac.conf
CONFIG_FILES_AICS=(/etc/ptp4l-aic1.conf /etc/ptp4l-aic2.conf)

#####################################################


# Check the system is synchronized to a GM
GM_PRESENT=$(pmc -f ${CONFIG_FILE_NAC} -u -b 0 'GET TIME_STATUS_NP' | awk '/gmPresent/ {print $2}')

if [ -z "$GM_PRESENT" ]; then
    echo "Failed to get GM value from ptp4l instance for NAC, exiting..."
    exit 1
elif [ "${GM_PRESENT}" != "true" ]; then
    echo "No GM present, exiting..."
    exit 1
fi

# Get the "upstream" Grandmaster values
PDS_GM_VALUES=$(pmc -f ${CONFIG_FILE_NAC} -u -b 0 'GET PARENT_DATA_SET' | awk 'BEGIN {ORS=" "} /gm./ {print $2}')
TPDS_GM_VALUES=$(pmc -f ${CONFIG_FILE_NAC} -u -b 0 'GET TIME_PROPERTIES_DATA_SET' | awk 'BEGIN {ORS=" "} NR>2 {print $2}')

if [ -z "$PDS_GM_VALUES" ]; then
    echo "No PARENT_DATA_SET values retrieved, exiting ..."
    exit 2
elif [ -z "$TPDS_GM_VALUES" ]; then
    echo "No TIME_PROPERTIES_DATA_SET values retrieved, exiting ..."
    exit 2
fi

# Unpack from PARENT_DATA_SET
read CLOCK_CLASS CLOCK_ACCURACY VARIANCE <<< $PDS_GM_VALUES

# Unpack from TIME_PROPERTIES_DATA_SET
read UTC_OFFSET LEAP_61 LEAP_59 UTC_OFFSET_VALID PTP_TIMESCALE T_TRACEABLE F_TRACEABLE T_SOURCE <<< $TPDS_GM_VALUES

if [ "$VERBOSE" -eq 1 ]; then
    echo "Read from PARENT_DATA_SET: clockClass=${CLOCK_CLASS} clockAccuracy=${CLOCK_ACCURACY} offsetScaledLogVariance=${VARIANCE}"
    echo "Read from TIME_PROPERTIES_DATA_SET: currentUtcOffset=${UTC_OFFSET} leap61=${LEAP_61} leap59=${LEAP_59}" \
         "currentUtcOffsetValid=${UTC_OFFSET_VALID} ptpTimescale=${PTP_TIMESCALE} timeTraceable=${T_TRACEABLE}" \
         "frequencyTraceable=${F_TRACEABLE} timeSource=${T_SOURCE}"
fi


# Forward these values to the "downstream" Time Receivers, updating the ptp4l instances
for FILE in "${CONFIG_FILES_AICS[@]}"; do
    if [ "$VERBOSE" -eq 1 ]; then
        echo "Updating GRANDMASTER_SETTINGS_NP (${FILE})"
    fi

    pmc -f ${FILE} -u -b 0 'SET GRANDMASTER_SETTINGS_NP
       clockClass              '${CLOCK_CLASS}'
       clockAccuracy           '${CLOCK_ACCURACY}'
       offsetScaledLogVariance '${VARIANCE}'
       currentUtcOffset        '${UTC_OFFSET}'
       leap61                  '${LEAP_61}'
       leap59                  '${LEAP_59}'
       currentUtcOffsetValid   '${UTC_OFFSET_VALID}'
       ptpTimescale            '${PTP_TIMESCALE}'
       timeTraceable           '${T_TRACEABLE}'
       frequencyTraceable      '${F_TRACEABLE}'
       timeSource              '${T_SOURCE}'' &> /dev/null

    if [ $? -ne 0 ]; then
        echo "Failed to update ptp4l instance using config file \"${FILE}\", exiting ..."
        exit 1
    fi
done
----
====
+
値は永続的ではないため、このスクリプトを`systemd`タイマーから実行し、定期的に、またインスタンスの再起動後に値が更新されるようにしてください。
+
[source,ini]
----
# /etc/systemd/system/ptp-forward-gm.service
[Unit]
Description=Forward Grandmaster parameters to the add-in ptp4l instances
Wants=ptp4l@nac.service ptp4l@aic1.service ptp4l@aic2.service
After=ptp4l@nac.service ptp4l@aic1.service ptp4l@aic2.service

[Service]
Type=oneshot
SELinuxContext=system_u:system_r:unconfined_t:s0
ExecStart=/usr/local/bin/04-ptp-forward-GM.sh
----
+
[source,ini]
----
# /etc/systemd/system/ptp-forward-gm.timer
[Unit]
Description=Refresh forwarded Grandmaster parameters

[Timer]
OnBootSec=2min
OnUnitActiveSec=5min

[Install]
WantedBy=timers.target
----
+
その効果は、BC上のアドイン`ptp4l`インスタンスにクエリを実行することで確認できます。転送前は、ノードはファイルデフォルト値をアドバタイズしますが、転送開始後は、グランドマスターの実際の値（その後、ダウンストリームのOCに伝播されます）をアドバタイズします。例えば、`gm.ClockClass`の変更点：

# ./get_pmc_values.sh /etc/ptp4l-aic1.conf     # after forwarding
        gm.ClockClass                         8
        gm.ClockAccuracy                      0xfe
        gm.OffsetScaledLogVariance            0xffff
----

[#sctp]
== SCTP - ストリーム制御伝送プロトコル
https://en.wikipedia.org/wiki/Stream_Control_Transmission_Protocol[ストリーム制御伝送プロトコル - Wikipedia]より

[quote]
____
ストリーム制御伝送プロトコル（SCTP）は、インターネットプロトコルスイートのトランスポート層におけるコンピュータネットワーク通信プロトコルです。
もともとは電気通信における信号システム7（SS7）のメッセージ転送を目的としていましたが、このプロトコルは、伝送制御プロトコル（TCP）のような輻輳制御を備えた信頼性の高い順序通りのメッセージ転送を保証しつつ、ユーザーデータグラムプロトコル（UDP）のメッセージ指向機能を提供します。
UDPやTCPとは異なり、このプロトコルはマルチホーミングと冗長パスをサポートしており、回復力と信頼性を向上させます。

SCTPは、インターネット技術標準化委員会（IETF）によってRFC 9260で標準化されています。SCTPの参照実装はFreeBSDバージョン7の一部としてリリースされ、それ以来、他のプラットフォームにも広く移植されています。
____

3GPP 4G（LTE）仕様において、SCTP（ストリーム制御伝送プロトコル）は、無線アクセスネットワーク（RAN）ドメインとの信号接続を含む、Evolved Packet Core（EPC）全体での制御プレーン信号メッセージの基盤となるレイヤー4トランスポートとして機能します。3GPP 5G仕様では、Diameter-over-SCTPベースのすべての信号インターフェースをHTTP/2に置き換えるサービスベースアーキテクチャ（SBA）の導入により、コアネットワーク内でのSCTPの必要性が排除されました。しかし、5G RANドメイン内では依然として必要とされています：

* 「分離された」gNodeBインスタンスを構成するネットワーク要素間の信号インターフェース（DUとCU-CP間のF1-Cインターフェース、およびCU-CPとCU-UP間のE1インターフェース）において。

* 信号目的でgNodeBインスタンスを接続するXn-Cインターフェースにおいて。

* 信号目的でgNodeBインスタンス（RANドメイン）とAMFインスタンス（コアネットワークドメイン）を接続するために使用されるN2（別名NG-C）参照ポイントにおいて。

次に、それを利用するSCTP対応のTelcoワークロードをホストするダウンストリームクラスターノードで、`sctp` Linux カーネルモジュール（`lksctp`）を有効にする必要があります。

* Linuxノードで`sctp`カーネルモジュールを手動でロードするには、次の手順を実行します。

[,shell]
----
$ sudo modprobe sctp
----

* ノードの起動時に毎回`sctp`カーネルモジュールを自動的にロードするには、`/etc/modules-load.d/`ディレクトリに`sctp.conf`というファイル名のファイルを作成し、その中に単に`sctp`という文字列（ https://www.freedesktop.org/software/systemd/man/latest/modules-load.d.html[systemd-modules-load.service]ユニットが起動時にロードすべきカーネルモジュールの名前）を記述します。

[,shell]
----
$ echo "sctp" > /etc/modules-load.d/sctp.conf
$ reboot
----

ノードの起動時に毎回`sctp`カーネルモジュールを確実にロードするための最も簡単で最適な方法は、ダウンストリームノードのプロビジョニングに使用されるEdge Image Builder (EIB) で構築された raw イメージにその`/etc/modules-load.d/sctp.conf`ファイルを追加することです。その方法の詳細については、xref:../quickstart/eib.adoc#adding-operating-system-files[EIB documentation]を参照してください。
