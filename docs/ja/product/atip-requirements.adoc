== Hardware (ハードウェア)

SUSE Telco Cloudのハードウェア要件は以下の通りです。

* **管理クラスタ**:管理クラスタには`SUSE Linux Micro`、`RKE2`、`SUSE Rancher Prime`、`Metal^3^`などのコンポーネントが含まれており、複数のダウンストリームクラスタを管理するために使用されます。管理するダウンストリームクラスタの数に応じて、サーバーのハードウェア要件は異なる場合があります。
  ** サーバー（`VM`または`bare-metal`）の最小要件は以下の通りです。
     *** RAM:最小8 GB（16 GB以上を推奨）
     *** CPU:最小2（4 CPU以上を推奨）

* **ダウンストリームクラスタ**:ダウンストリームクラスタは、Telcoワークロードを実行するためにデプロイされるクラスタです。`SR-IOV`、`CPU Performance Optimization`などの特定のTelco機能を有効にするには、特定の要件が必要です。
  ** SR-IOV: パススルーモードでVF（仮想機能）をCNF/VNFに接続するには、NICがSR-IOVをサポートし、BIOSでVT-d/AMD-Viが有効になっている必要があります。
  ** CPUプロセッサ:特定のTelcoワークロードを実行するには、この参照<<atip-features,テーブル>>で利用可能な機能のほとんどを有効にするために、CPUプロセッサモデルを適合させる必要があります。
  ** 仮想メディアを使用してインストールするためのファームウェア要件:

== ネットワーク

ネットワークアーキテクチャの参考として、次の図にTelco環境の一般的なネットワークアーキテクチャを示します。

image::product-atip-requirements1.png[scaledwidth=100%]

ネットワークアーキテクチャは、以下のコンポーネントに基づいています。

* **管理ネットワーク**:このネットワークは、ダウンストリームクラスターノードの管理に使用されます。これは帯域外管理に使用されます。通常、このネットワークは別の管理スイッチにも接続されますが、VLANを使用してトラフィックを分離することで、同じサービススイッチに接続することも可能です。
* **コントロールプレーンネットワーク**:このネットワークは、ダウンストリームクラスターノード間およびそれらで実行されているサービス間の通信に使用されます。このネットワークは、ノードと`DHCP`や`DNS`サーバーなどの外部サービスとの間の通信にも使用されます。接続環境によっては、スイッチ/ルーターがインターネット経由のトラフィックを処理できる場合があります。
* **その他のネットワーク**:特定の目的のために、ノードが他のネットワークに接続される場合があります。

[NOTE]
====
ダイレクトネットワークプロビジョニングワークフローを使用するには、ホストの準備とプロビジョニングを自動化できるように、管理クラスタがダウンストリームクラスタサーバーのベースボード管理コントローラー（BMC）へのネットワーク接続を備えている必要があります。
====

正確なリストは、デプロイされたオプションコンポーネントおよび選択されたデプロイメントオプション（CNIプラグインなど）によって異なります。
====

=== ダウンストリーム ノード

SUSE Telco Cloud では、任意の（ダウンストリーム）サーバーが実行中のダウンストリーム Kubernetes クラスタの一部になる（またはそれ自体がシングルノードのダウンストリーム Kubernetes クラスタを実行する）前に、 https://github.com/metal3-io/baremetal-operator/blob/main/docs/baremetalhost-states.md[BaremetalHost プロビジョニング状態] のいくつかを通過する必要があります。

* 宣言されたばかりのダウンストリームサーバーのベースボード管理コントローラー（BMC）は、帯域外ネットワーク経由でアクセス可能である必要があります。BMC は（管理クラスタ上で実行されている ironic サービスから）実行すべき初期ステップについて指示を受けます：
. BMC が提供する `virtual media` に、指定された IPA ラムディスクイメージをプルしてロードします。
. サーバーの電源を入れます。

BMCから公開されることが想定されるポートは以下の通りです（正確なハードウェアによって異なる場合があります）。

== サービス（DHCP、DNSなど）

デプロイ先の環境の種類によっては、`DHCP`、`DNS`などの外部サービスが必要になる場合があります。

* **接続環境**:この場合、ノードは（L3ルーティングプロトコルを介して）インターネットに接続され、外部サービスはお客様によって提供されます。
* **切断環境 / エアギャップ環境**:この場合、ノードはインターネットIP接続を持たず、ダイレクトネットワークプロビジョニングワークフローで必要とされるコンテンツをローカルにミラーリングするために追加のサービスが必要となります。
* **ファイルサーバ**:ファイルサーバは、ダイレクトネットワークプロビジョニングワークフロー中にダウンストリームクラスターノードにプロビジョニングされるOSイメージを保存するために使用されます。`Metal^3^` HelmチャートはOSイメージを保存するためのメディアサーバをデプロイできます。次のxref:metal3-media-server[セクション]を確認してください。ただし、既存のローカルWebサーバを使用することも可能です。

== systemdサービスの無効化

Telcoワークロードの場合、ノード上で実行されているワークロードのパフォーマンス（レイテンシ）への影響を回避するために、ノード上で実行されている一部のサービスを無効にするか、適切に設定することが重要です。

* `rebootmgr`は、システムに保留中の更新がある場合に再起動の戦略を設定できるようにするサービスです。
Telcoワークロードの場合、システムによってスケジュールされた更新によるノードの再起動を回避し、ノード上で実行されているサービスへの影響を避けるために、`rebootmgr`サービスを無効にするか、適切に設定することが非常に重要です。

[NOTE]
====
`rebootmgr`の詳細については、 https://github.com/SUSE/rebootmgr[rebootmgr GitHubリポジトリ]を参照してください。
====

使用されている戦略を確認するには、次を実行します。

[,shell]
----
cat /etc/rebootmgr.conf
[rebootmgr]
window-start=03:30
window-duration=1h30m
strategy=best-effort
lock-group=default
----

また、次を実行して無効にすることもできます。

[,shell]
----
sed -i 's/strategy=best-effort/strategy=off/g' /etc/rebootmgr.conf
----

または、`rebootmgrctl`コマンドを使用します。

[,shell]
----
rebootmgrctl strategy off
----

[NOTE]
====
`rebootmgr`戦略を設定するためのこの構成は、ダイレクトネットワークプロビジョニングワークフローを使用して自動化できます。詳細については、<<atip-automated-provisioning,自動プロビジョニングのドキュメント>>を確認してください。
====

* `transactional-update`は、システムによって制御される自動更新を可能にするサービスです。Telcoワークロードの場合、ノード上で実行されているサービスへの影響を回避するために、自動更新を無効にすることが重要です。

自動更新を無効にするには、次のコマンドを実行します。

[,shell]
----
systemctl --now disable transactional-update.timer
systemctl --now disable transactional-update-cleanup.timer
----

* `fstrim`は、毎週自動的にファイルシステムをトリムできるようにするサービスです。Telcoワークロードの場合、ノード上で実行されているサービスへの影響を回避するために、自動トリムを無効にすることが重要です。

自動トリムを無効にするには、次のコマンドを実行します。

[,shell]
----
systemctl --now disable fstrim.timer
----
