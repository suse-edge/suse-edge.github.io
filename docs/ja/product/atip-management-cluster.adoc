== 概要
管理クラスタは、ランタイムスタックのプロビジョニングとライフサイクルを管理するために使用されるSUSE Telco Cloudの一部です。
技術的な観点から、管理クラスタには以下のコンポーネントが含まれています。

* OSとしての`SUSE Linux Micro`。ユースケースに応じて、ネットワーク、ストレージ、ユーザー、カーネル引数などの一部の構成をカスタマイズできます。
* Kubernetesクラスタとしての`RKE2`。ユースケースに応じて、`Multus`、`Cilium`、`Calico`などの特定のCNIプラグインを使用するように構成できます。
* クラスタのライフサイクルを管理するための管理プラットフォームとしての`Rancher`。
* ベアメタルノードのライフサイクルを管理するためのコンポーネントとしての`Metal^3^`。
* Kubernetesクラスタ（ダウンストリームクラスタ）のライフサイクルを管理するためのコンポーネントとしての`CAPI`。`RKE2 CAPI Provider`は、RKE2クラスタのライフサイクルを管理するために使用されます。

上記のすべてのコンポーネントにより、管理クラスタは、宣言的なアプローチを使用してインフラストラクチャおよびアプリケーションを管理し、ダウンストリームクラスタのライフサイクルを管理できます。

[NOTE]
====
`SUSE Linux Micro`の詳細については、以下を参照してください。<<components-slmicro,SUSE Linux Micro>>

`RKE2`の詳細については、以下を参照してください。<<components-rke2,RKE2>>

`Rancher`の詳細については、以下を参照してください。<<components-rancher,Rancher>>

`Metal^3^`の詳細については、以下を参照してください。<<components-metal3,Metal^3^>>
====

== 管理クラスタをセットアップする手順

管理クラスタをセットアップするには（単一ノードを使用）、以下の手順が必要です。

image::product-atip-mgmtcluster1.png[scaledwidth=100%]

宣言的なアプローチを使用して管理クラスタをセットアップするための主な手順は以下のとおりです。

. **xref:mgmt-cluster-image-preparation-connected[接続環境向けのイメージ準備]**:最初のステップは、接続環境で使用するために必要なすべての構成を含むマニフェストとファイルを準備することです。

  - xref:mgmt-cluster-directory-structure[接続環境のディレクトリ構造]:このステップでは、Edge Image Builderが設定ファイルとイメージ自体を保存するために使用するディレクトリ構造を作成します。
  - xref:mgmt-cluster-image-definition-file[管理クラスター定義ファイル]:`mgmt-cluster.yaml`ファイルは、管理クラスターのメイン定義ファイルです。これには、作成されるイメージに関する以下の情報が含まれています。
        ** イメージ情報:ベースイメージを使用して作成されるイメージに関連する情報。
        ** オペレーティングシステム:イメージで使用されるオペレーティングシステムの構成。
        ** Kubernetes:Helmチャートとリポジトリ、Kubernetesバージョン、ネットワーク設定、およびクラスターで使用されるノード。
  - xref:mgmt-cluster-custom-folder[カスタムフォルダ]:`custom`フォルダには、Edge Image Builderが完全に機能する管理クラスターをデプロイするために使用する設定ファイルとスクリプトが含まれています。
        ** ファイル:管理クラスターで使用される設定ファイルが含まれています。
        ** スクリプト:管理クラスターで使用されるスクリプトが含まれています。
  - xref:mgmt-cluster-kubernetes-folder[Kubernetesフォルダ]:`kubernetes`フォルダには、管理クラスターで使用される設定ファイルが含まれています。
        ** マニフェスト:管理クラスターで使用されるマニフェストが含まれています。
        ** Helm:管理クラスターで使用するHelm値ファイルが含まれています。
        ** Config:管理クラスターで使用される設定ファイルが含まれています。
  - xref:mgmt-cluster-network-folder[ネットワークフォルダ]:`network`フォルダには、管理クラスターノードで使用するネットワーク設定ファイルが含まれています。

. **xref:mgmt-cluster-image-preparation-airgap[エアギャップ環境向けのイメージ準備]**:このステップでは、エアギャップシナリオで使用するマニフェストとファイルの準備における違いを示します。
  - xref:mgmt-cluster-image-definition-file-airgap[定義ファイルの変更]:EIB出力イメージに含めるすべてのコンテナイメージに対して`images`フィールドが設定された`embeddedArtifactRegistry`セクションを含めるように、`mgmt-cluster.yaml`ファイルを変更する必要があります。
  - xref:mgmt-cluster-custom-folder-airgap[カスタムフォルダの変更]:エアギャップ環境で管理クラスターを実行するために必要なリソースを含めるように、`custom`フォルダを変更する必要があります。
        ** 登録スクリプト:エアギャップ環境を使用する場合は、`custom/scripts/99-register.sh`スクリプトを削除する必要があります。

. **xref:mgmt-cluster-image-creation[イメージの作成]**:このステップでは、Edge Image Builderツールを使用したイメージの作成について説明します（接続環境とエアギャップ環境の両方に対応）。システムでEdge Image Builderツールを実行するための<<components-eib,前提条件>>を確認してください。

. **xref:mgmt-cluster-provision[管理クラスターのプロビジョニング]**:このステップでは、前のステップで作成したイメージを使用した管理クラスターのプロビジョニングについて説明します（接続環境とエアギャップ環境の両方に対応）。このステップは、ラップトップ、サーバー、VM、またはUSBポートを備えたその他の{x86-64}システムを使用して実行できます。

[NOTE]
====
Edge Image Builderの詳細については、<<components-eib,Edge Image Builder>>および<<quickstart-eib,Edge Image Builder クイックスタート>>を参照してください。
====

[#mgmt-cluster-image-preparation-connected]
== 接続環境向けのイメージ準備

Edge Image Builderは管理クラスター用のイメージを作成するために使用されます。本書では、管理クラスターをセットアップするために必要な最小限の設定について説明します。

Edge Image Builderはコンテナ内で実行されるため、 https://podman.io[Podman]や https://rancherdesktop.io[Rancher Desktop]などのコンテナランタイムが必要です。このガイドでは、podmanが利用可能であると想定しています。

また、高可用性管理クラスターをデプロイするための前提条件として、ネットワーク内に3つのIPを予約する必要があります。

- `apiVIP`はAPI VIPアドレス用（Kubernetes APIサーバーへのアクセスに使用）。
- `ingressVIP`はIngress VIPアドレス用（例えば、Rancher UIによって消費される）。
- `metal3VIP`はMetal3 VIPアドレス用。

`mgmt-cluster.yaml`定義ファイルのフィールドと値を説明するために、以下のセクションに分割しました。

- イメージセクション（定義ファイル）:

[,yaml,subs="attributes"]
----
image:
  imageType: iso
  arch: x86_64
  baseImage: {micro-base-image-iso}
  outputImageName: eib-mgmt-cluster-image.iso
----

`baseImage`は、SUSE Customer CenterまたはSUSEダウンロードページからダウンロードした元のイメージです。`outputImageName`は、管理クラスターのプロビジョニングに使用される新しいイメージの名前です。

- オペレーティングシステムセクション（定義ファイル）:

[,yaml]
----
operatingSystem:
  isoConfiguration:
    installDevice: /dev/sda
  users:
  - username: root
    encryptedPassword: $ROOT_PASSWORD
  packages:
    packageList:
    - jq
    sccRegistrationCode: $SCC_REGISTRATION_CODE
----

`installDevice`はオペレーティングシステムのインストールに使用するデバイス、`username`と`encryptedPassword`はシステムへのアクセスに使用する資格情報、`packageList`はインストールするパッケージのリスト（`jq`はインストールプロセス中に内部的に必要）、`sccRegistrationCode`はビルド時にパッケージと依存関係を取得するために使用される登録コードであり、SUSE Customer Centerから入手できます。
暗号化されたパスワードは、`openssl` コマンドを使用して次のように生成できます。

[,shell]
----
openssl passwd -6 MyPassword!123
----

これは次のような出力を生成します。

[,console]
----

`helm` セクションには、インストールする Helm チャートのリスト、使用するリポジトリ、およびそれらすべてのバージョン構成が含まれています。

`network` セクションには、`RKE2` コンポーネントで使用される `apiHost` や `apiVIP` などのネットワーク構成が含まれています。
`apiVIP` は、ネットワーク内で使用されていない IP アドレスである必要があり、（DHCP を使用する場合）DHCP プールの一部であってはなりません。また、マルチノードクラスターで `apiVIP` を使用する場合、これは Kubernetes API サーバーへのアクセスに使用されます。
`apiHost` は、`RKE2` コンポーネントで使用される `apiVIP` への名前解決です。

`nodes` セクションには、クラスターで使用されるノードのリストが含まれています。この例ではシングルノードクラスターが使用されていますが、リストにノードを追加する（行のコメントを解除する）ことで、マルチノードクラスターに拡張できます。

[NOTE]
====
* クラスター内のノード名は一意である必要があります。
* オプションで `initializer` フィールドを使用してブートストラップホストを指定できます。指定しない場合は、リストの最初のノードが使用されます。
* ネットワーク構成が必要な場合、ノード名は <<mgmt-cluster-network-folder, Network Folder>> で定義されたホスト名と同じである必要があります。
====

[#mgmt-cluster-custom-folder]
=== カスタムフォルダ

`custom` フォルダには、次のサブフォルダが保管されています。

[,console]
----
...
├── custom
│ ├── scripts
│ │ ├── 99-register.sh
│ │ ├── 99-mgmt-setup.sh
│ │ └── 99-alias.sh
│ └── files
│     ├── rancher.sh
│     ├── mgmt-stack-setup.service
│     ├── metal3.sh
│     └── basic-setup.sh
...
----

- `custom/files` フォルダには、管理クラスターで使用される設定ファイルが保管されています。
- `custom/scripts` フォルダには、管理クラスターで使用されるスクリプトが含まれています。


`custom/files` フォルダには、次のファイルが収められます。

* `basic-setup.sh`: `Metal^3^`、`Rancher`、および `MetalLB` の構成パラメータが含まれています。使用する名前空間を変更する場合にのみ、このファイルを変更してください。
+
[,shell]
----
#!/bin/bash
# Pre-requisites. Cluster already running
export KUBECTL="/var/lib/rancher/rke2/bin/kubectl"
export KUBECONFIG="/etc/rancher/rke2/rke2.yaml"

##################
# METAL3 DETAILS #
##################
export METAL3_CHART_TARGETNAMESPACE="metal3-system"

###########
# METALLB #
###########
export METALLBNAMESPACE="metallb-system"

###########
# RANCHER #
###########
export RANCHER_CHART_TARGETNAMESPACE="cattle-system"
export RANCHER_FINALPASSWORD="adminadminadmin"

die(){
  echo ${1} 1>&2
  exit ${2}
}
----

* `metal3.sh`: 使用する `Metal^3^` コンポーネントの構成が含まれています（変更は不要です）。将来のバージョンでは、このスクリプトは `Rancher Turtles` を使用するように置き換えられ、簡素化される予定です。
+
[,shell]
----
#!/bin/bash
set -euo pipefail

BASEDIR="$(dirname "$0")"
source ${BASEDIR}/basic-setup.sh

METAL3LOCKNAMESPACE="default"
METAL3LOCKCMNAME="metal3-lock"

trap 'catch $? $LINENO' EXIT

catch() {
  if [ "$1" != "0" ]; then
    echo "Error $1 occurred on $2"
    ${KUBECTL} delete configmap ${METAL3LOCKCMNAME} -n ${METAL3LOCKNAMESPACE}
  fi
}

# Get or create the lock to run all those steps just in a single node
# As the first node is created WAY before the others, this should be enough
# TODO: Investigate if leases is better
if [ $(${KUBECTL} get cm -n ${METAL3LOCKNAMESPACE} ${METAL3LOCKCMNAME} -o name | wc -l) -lt 1 ]; then
  ${KUBECTL} create configmap ${METAL3LOCKCMNAME} -n ${METAL3LOCKNAMESPACE} --from-literal foo=bar
else
  exit 0
fi

# Wait for metal3
while ! ${KUBECTL} wait --for condition=ready -n ${METAL3_CHART_TARGETNAMESPACE} $(${KUBECTL} get pods -n ${METAL3_CHART_TARGETNAMESPACE} -l app.kubernetes.io/name=metal3-ironic -o name) --timeout=10s; do sleep 2 ; done

# Get the ironic IP
IRONICIP=$(${KUBECTL} get cm -n ${METAL3_CHART_TARGETNAMESPACE} ironic -o jsonpath='{.data.IRONIC_IP}')

# If LoadBalancer, use metallb, else it is NodePort
if [ $(${KUBECTL} get svc -n ${METAL3_CHART_TARGETNAMESPACE} metal3-metal3-ironic -o jsonpath='{.spec.type}') == "LoadBalancer" ]; then
  # Wait for metallb
  while ! ${KUBECTL} wait --for condition=ready -n ${METALLBNAMESPACE} $(${KUBECTL} get pods -n ${METALLBNAMESPACE} -l app.kubernetes.io/component=controller -o name) --timeout=10s; do sleep 2 ; done

  # Do not create the ippool if already created
  ${KUBECTL} get ipaddresspool -n ${METALLBNAMESPACE} ironic-ip-pool -o name || cat <<-EOF | ${KUBECTL} apply -f -
  apiVersion: metallb.io/v1beta1
  kind: IPAddressPool
  metadata:

- `rancher.sh`: 使用する `Rancher` コンポーネントの構成が含まれています（変更は不要です）。
+
[,shell]
----
#!/bin/bash
set -euo pipefail

BASEDIR="$(dirname "$0")"
source ${BASEDIR}/basic-setup.sh

RANCHERLOCKNAMESPACE="default"
RANCHERLOCKCMNAME="rancher-lock"

if [ -z "${RANCHER_FINALPASSWORD}" ]; then
  # If there is no final password, then finish the setup right away
  exit 0
fi

trap 'catch $? $LINENO' EXIT

catch() {
  if [ "$1" != "0" ]; then
    echo "Error $1 occurred on $2"
    ${KUBECTL} delete configmap ${RANCHERLOCKCMNAME} -n ${RANCHERLOCKNAMESPACE}
  fi
}

# Get or create the lock to run all those steps just in a single node
# As the first node is created WAY before the others, this should be enough
# TODO: Investigate if leases is better
if [ $(${KUBECTL} get cm -n ${RANCHERLOCKNAMESPACE} ${RANCHERLOCKCMNAME} -o name | wc -l) -lt 1 ]; then
  ${KUBECTL} create configmap ${RANCHERLOCKCMNAME} -n ${RANCHERLOCKNAMESPACE} --from-literal foo=bar
else
  exit 0
fi

# Wait for rancher to be deployed
while ! ${KUBECTL} wait --for condition=ready -n ${RANCHER_CHART_TARGETNAMESPACE} $(${KUBECTL} get pods -n ${RANCHER_CHART_TARGETNAMESPACE} -l app=rancher -o name) --timeout=10s; do sleep 2 ; done
until ${KUBECTL} get ingress -n ${RANCHER_CHART_TARGETNAMESPACE} rancher > /dev/null 2>&1; do sleep 10; done

RANCHERBOOTSTRAPPASSWORD=$(${KUBECTL} get secret -n ${RANCHER_CHART_TARGETNAMESPACE} bootstrap-secret -o jsonpath='{.data.bootstrapPassword}' | base64 -d)
RANCHERHOSTNAME=$(${KUBECTL} get ingress -n ${RANCHER_CHART_TARGETNAMESPACE} rancher -o jsonpath='{.spec.rules[0].host}')

# Skip the whole process if things have been set already
if [ -z $(${KUBECTL} get settings.management.cattle.io first-login -ojsonpath='{.value}') ]; then
  # Add the protocol
  RANCHERHOSTNAME="https://${RANCHERHOSTNAME}"
  TOKEN=""
  while [ -z "${TOKEN}" ]; do
    # Get token
    sleep 2
    TOKEN=$(curl -sk -X POST ${RANCHERHOSTNAME}/v3-public/localProviders/local?action=login -H 'content-type: application/json' -d "{\"username\":\"admin\",\"password\":\"${RANCHERBOOTSTRAPPASSWORD}\"}" | jq -r .token)
  done

  # Set password
  curl -sk ${RANCHERHOSTNAME}/v3/users?action=changepassword -H 'content-type: application/json' -H "Authorization: Bearer $TOKEN" -d "{\"currentPassword\":\"${RANCHERBOOTSTRAPPASSWORD}\",\"newPassword\":\"${RANCHER_FINALPASSWORD}\"}"

  # Create a temporary API token (ttl=60 minutes)
  APITOKEN=$(curl -sk ${RANCHERHOSTNAME}/v3/token -H 'content-type: application/json' -H "Authorization: Bearer ${TOKEN}" -d '{"type":"token","description":"automation","ttl":3600000}' | jq -r .token)

  curl -sk ${RANCHERHOSTNAME}/v3/settings/server-url -H 'content-type: application/json' -H "Authorization: Bearer ${APITOKEN}" -X PUT -d "{\"name\":\"server-url\",\"value\":\"${RANCHERHOSTNAME}\"}"
  curl -sk ${RANCHERHOSTNAME}/v3/settings/telemetry-opt -X PUT -H 'content-type: application/json' -H 'accept: application/json' -H "Authorization: Bearer ${APITOKEN}" -d '{"value":"out"}'
fi

# Clean up the lock cm
${KUBECTL} delete configmap ${RANCHERLOCKCMNAME} -n ${RANCHERLOCKNAMESPACE}
----

RKE2/K3s に統合されている `Traefik` イングレスプロバイダーは、`{product} {version}` リリースでサポートされている唯一のイングレスコントローラーです。複雑なイングレス移行シナリオをサポートするために、`{product}` 管理クラスターやダウンストリームクラスターがバージョン `{version}` にアップグレードされた後、かつその移行を実行するために必要な期間に限り、`Ingress-NGINX` を `Traefik` と並行して一時的に実行することは可能です。`Traefik` は RKE2 のデフォルトのイングレスコントローラーではないため（RKE2 v1.36 以降でデフォルトになります）、RKE2 サーバー設定ファイルから明示的に「要求」する必要があります。その結果、`{product} {version}` 管理クラスターのノードをプロビジョニングするために生成されるすべての EIB 自己インストール ISO イメージに `kubernetes/config/server.yaml` 設定ファイルを含める必要があります。

RKE2 https://docs.rke2.io/reference/ingress_migration[Ingress NGINX から Traefik への移行] ガイドには、`Traefik` イングレスコントローラーが廃止された `Ingress-NGINX` に取って代わった後に利用可能なイングレス移行パスの詳細が記載されています。

メディアサーバーは、Metal^3^に含まれるオプション機能です（デフォルトでは無効になっています）。Metal3機能を使用するには、前のマニフェストで設定する必要があります。

[,yaml]
----
metal3-media:

外部メディアサーバーを使用してイメージを保存できます。TLSで使用する場合は、Metal^3^用の信頼されたCAバンドルを提供する必要があります。

*CAバンドルの準備：*

まず、Metal^3^が必要とするすべての証明書を含むCAバンドルファイルを準備してください。これには、外部メディアサーバーのCA証明書が含まれます。
+
*オプション - システムCAバンドル：*Metal^3^がパブリックCAも信頼する必要がある場合（外部のHTTPSリソースにアクセスする場合など）、システムCAバンドルを含めることができます。コンテナイメージから抽出して、カスタム証明書と連結してください：
+
[,shell]
----
# Extract system CAs from a container image
podman run --rm registry.suse.com/bci/bci-base:latest cat /etc/ssl/certs/ca-certificates.crt > system-cas.pem

# Concatenate system CAs with your custom CA
cat system-cas.pem your-custom-ca.crt > ca-bundle.pem
----
+
または、カスタムCAのみが必要な場合は、次のとおりです。
+
[,shell]
----
cp your-custom-ca.crt ca-bundle.pem
----
+
[IMPORTANT]
====
システムCAバンドルを含める場合は、それを最新の状態に保つ責任が生じます。コンテナイメージ内のシステムCAは、証明書の期限切れや失効に伴い、古くなる可能性があります。更新されたコンテナイメージから再抽出して、バンドルを定期的に更新してください。
====

*ConfigMapを作成します：*

ConfigMapを作成するには、次の2つの方法があります。

. *マニフェストファイルを使用する（EIBで推奨）：*`kubernetes/manifests/metal3-cacert-configmap.yaml`ファイルを作成し、CAバンドルの内容をインラインで含めます。証明書の各行を4つのスペースで適切にインデントする必要があります。
+
[,yaml]
----
apiVersion: v1

  name: metal3-system
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: tls-ca-bundle
  namespace: metal3-system
data:
  ca-bundle.pem: |
    -----BEGIN CERTIFICATE-----
    MIIDXTCCAkWgAwIBAgIJAKJ... (your certificate content here)
    ...
    -----END CERTIFICATE-----
    -----BEGIN CERTIFICATE-----
    MIIEkjCCA3qgAwIBAgIQCgF... (additional certificates if any)
    ...
    -----END CERTIFICATE-----
----
+
このファイルを`ca-bundle.pem`から自動的に入力するには、次を使用できます。
+
[,shell]
----
cat > kubernetes/manifests/metal3-cacert-configmap.yaml <<EOF

  name: metal3-system
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: tls-ca-bundle

----

. *kubectlを直接使用する（手動デプロイ用）：*EIBを使用しておらず、クラスタ上で直接ConfigMapを作成したい場合は、次のとおりです。

----

- `metal3.yaml`ファイルの`global.trustedCAs`値を設定して、ConfigMap名を参照します。

=== Networkingフォルダ

`network`フォルダには、管理クラスター内のノード数と同じ数のファイルが含まれています。今回のケースではノードが1つしかないため、`mgmt-cluster-node1.yaml`というファイルが1つだけ存在します。
ファイル名は、前述のnetwork/nodeセクションで定義された`mgmt-cluster.yaml`定義ファイルのホスト名と一致している必要があります。

ネットワーク構成をカスタマイズする必要がある場合（例：特定の静的IPアドレスを使用するDHCPなしのシナリオ）、`network`フォルダ下の`mgmt-cluster-node1.yaml`ファイルを使用できます。この章は次の項目で構成されています。

* `$\{MGMT_GATEWAY\}`:ゲートウェイのIPアドレス。
* `$\{MGMT_DNS\}`:DNSサーバのIPアドレス。
* `$\{MGMT_MAC\}`:ネットワークインタフェースのMACアドレス。
* `$\{MGMT_NODE_IP\}`:管理クラスターのIPアドレス。

[,yaml]
----
routes:
  config:
  - destination: 0.0.0.0/0
    metric: 100
    next-hop-address: ${MGMT_GATEWAY}
    next-hop-interface: eth0
    table-id: 254
dns-resolver:
  config:
    server:
    - ${MGMT_DNS}
    - 8.8.8.8
interfaces:
- name: eth0
  type: ethernet
  state: up
  mac-address: ${MGMT_MAC}
  ipv4:
    address:
    - ip: ${MGMT_NODE_IP}
      prefix-length: 24
    dhcp: false
    enabled: true
  ipv6:
    enabled: false

----

DHCPを使用してIPアドレスを取得する場合は、次の構成を使用できます（`MAC`アドレスは`$\{MGMT_MAC\}`変数を使用して適切に設定する必要があります）。

[,yaml]
----

## This is an example of a dhcp network configuration for a management cluster
interfaces:

.. *オプション 1:内部DNSを使用する*（推奨）:内部DNSサーバーを構成してRancherホスト名を解決し、それに応じてファイルを更新します。

[,yaml,subs="attributes"]
----
hostname: rancher.yourdomain.internal

.. *オプション 2:/etc/hosts インジェクションを使用する*:内部DNSサーバーがない場合は、EIBを介して静的な`/etc/hosts`エントリを注入できます。EIBディレクトリ構造内の`eib/os-files/etc/hosts`に、以下のような内容のファイルを作成します。
+
[,shell,subs="attributes"]
----

$\{INGRESS_VIP} rancher-$\{INGRESS_VIP}.sslip.io
----
+
次に、`rancher.yaml`ファイルを更新してこのホスト名を使用するようにします。

  cattle:
    systemDefaultRegistry: "registry.rancher.com"

+
[,yaml,subs="attributes"]
----

  tls:
    certSource: secret
    enabled: true

      secretName: suse-registry-tls

- `kubernetes/manifests/suse-private-registry-creds.yaml`は、以下の内容で作成する必要があります。

[,yaml,subs="attributes"]
----
apiVersion: v1
kind: Secret
metadata:
  name: suse-registry
  namespace: suse-private-registry
type: kubernetes.io/dockerconfigjson
data:
  .dockerconfigjson: $\{DOCKER_CONFIG_JSON_BASE64\}
---
apiVersion: v1
kind: Secret
metadata:
    name: suse-registry-tls
    namespace: suse-private-registry
type: kubernetes.io/tls
data:
    tls.crt: $\{TLS_CRT_BASE64\}
    tls.key: $\{TLS_KEY_BASE64\}
----

`$\{DOCKER_CONFIG_JSON_BASE64\}`、`$\{TLS_CRT_BASE64\}`、および`$\{TLS_KEY_BASE64\}`を変更する必要があります。docker config json (base64) を正しく構成するには、以下を実行します。

[,shell,subs="attributes"]
----
# $\{DOCKER_CONFIG_JSON_BASE64\} CONTENT
echo -n '{"auths":{"&lt;MGMT_CLUSTER_REGISTRY_IP&gt;":{"username":"&lt;USERNAME&gt;","password":"&lt;PASSWORD&gt;","auth":"&lt;AUTH&gt;"}}}' | base64 -w 0
----

ここで、IPは以前に構成した`$\{MGMT_CLUSTER_REGISTRY_IP\}`と同じであり、`&lt;USERNAME&gt;`および`&lt;PASSWORD&gt;`の値は https://documentation.suse.com/cloudnative/suse-private-registry/html/private-registry/pr-deployment.html#pr-deployment-kube-secrets[SUSE Private Registry公式ドキュメント]から取得できます。`auth`フィールドに設定される`&lt;AUTH&gt;`値は、`&lt;USERNAME&gt;:&lt;PASSWORD&gt;`連結のbase64エンコーディングです。


上記の `suse-registry-tls` Secret マニフェスト内の `tls.crt` フィールドと `tls.key` フィールドの内容を設定するには、以下のコマンドを実行して、独自の TLS 自己署名証明書と関連する秘密鍵を生成します。

[,shell,subs="attributes"]
----
# Generate a self-signed certificate and key
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -sha256 -days 365 -nodes

# Convert them to base64 for the suse-private-registry-creds.yaml file
cat cert.pem | base64 -w 0
cat key.pem | base64 -w 0
----

[#mgmt-cluster-dualstack]
== デュアルスタックに関する考慮事項と構成

前のセクションで示した例は、シングルスタック IPv4 管理クラスターをセットアップする方法に関するガイダンスと例を提供しています。このような管理クラスターは、ダウンストリームクラスターの動作状態とは独立しており、ダウンストリームクラスターはデプロイ後に IPv4/IPv6 シングルスタックまたはデュアルスタック構成のいずれかで動作するように個別に構成できます。ただし、管理クラスターの構成方法は、プロビジョニングフェーズで使用できる通信プロトコルに直接影響します。インバンド通信とアウト・オブ・バンド通信の両方が、管理クラスターとダウンストリームホストがサポートするプロトコルに従って行われる必要があるためです。BMC やダウンストリームの一部またはすべてで IPv6 を使用することが想定される場合は、管理クラスターのデュアルスタック設定が必要になります。

[NOTE]
====
シングルスタック IPv6 管理クラスターは、現時点ではサポートされていません。
====

デュアルスタック機能を実現するには、Kubernetes に POD およびサービス用の IPv4 CIDR と IPv6 CIDR の両方を提供する必要があります。ただし、EIB を使用して管理クラスターイメージをビルドする前に、他のコンポーネントも特定の調整を行う必要があります。Metal^3^ プロビジョニングサービス (Ironic) は、インフラストラクチャや要件に応じて、さまざまな方法で構成できます。

- Ironic サービスは、単一の IP アドレスではなく、システム上のすべてのインターフェースでリスン(する)ように構成できます。したがって、管理クラスターホストが関連するインターフェースに IPv4 アドレスと IPv6 アドレスの両方を割り当てられている限り、プロビジョニング中にそれらのいずれかを使用できる可能性があります。現時点では、URL 生成（他のサービス、例えば Baremetal Operator や BMC などによる消費用）にはこれらのアドレスのうち 1 つしか選択できないことに注意してください。その結果、BMC との IPv6 通信を有効にするには、IPv6 アドレスを含む BMH 定義を扱う際に、IPv6 URL を公開して渡すように Baremetal Operator に指示することができます。言い換えれば、BMC が IPv6 対応であると識別された場合、プロビジョニングは IPv6 経由でのみ実行され、それ以外の場合は IPv4 経由で実行されます。

- IPv4 と IPv6 の両方に解決される単一のホスト名を Metal^3^ で使用することで、Ironic がバインディングと URL 作成にそれらのアドレスを使用できるようにすることができます。このアプローチにより、構成が容易になり、柔軟な動作が可能になります（各プロビジョニングステップで IPv4 と IPv6 の両方が有効なままになります）が、既存の DNS サーバー、IP 割り当て、およびレコードがすでに配置されているインフラストラクチャが必要になります。

いずれの場合も、Kubernetes は IPv4 と IPv6 の両方に使用する CIDR を認識する必要があるため、EIB ディレクトリ内の`kubernetes/config/server.yaml`に以下の行を追加します。その際、IPv4 を先に記述するようにしてください。

[,yaml]
----
service-cidr: 10.96.0.0/12,fd12:4567:789c::/112
cluster-cidr: 193.168.0.0/18,fd12:4567:789b::/48
----

一部のコンテナはホストネットワークを利用するため、`network`ディレクトリ配下のホストのネットワーク設定を変更し、IPv6接続を有効にします。

[,yaml]
----
routes:
  config:
  - destination: 0.0.0.0/0
    next-hop-address: ${MGMT_GATEWAY_V4}
    next-hop-interface: eth0
  - destination: ::/0
    next-hop-address: ${MGMT_GATEWAY_V6}
    next-hop-interface: eth0 
dns-resolver:
  config:
    server:
    - ${MGMT_DNS}
    - 8.8.8.8
    - 2001:4860:4860::8888
interfaces:
- name: eth0
  type: ethernet
  state: up
  mac-address: ${MGMT_MAC}
  ipv4:
    address:
    - ip: ${MGMT_CLUSTER_IP_V4}
      prefix-length: 24
    dhcp: false
    enabled: true
  ipv6:
    address:
    - ip: ${MGMT_CLUSTER_IP_V6}
      prefix-length: 128
    dhcp: false
    autoconf: false
    enabled: true
----

プレースホルダーを、ゲートウェイのIPアドレス、追加のDNSサーバー（必要な場合）、ネットワークインタフェースのMACアドレス、および管理クラスターのIPアドレスに置き換えてください。アドレスの自動設定を使用する場合は、以下の抜粋を参照し、`$\{MGMT_MAC\}`変数を設定してください。

[,yaml]
----
interfaces:
- name: eth0
  type: ethernet
  state: up
  mac-address: ${MGMT_MAC}
  ipv4:
    enabled: true
    dhcp: true
  ipv6:
    enabled: false
    dhcp: true
    autoconf: true
----

次に、最初のオプションから始めて、シングルノード構成の残りのファイルを定義します。`kubernetes/helm/values/metal3.yaml`を以下のように作成してください。

[,yaml]
----
global:
  ironicIP: ${MGMT_CLUSTER_IP_V4}
  enable_vmedia_tls: false
  # trustedCAs: tls-ca-bundle  # Optional: Uncomment and set to ConfigMap name for trusted CA bundle
metal3-ironic:
  global:
    predictableNicNames: true
  listenOnAll: true
  persistence:
    ironic:
      size: "5Gi"
  service:
    type: NodePort
metal3-baremetal-operator:
  baremetaloperator:
    externalHttpIPv6: ${MGMT_CLUSTER_IP_V6}
----

さらに、`kubernetes/helm/values/rancher.yaml`を以下のように作成します。

[,yaml]
----
hostname: rancher-${MGMT_CLUSTER_IP_V4}.sslip.io
bootstrapPassword: "foobar"
replicas: 1
global:
  cattle:
    systemDefaultRegistry: "registry.rancher.com"
----

ここで、`$\{MGMT_CLUSTER_IP_V4\}`と`$\{MGMT_CLUSTER_IP_V6\}`は、以前にホストに割り当てられたIPアドレスです。

あるいは、IPアドレスの代わりにホスト名を使用する場合は、`kubernetes/helm/values/metal3.yaml`を以下のように変更します。

[,yaml]
----
global:
  provisioningHostname: `${MGMT_CLUSTER_HOSTNAME}`
  enable_vmedia_tls: false
  # trustedCAs: tls-ca-bundle  # Optional: Uncomment and set to ConfigMap name for trusted CA bundle
metal3-ironic:
  global:
    predictableNicNames: true
  persistence:
    ironic:
      size: "5Gi"
  service:
    type: NodePort
----

さらに、`kubernetes/helm/values/rancher.yaml`を以下のように変更します。

[,yaml]
----
hostname: rancher-${MGMT_CLUSTER_HOSTNAME}.sslip.io
bootstrapPassword: "foobar"
replicas: 1
global:
  cattle:
    systemDefaultRegistry: "registry.rancher.com"
----

ここで、`$\{MGMT_CLUSTER_HOSTNAME\}`にはホストのIPアドレスに解決される完全修飾ドメイン名を指定する必要があります。
