== Ironic

=== 予測可能なネットワーク名

xref:../components/metal3.adoc#known-issues-metal3[既知の問題]により、ターゲットOSのネットワークデバイスに対して予測可能な名前を設定しようとしてエラーが発生し、検出されたデバイス名が異なる命名パターンになっている場合は、いくつかの選択肢があります。

_オプション1:_検査/プロビジョニングフェーズ用と、デプロイされたOS用の2つのネットワーク設定シークレットを使用します。

ネットワーク設定を含む2つの異なるシークレットを作成することをお勧めします。1つは、IPAが検出したデバイス名を使用して`preprovisioningNetworkDataName`定義の`BareMetalHost`として使用するもの、もう1つは、SL Microが検出したデバイス名を使用して`networkData.name`定義の`BareMetalHost`として使用するシークレットです。

*_IPA用とターゲットOS用の2つのシークレットを作成する例_*

* ターゲットOS（SL Micro）シークレット:

----
apiVersion: v1
kind: Secret                                                                                                                                                               metadata:
  name: controlplane-0-networkdata-os
type: Opaque
stringData:
  networkData: |
    interfaces:
    - name: enp1s0
      type: ethernet
      state: up
      mac-address: "00:f3:65:8a:a3:b0"
      ipv4:
        address:
        - ip:  192.168.125.200
          prefix-length: 24
        enabled: true
        dhcp: false                                                                                                                                     dns-resolver:
      config:
        server:
        - 192.168.125.1
    routes:
      config:
      - destination: 0.0.0.0/0
        next-hop-address: 192.168.125.1
        next-hop-interface: enp1s0
----

* ironic（IPA）シークレット:

----
apiVersion: v1
kind: Secret
metadata:
  name: controlplane-0-networkdata-ipa
type: Opaque
stringData:
  networkData: |
    interfaces:
    - name: enp1s0np0
      type: ethernet
      state: up
      mac-address: "00:f3:65:8a:a3:b0"
      ipv4:
        address:
        - ip:  192.168.125.200
          prefix-length: 24
        enabled: true
        dhcp: false
    dns-resolver:
      config:
        server:
        - 192.168.125.1
    routes:
      config:
      - destination: 0.0.0.0/0
        next-hop-address: 192.168.125.1
        next-hop-interface: enp1s0np0
----

* ベアメタルホストに適用:

----
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: controlplane-0
  labels:
    cluster-role: control-plane
spec:
  preprovisioningNetworkDataName: controlplane-0-networkdata-ipa
  networkData:
    name: controlplane-0-networkdata-os
...

----

_オプション2:_あるいは、識別子としてUUIDを使用することもできます。

必要なUUIDを取得する方法:

1. OpenSUSEまたはSLESマシンにnmcをインストールします:
`zypper in nm-configurator`

2. 次に、以下を直接実行します:
`nmc generate --config-dir /path/to/your/config --output-dir /where/you/want/it`
これで、出力ファイルに設定で使用できるUUIDが含まれているはずです。

3. あるいは、OpenSUSEまたはSLESを使用していない場合は、Edge Image Builderコンテナイメージを介してnmcを使用できます:
`podman run -it --rm -v $(pwd):/path/to/your/config:Z --entrypoint=/usr/bin/nmc registry.suse.com/edge/{version-edge-registry}/edge-image-builder:{version-eib} generate --confi
g-dir /path/to/your/config --output-dir /where/you/want/it`

== `BareMetalHost`の選択とクラスターの関連付け

Metalˆ3ˆクラスターオブジェクトとその対応する関連オブジェクトが作成されると、どの`BareMetalHost`をクラスターの一部にするかを選択するプロセスが実行されます。
このプロセスは、標準の https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/[Kubernetesラベル]およびセレクターを使用して、`BareMetalHost`と特定の`Metal3MachineTemplate`を接続します。

例として、各`BareMetalHost`には、そのプロパティと対象のクラスターを識別するためのラベルが付けられます（例：クラスターロール、クラスター名、場所など）。

----
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: mynode1
  labels:
    cluster-role: control-plane
    cluster: foobar
    location: madrid
    datacenter: xyz
<snip>
---
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: mynode2
  labels:
    cluster-role: worker
    cluster: foobar
    location: madrid
    datacenter: xyz
<snip>
---
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: mynode3
  labels:
    cluster-role: worker
    cluster: foobar2
    location: madrid
    datacenter: xyz
<snip>
...
----

次に、Metal3MachineTemplateオブジェクトは https://doc.crds.dev/github.com/metal3-io/cluster-api-provider-metal3/infrastructure.cluster.x-k8s.io/Metal3MachineTemplate/{version-capi-provider-metal3}#spec-template-spec-hostSelector[`spec.hostSelector`]フィールドを使用して、目的のBareMetalHostと照合します。

https://doc.crds.dev/github.com/metal3-io/cluster-api-provider-metal3/infrastructure.cluster.x-k8s.io/Metal3MachineTemplate/{version-capi-provider-metal3}#spec-template-spec-hostSelector-matchLabels[`matchLabels`]（完全なキーと値の一致用）と https://doc.crds.dev/github.com/metal3-io/cluster-api-provider-metal3/infrastructure.cluster.x-k8s.io/Metal3MachineTemplate/{version-capi-provider-metal3}#spec-template-spec-hostSelector-matchExpressions[`matchExpressions`]（より複雑なルール用）の両方を使用できます。

----
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: Metal3MachineTemplate
metadata:
  name: foobar-cluster-controlplane
  namespace: mynamespace
spec:
  template:
    spec:
      hostSelector:
        matchLabels:
          cluster-role: control-plane
          cluster: foobar
<snip>
---
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: Metal3MachineTemplate
metadata:
  name: foobar-cluster-worker
  namespace: mynamespace
spec:
  template:
    spec:
      hostSelector:
        matchExpressions:
          - { key: cluster-role, operator: In, values: [worker] }
          - { key: cluster, operator: In, values: [foobar] }
<snip>
----

[NOTE]
====
Kubernetesネームスペースを使用して、さまざまなオブジェクトをより適切に整理することもできます。
====

== 古いEFIブートエントリーのクリーンアップ

https://en.wikipedia.org/wiki/UEFI#UEFI_booting[UEFIブートマネージャー]には、おそらくもう不要な古いオペレーティングシステムの項目が複数含まれていることがあります（特に、ホストが何度も再プロビジョニングされる場合に顕著です）。
以下のいずれかの手順に従って、それらの古い項目をクリーンアップできます。

* BIOS/EFIセットアップインターフェース上で直接削除します（正確な手順はハードウェアによって異なります）。
* UEFI https://uefi.org/sites/default/files/resources/UEFI_Shell_2_2.pdf[`bcfg`]シェルを次のように実行します。
+
----
# List the entries
bcfg boot dump -b
# Delete entry number X
bcfg boot rm X
# X is the number associated the entry to remove. For example, if the entry is "Boot0002 foobar", then X is 2.
----

* Linuxシステム上で`efibootmgr`を次のように使用します。
+
----
# List the entries
efibootmgr -v
# Delete entry number X
efibootmgr -b X -B 
----

このプロセスにより、EFIシステムパーティション（ESP）に孤立したファイルが残る場合があります。これらは通常、ベンダー名（例: `EFI/opensuse`や`EFI/Microsoft`）のサブディレクトリにあります。
これらのファイルは一般的に無害ですが、過剰な容量を消費している場合は、新しいOSのインストールやブートマネージャーの更新を妨げる可能性があるため、削除する必要があります。
削除するには、ESPを明示的にマウントする必要がある場合があります。通常、Linuxシステムでは`/boot/efi/EFI`としてマウントされます。
