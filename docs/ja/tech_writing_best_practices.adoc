より良い技術ドキュメントを作成するための5つの基本ルール

== #1 視点を変える

____
仕組みを説明するのではなく...使い方を説明してください！
____

* 常に読者の立場に立って考えてください。
** 読者にどの程度の知識レベルを求めていますか？
** 読者は何を達成したいのでしょうか？
** 読者はどのような疑問を抱くでしょうか？
** どのような問題が発生する可能性がありますか？
* 読者が以下のような状況にあることを考慮してください。
** 時間が限られている
** フラストレーションを感じている
** プレッシャーを感じている
** 騒がしい環境で作業している
** 母国語が異なる


[IMPORTANT]
====
読者の80%以上は（Google）検索経由で訪れており、おそらく書籍のランダムな章にたどり着いています。
各章の冒頭で、必要な背景情報と要件を必ずすべて提供するようにしてください。
====




== #2 シンプルかつ簡潔に（KISS）

短くシンプルな説明は理解しやすく、エラーも起こりにくくなります。
これは読者だけでなく、ローカライズにとっても重要です。

簡潔で明確な言葉遣い::
+
* -> *使用する*
* -> *示す*、*伝える*、*言う*
* 前提となる-> *要件*
+
つなぎ言葉を使用しない::
+
* -> *～するために*
* -> *既存の*
* -> *新しい*
* -> *実行する*
* -> *実行してください*
+
現在形を使用する::
+
* xxxを実行します。yyyダイアログが表示されます。-> *Run xxx.yyyダイアログが表示されます。*
+
1つの文には1つのアイデアのみを含める::
+
YaST（X Window UIとncursesの2種類があります）を使用して、システムの構成と管理を行い、新しいソフトウェアやセキュリティ更新、パッチをインストールします。
+
->
+
*YaSTを使用して、システムの構成と管理を行います。*
*また、新しいソフトウェアのインストールやシステムの最新状態の維持にも使用します。*
*YaSTには、X Window環境で使用するUIが付属しています。*
*ターミナルで使用する場合は、ncursesインターフェースが利用可能です。*
+
代替案の説明を制限する::
+
通常、物事を行う方法は複数あります。
ドキュメントは、推奨されサポートされている_1つ_の方法に限定してください。
UIやコマンドラインなど、どうしても必要な場合にのみ代替案を文書化してください。

== #3 情報を構造化する

* ドキュメントを漏斗（じょうご）のように考えてください。一般的な情報から始めて、進むにつれてより具体的にしていきます。
* 情報を重要な場所に配置する
** 目的とコンテキストを最初に記述します。
** 要件は2番目に記述します。
** 手順は最後に記述します。
** 警告や注記は、関連する場所に配置する必要があります。
** 上記はドキュメントのすべてのセクションにも適用されます。
* 一連の手順（プロシージャ）を説明する場合は、常に番号付きリストを使用してください。
** 1つの手順につき10ステップ以内（7±2が理想的）にしてください。短くするために別のタスクに分割します。
** 目的、手順、結果
* プログラムリスト内に情報を配置しないでください。
** ...翻訳されないためです。
* レベル3（`==== Level 3 headline`）より小さい見出しは使用しないでください。
* 80文字を超えるコマンドは、複数行に分割してください。

== #4 一貫性を保つ

繰り返しは _悪く_ ありません::
+
. コマンド XXX を実行します -> *コマンド XXX を実行します*
. コマンド YYY を実行します -> *コマンド YYY を実行します*
. コマンド ZZZ を実行します -> *コマンド ZZZ を実行します*
+
一貫した用語を使用する::
+
* シンボリックリンク、リンク、ソフトリンク、symlink -> *シンボリックリンク*
* 更新する vs アップグレードする
* アドオン、アドオン、アドオン -> *アドオン*

== #5 中断を避ける

一つの考え方::
+
ただし、それらはインストール済みとしてマークされていません。-> *ただし、それらはインストール済みとしてマークされていません。*
+
動詞を分割しない::
+
サーバーをシャットダウンします。-> *サーバーをシャットダウンします。*
