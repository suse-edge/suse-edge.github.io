== Introdução

O provisionamento de clusters Kubernetes é uma tarefa complexa que exige profundo conhecimento na configuração de componentes de cluster. À medida que as configurações se tornam mais complexas, ou à medida que as demandas de diferentes provedores introduzem inúmeras definições de recursos específicas do provedor, a criação de clusters pode parecer assustadora.
Felizmente, a Kubernetes Cluster API (CAPI) oferece uma abordagem declarativa mais elegante, que é ainda mais aprimorada pelo ClusterClass.
Esse recurso introduz um modelo orientado a templates, permitindo que você defina uma classe de cluster reutilizável que encapsula a complexidade e promove a consistência.

== O que é ClusterClass?

O projeto CAPI introduziu o recurso ClusterClass como uma mudança de paradigma no gerenciamento do ciclo de vida de clusters Kubernetes por meio da adoção de uma metodologia baseada em templates para a instanciação de clusters. Em vez de definir recursos independentemente para cada cluster, os usuários definem uma ClusterClass, que serve como um projeto abrangente e reutilizável. Essa representação abstrata encapsula o estado desejado e a configuração de um cluster Kubernetes, permitindo a criação rápida e consistente de múltiplos clusters que aderem às especificações definidas.
Essa abstração reduz a carga de configuração, resultando em manifestos de implantação mais gerenciáveis.  Isso significa que os componentes principais de um cluster de carga de trabalho são definidos no nível da classe, permitindo que os usuários usem esses modelos como tipos de cluster Kubernetes que podem ser reutilizados uma ou várias vezes para o provisionamento de clusters.
A implementação do ClusterClass gera várias vantagens importantes que abordam os desafios inerentes ao gerenciamento tradicional do CAPI em escala:

* Redução substancial na complexidade e na verbosidade do YAML
* Processos de manutenção e atualização otimizados
* Consistência e padronização aprimoradas em todas as implantações
* Escalabilidade e recursos de automação aprimorados
* Gerenciamento declarativo e controle de versão robusto

== Exemplo de arquivo de provisionamento CAPI atual

A implantação de um cluster Kubernetes, aproveitando a Cluster API (CAPI) com os provedores CAPRKE2 (plano de controle e inicialização) e CAPM3 (infraestrutura), exige que você defina vários recursos personalizados.
Esses recursos definem o estado desejado do cluster e sua infraestrutura subjacente, permitindo que o CAPI orquestre o ciclo de vida de provisionamento e gerenciamento.
O trecho de código abaixo ilustra os tipos de recursos que devem ser configurados para instanciar um cluster Kubernetes apenas com nós do plano de controle:

* **Cluster**: Este recurso encapsula configurações de alto nível, incluindo a topologia de rede que regerá a comunicação entre nós e a descoberta de serviços. Além disso, ele estabelece vínculos essenciais com a especificação do plano de controle e o recurso de provedor de infraestrutura designado, informando assim ao CAPI sobre a arquitetura de cluster desejada e a infraestrutura subjacente na qual ele será provisionado.
* **Metal3Cluster**: Este recurso define atributos de nível de infraestrutura exclusivos do Metal3, por exemplo, o endpoint externo através do qual o servidor de API do Kubernetes será acessível.
* **RKE2ControlPlane**: O recurso RKE2ControlPlane define as características e o comportamento dos nós do plano de controle do cluster. Dentro desta especificação, parâmetros como o número desejado de réplicas do plano de controle (crucial para garantir alta disponibilidade e tolerância a falhas), a versão específica da distribuição Kubernetes (alinhada com a versão do RKE2 escolhida) e a estratégia para implementar atualizações nos componentes do plano de controle são configurados. Além disso, este recurso determina a Interface de Rede de Contêiner (CNI) a ser empregada no cluster e facilita a injeção de configurações específicas do agente, frequentemente utilizando o Ignition para o provisionamento fluido e automatizado dos agentes RKE2 nos nós do plano de controle.
* **Metal3MachineTemplate**: Este recurso serve como um modelo para a criação das instâncias de computação individuais que formam os nós do plano de controle do cluster.
* **Metal3DataTemplate**: Complementando o Metal3MachineTemplate, o recurso Metal3DataTemplate permite que metadados adicionais sejam especificados para as instâncias de máquina recém-provisionadas.

== Transformando o arquivo de provisionamento CAPI para ClusterClass

=== Definição de ClusterClass

O código a seguir define um recurso ClusterClass, um modelo declarativo para implantar consistentemente tipos específicos de clusters Kubernetes. Esta especificação inclui configurações comuns de infraestrutura e plano de controle, permitindo o provisionamento eficiente e o gerenciamento de ciclo de vida uniforme em uma frota de clusters.
Existem algumas variáveis definidas no exemplo de ClusterClass a seguir, que serão substituídas durante o processo de instanciação do cluster usando os valores reais solicitados para cada instância de cluster.
As variáveis a seguir são usadas no exemplo:

* `metallbHelmChartVersion`: Esta variável opcional permite especificar a versão do gráfico Helm `MetalLB` a ser implantado no cluster; quando não fornecida, o gráfico Helm `MetalLB` não será implantado.
* `endpointCopierOperatorHelmChartVersion`: Esta variável opcional permite especificar a versão do gráfico Helm `Endpoint Copier Operator` a ser implantado no cluster (quando uma versão para o gráfico Helm `MetalLB` também tiver sido fornecida); quando não fornecida, o gráfico Helm `Endpoint Copier Operator` não será implantado.
* `controlPlaneMachineTemplateImageURL`: Esta variável obrigatória permite especificar a URL da imagem a ser usada para provisionar as máquinas do plano de controle.
* `controlPlaneMachineTemplateHostSelectorDeployRegion`: Esta variável obrigatória permite especificar o valor do seletor de host `deploy-region` para as máquinas do plano de controle.
* `controlPlaneMachineTemplateHostSelectorClusterType`: Esta variável obrigatória permite especificar o valor do seletor de host `cluster-type` para as máquinas do plano de controle.
* `controlPlaneMachineTemplateDataTemplateName`: Esta variável obrigatória permite especificar o nome do objeto de API `Metal3DataTemplate` a ser usado para as máquinas do plano de controle.
* `controlPlaneEndpointHost`: Esta variável obrigatória permite especificar o nome de host ou o endereço IP do endpoint do plano de controle.
* `tlsSan`: Esta variável obrigatória permite especificar a lista de Nomes Alternativos de Assunto (SANs) TLS para o endpoint do plano de controle.

O arquivo de definição de ClusterClass consiste nos quatro recursos a seguir:

* **ClusterClass**: Este recurso encapsula toda a definição do ClusterClass, incluindo os modelos de plano de controle e de infraestrutura. Além disso, ele inclui a lista de variáveis que serão substituídas durante o processo de instanciação (e define os patches que as utilizam).
* **RKE2ControlPlaneTemplate**: Este recurso define o modelo do plano de controle, especificando a configuração desejada para os nós do plano de controle. Além disso, alguns parâmetros serão substituídos pelos valores corretos durante o processo de instanciação.
* **Metal3ClusterTemplate**: Este recurso define o modelo de infraestrutura, especificando a configuração desejada para a infraestrutura subjacente. Ele inclui parâmetros como o endpoint do plano de controle e a flag cloudProviderEnabled (true|false). Além disso, alguns parâmetros serão substituídos pelos valores corretos durante o processo de instanciação.
* **Metal3MachineTemplate**: Este recurso define o blueprint para as máquinas dos nós do plano de controle, fornecendo os espaços reservados para que os parâmetros sejam substituídos pelos valores corretos durante o processo de instanciação.

=== Definição da instância de cluster

Dentro do contexto de ClusterClass, uma instância de cluster refere-se a uma instanciação específica e em execução de um cluster que foi criado com base em uma ClusterClass definida.
Ela representa uma implantação concreta com suas configurações, recursos e estado operacional exclusivos, derivados diretamente do blueprint especificado na ClusterClass.
Isso inclui o conjunto específico de máquinas, configurações de rede e componentes do Kubernetes associados que estão em execução ativa.
Entender a instância de cluster é crucial para gerenciar o ciclo de vida, realizar atualizações, executar operações de escalonamento e conduzir o monitoramento de um cluster implantado específico que foi provisionado usando a estrutura ClusterClass.

Para definir uma instância de cluster, precisamos definir os dois recursos a seguir:

* **Cluster**: Este recurso representa a instância de cluster real, incluindo uma referência ao seu `topology` (ou seja, objeto `ClusterClass`), a versão necessária do Kubernetes, o número de nós do plano de controle a serem instanciados e os valores fornecidos para cada uma das variáveis definidas no `ClusterClass` referenciado, que serão usados durante o processo de instanciação.
* **Metal3DataTemplate**: Este recurso fornece metadados adicionais para as máquinas no cluster (apenas máquinas do plano de controle neste exemplo), complementando o objeto `Metal3MachineTemplate` criado automaticamente para cada cluster instanciado. Observe que não é possível definir um único recurso `Metal3DataTemplate` válido para todos os clusters instanciados a partir de um `ClusterClass` comum, uma vez que o campo `clusterName` na especificação `Metal3DataTemplate` deve referenciar a instância de cluster específica à qual ele "pertence".
+

[,yaml,subs="attributes"]
----
apiVersion: cluster.x-k8s.io/v1beta2
kind: Cluster
metadata:
  name: emea-spa-cluster-3
  namespace: emea-spa
  labels:
    cluster-api.cattle.io/rancher-auto-import: "true"
spec:
  topology:
    classRef:
      name: example-clusterclass
      namespace: emea-spa
    version: v1.35.3+rke2r3
    controlPlane:
      replicas: 1
    variables:                       # Values to be replaced in the clusterclass template variables to create this specific cluster
    - name: endpointCopierOperatorHelmChartVersion
      value: 306.0.1+up0.3.0
    - name: metallbHelmChartVersion
      value: 306.0.2+up0.15.3
    - name: controlPlaneMachineTemplateImageURL
      value: http://fileserver.local:8080/eibimage-downstream-cluster.raw.sha256
    - name: controlPlaneMachineTemplateHostSelectorDeployRegion
      value: emea-spa
    - name: controlPlaneMachineTemplateHostSelectorClusterType
      value: group-3
    - name: controlPlaneMachineTemplateDataTemplateName
      value: emea-spa-cluster-3
    - name: controlPlaneEndpointHost
      value: 192.168.122.203
    - name: tlsSan
      value:
      - 192.168.122.203
      - https://192.168.122.203.sslip.io
---
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: Metal3DataTemplate
metadata:
  name: emea-spa-cluster-3
  namespace: emea-spa
spec:
  clusterName: emea-spa-cluster-3
  metaData:
    objectNames:
    - key: name
      object: machine
    - key: local-hostname
      object: machine
    - key: local_hostname
      object: machine

----

[NOTE]
====
Adicionar o rótulo `cluster-api.cattle.io/rancher-auto-import: "true"` a um objeto de API `Cluster` no grupo de API `cluster.x-k8s.io` importará o cluster para o Rancher (criando um objeto de API `Cluster` do Rancher correspondente no grupo de API `management.cattle.io`).
Consulte a https://documentation.suse.com/cloudnative/cluster-api/latest/en/user/rancher-cluster-registration.html#_how_to_register_a_capi_cluster_in_rancher_using_turtles_auto_import[documentação da Cluster API] para obter mais informações.
====

Essa abordagem simplifica o processo, permitindo que você implante um cluster usando apenas dois recursos assim que os blueprints do ClusterClass forem definidos.
