[#atip-hardware]
== Hardware

Os requisitos de hardware para o SUSE Telco Cloud são os seguintes:

* **Cluster de gerenciamento**: O cluster de gerenciamento contém componentes como `SUSE Linux Micro`, `RKE2`, `SUSE Rancher Prime`, `Metal^3^`, e é usado para gerenciar vários clusters downstream. Dependendo do número de clusters downstream a serem gerenciados, os requisitos de hardware para o servidor podem variar.
  ** Os requisitos mínimos para o servidor (`VM` ou `bare-metal`) são:
     *** RAM: 8 GB Mínimo (recomendamos pelo menos 16 GB)
     *** CPU: 2 Mínimo (recomendamos pelo menos 4 CPU)

* **Downstream clusters**: Os clusters downstream são os clusters implantados para executar cargas de trabalho de Telco. Requisitos específicos são necessários para habilitar certas capacidades de Telco como `SR-IOV`, `CPU Performance Optimization`, etc.
  ** SR-IOV: para anexar VFs (Virtual Functions) em modo de passagem a CNFs/VNFs, a NIC deve suportar SR-IOV e o VT-d/AMD-Vi deve estar habilitado no BIOS.
  ** Processadores de CPU: Para executar cargas de trabalho Telco específicas, o modelo de processador de CPU deve ser adaptado para habilitar a maioria dos recursos disponíveis nesta <<atip-features,tabela de referência>>.

[#atip-network]
== Rede

Como referência para a arquitetura de rede, o diagrama a seguir mostra uma arquitetura de rede típica para um ambiente de telecomunicações:

image::product-atip-requirements1.png[scaledwidth=100%]

A arquitetura de rede é baseada nos seguintes componentes:

* **Rede de gerenciamento**: Esta rede é usada para o gerenciamento de nós de clusters downstream. Ela é usada para o gerenciamento fora de banda. Geralmente, esta rede também é conectada a um switch de gerenciamento separado, mas pode ser conectada ao mesmo switch de serviço usando VLANs para isolar o tráfego.
* **Rede do plano de controle**: Esta rede é usada para a comunicação entre os nós do cluster downstream e os serviços que estão sendo executados neles. Esta rede também é usada para a comunicação entre os nós e os serviços externos, como os servidores `DHCP` ou `DNS`. Em alguns casos, para ambientes conectados, o switch/roteador pode lidar com o tráfego através da Internet.
* **Outras redes**: Em alguns casos, os nós podem ser conectados a outras redes para fins específicos.

[NOTE]
====
Para usar o fluxo de trabalho de provisionamento de rede direcionado, o cluster de gerenciamento deve ter conectividade de rede com o Baseboard Management Controller (BMC) do servidor do cluster downstream para que a preparação e o provisionamento do host possam ser automatizados.
====

=== Nós downstream

No SUSE Telco Cloud, antes que qualquer servidor downstream se torne parte de um cluster Kubernetes downstream em execução (ou execute um cluster Kubernetes downstream de nó único), é necessário passar por alguns dos https://github.com/metal3-io/baremetal-operator/blob/main/docs/baremetalhost-states.md[estados de provisionamento BaremetalHost].

* O Baseboard Management Controller (BMC) de um servidor downstream recém-declarado deve estar acessível através da rede out-of-band. O BMC é instruído (pelo serviço ironic em execução no cluster de gerenciamento) sobre as etapas iniciais a serem seguidas: 
. Extrair e carregar a imagem de ramdisk IPA indicada no `virtual media` oferecido pelo BMC. 
. Ligar o servidor.

[#atip-services]
== Serviços (DHCP, DNS, etc.)

Alguns serviços externos como `DHCP`, `DNS`, etc. podem ser necessários dependendo do tipo de ambiente onde são implantados:

* **Ambiente conectado**: Neste caso, os nós estarão conectados à Internet (via protocolos de roteamento L3) e os serviços externos serão fornecidos pelo cliente.
* **Ambiente desconectado / air gap**: Neste caso, os nós não terão conectividade IP com a Internet e serviços adicionais serão necessários para espelhar localmente o conteúdo exigido pelo fluxo de trabalho de provisionamento de rede direcionado.
* **Servidor de arquivos**: Um servidor de arquivos é usado para armazenar as imagens do SO a serem provisionadas nos nós do cluster downstream durante o fluxo de trabalho de provisionamento de rede direcionado. O gráfico Helm `Metal^3^` pode implantar um servidor de mídia para armazenar as imagens do SO — verifique a xref:metal3-media-server[seção] a seguir, mas também é possível usar um servidor web local existente.

[#atip-systemd-services]
== Desativando serviços do systemd

Para cargas de trabalho de telecomunicações, é importante desativar ou configurar adequadamente alguns dos serviços em execução nos nós para evitar qualquer impacto no desempenho da carga de trabalho em execução nos nós (latência).

* `rebootmgr` é um serviço que permite configurar uma estratégia de reinicialização quando o sistema tem atualizações pendentes.
Para cargas de trabalho de telecomunicações, é realmente importante desativar ou configurar adequadamente o serviço `rebootmgr` para evitar a reinicialização dos nós em caso de atualizações agendadas pelo sistema, para evitar qualquer impacto nos serviços em execução nos nós.

[NOTE]
====
Para obter mais informações sobre o `rebootmgr`, consulte o https://github.com/SUSE/rebootmgr[repositório GitHub do rebootmgr].
====

Verifique a estratégia que está sendo usada executando:

[,shell]
----
cat /etc/rebootmgr.conf
[rebootmgr]
window-start=03:30
window-duration=1h30m
strategy=best-effort
lock-group=default
----

e você pode desativá-la executando:

[,shell]
----
sed -i 's/strategy=best-effort/strategy=off/g' /etc/rebootmgr.conf
----

ou usando o comando `rebootmgrctl`:

[,shell]
----
rebootmgrctl strategy off
----

[NOTE]
====
Esta configuração para definir a estratégia `rebootmgr` pode ser automatizada usando o fluxo de trabalho de provisionamento de rede direcionado. Para obter mais informações, consulte a <<atip-automated-provisioning,documentação de Provisionamento Automatizado>>.
====

* `transactional-update` é um serviço que permite atualizações automáticas controladas pelo sistema. Para cargas de trabalho de telecomunicações, é importante desativar as atualizações automáticas para evitar qualquer impacto nos serviços em execução nos nós.

Para desativar as atualizações automáticas, você pode executar:

[,shell]
----
systemctl --now disable transactional-update.timer
systemctl --now disable transactional-update-cleanup.timer
----

* `fstrim` é um serviço que permite realizar o trim dos sistemas de arquivos automaticamente toda semana. Para cargas de trabalho de telecomunicações, é importante desativar o trim automático para evitar qualquer impacto nos serviços em execução nos nós.

Para desativar o trim automático, você pode executar:

[,shell]
----
systemctl --now disable fstrim.timer
----
