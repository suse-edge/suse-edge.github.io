[#mgmt-cluster-intro]
== Introdução
O cluster de gerenciamento é a parte do SUSE Telco Cloud que é usada para gerenciar o provisionamento e o ciclo de vida das pilhas de tempo de execução.
Do ponto de vista técnico, o cluster de gerenciamento contém os seguintes componentes:

* `SUSE Linux Micro` como o SO. Dependendo do caso de uso, algumas configurações como rede, armazenamento, usuários e argumentos de kernel podem ser personalizadas.
* `RKE2` como o cluster Kubernetes. Dependendo do caso de uso, ele pode ser configurado para usar plugins CNI específicos, como `Multus`, `Cilium`, `Calico`, etc.
* `Rancher` como a plataforma de gerenciamento para gerenciar o ciclo de vida dos clusters.
* `Metal^3^` como o componente para gerenciar o ciclo de vida dos nós bare-metal.
* `CAPI` como o componente para gerenciar o ciclo de vida dos clusters Kubernetes (clusters downstream). O `RKE2 CAPI Provider` é usado para gerenciar o ciclo de vida dos clusters RKE2.

Com todos os componentes mencionados acima, o cluster de gerenciamento pode gerenciar o ciclo de vida de clusters downstream, usando uma abordagem declarativa para gerenciar a infraestrutura e os aplicativos.

[NOTE]
====
Para obter mais informações sobre o `SUSE Linux Micro`, consulte: <<components-slmicro,SUSE Linux Micro>>

Para obter mais informações sobre o `RKE2`, consulte: <<components-rke2,RKE2>>

Para obter mais informações sobre o `Rancher`, consulte: <<components-rancher,Rancher>>

Para obter mais informações sobre o `Metal^3^`, consulte: <<components-metal3,Metal^3^>>
====

[#mgmt-cluster-setup]
== Etapas para configurar o cluster de gerenciamento

As seguintes etapas são necessárias para configurar o cluster de gerenciamento (usando um único nó):

image::product-atip-mgmtcluster1.png[scaledwidth=100%]

A seguir estão as principais etapas para configurar o cluster de gerenciamento usando uma abordagem declarativa:

. **xref:mgmt-cluster-image-preparation-connected[Preparação de imagem para ambientes conectados]**: O primeiro passo é preparar os manifestos e arquivos com todas as configurações necessárias para serem usados em ambientes conectados.

  - xref:mgmt-cluster-directory-structure[Estrutura de diretório para ambientes conectados]: Este passo cria uma estrutura de diretório a ser usada pelo Edge Image Builder para armazenar os arquivos de configuração e a própria imagem.
  - xref:mgmt-cluster-image-definition-file[Arquivo de definição do cluster de gerenciamento]: O arquivo `mgmt-cluster.yaml` é o principal arquivo de definição para o cluster de gerenciamento. Ele contém as seguintes informações sobre a imagem a ser criada:
        ** Informações da Imagem: As informações relacionadas à imagem a ser criada usando a imagem base.
        ** Sistema operacional: As configurações do sistema operacional a serem usadas na imagem.
        ** Kubernetes: Charts Helm e repositórios, versão do Kubernetes, configuração de rede e os nós a serem usados no cluster.
  - xref:mgmt-cluster-custom-folder[Pasta Personalizada]: A pasta `custom` contém os arquivos de configuração e scripts a serem usados pelo Edge Image Builder para implantar um cluster de gerenciamento totalmente funcional.
        ** Arquivos: Contém os arquivos de configuração a serem usados pelo cluster de gerenciamento.
        ** Scripts: Contém os scripts a serem usados pelo cluster de gerenciamento.
  - xref:mgmt-cluster-kubernetes-folder[Kubernetes folder]: A pasta `kubernetes` contém os arquivos de configuração a serem usados pelo cluster de gerenciamento.
        ** Manifestos: Contém os manifestos a serem usados pelo cluster de gerenciamento.
        ** Helm: Contém os arquivos de valores do Helm a serem usados pelo cluster de gerenciamento.
        ** Configuração: Contém os arquivos de configuração a serem usados pelo cluster de gerenciamento.
  - xref:mgmt-cluster-network-folder[Pasta de rede]: A pasta `network` contém os arquivos de configuração de rede a serem usados pelos nós do cluster de gerenciamento.

. **xref:mgmt-cluster-image-preparation-airgap[Preparação de imagem para ambientes air-gap]**: A etapa consiste em mostrar as diferenças para preparar os manifestos e arquivos a serem usados em um cenário air-gap.
  - xref:mgmt-cluster-image-definition-file-airgap[Modificações no arquivo de definição]: O arquivo `mgmt-cluster.yaml` deve ser modificado para incluir a seção `embeddedArtifactRegistry` com o campo `images` definido para todas as imagens de contêiner a serem incluídas na imagem de saída do EIB.
  - xref:mgmt-cluster-custom-folder-airgap[Modificações na pasta personalizada]: A pasta `custom` deve ser modificada para incluir os recursos necessários para executar o cluster de gerenciamento em um ambiente air-gap.
        ** Script de registro: O script `custom/scripts/99-register.sh` deve ser removido ao usar um ambiente air-gap.

. **xref:mgmt-cluster-image-creation[Criação de imagem]**: Esta etapa abrange a criação da imagem usando a ferramenta Edge Image Builder (para ambos os cenários, conectado e air-gap). Verifique os <<components-eib,pré-requisitos>> para executar a ferramenta Edge Image Builder em seu sistema.

. **xref:mgmt-cluster-provision[Provisionamento do cluster de gerenciamento]**: Esta etapa abrange o provisionamento do cluster de gerenciamento usando a imagem criada na etapa anterior (para ambos os cenários, conectado e air-gap). Esta etapa pode ser feita usando um laptop, servidor, VM ou qualquer outro sistema {x86-64} com uma porta USB.

[NOTE]
====
Para obter mais informações sobre o Edge Image Builder, consulte <<components-eib,Edge Image Builder>> e <<quickstart-eib,Início Rápido do Edge Image Builder>>.

[#mgmt-cluster-image-preparation-connected]
== Preparação de imagem para ambientes conectados

O Edge Image Builder é usado para criar a imagem para o cluster de gerenciamento; neste documento, abordamos a configuração mínima necessária para configurar o cluster de gerenciamento.

O Edge Image Builder é executado dentro de um contêiner, portanto, é necessário um tempo de execução do contêiner, como https://podman.io[Podman] ou https://rancherdesktop.io[Rancher Desktop]. Para este guia, assumimos que o podman está disponível.

Além disso, como pré-requisito para implantar um cluster de gerenciamento de alta disponibilidade, você precisa reservar três IPs em sua rede:

- `apiVIP` para o endereço VIP da API (usado para acessar o servidor de API do Kubernetes).
- `ingressVIP` para o endereço VIP de Ingress (consumido, por exemplo, pela interface do usuário do Rancher).
- `metal3VIP` para o endereço VIP do Metal3.

[NOTE]

A imagem `{micro-base-image-iso}` deve ser baixada do https://scc.suse.com/[SUSE Customer Center] ou da https://www.suse.com/download/sle-micro/[página de download da SUSE], e deve estar localizada na pasta `base-images`.

Para explicar os campos e valores no arquivo de definição `mgmt-cluster.yaml`, nós o dividimos nas seguintes seções.

- Seção de imagem (arquivo de definição):

[,yaml,subs="attributes"]
----
image:
  imageType: iso
  arch: x86_64
  baseImage: {micro-base-image-iso}
  outputImageName: eib-mgmt-cluster-image.iso
----

onde `baseImage` é a imagem original que você baixou do SUSE Customer Center ou da página de download da SUSE. `outputImageName` é o nome da nova imagem que será usada para provisionar o cluster de gerenciamento.

- Seção do sistema operacional (arquivo de definição):

[,yaml]
----
operatingSystem:
  isoConfiguration:
    installDevice: /dev/sda
  users:
  - username: root
    encryptedPassword: $ROOT_PASSWORD
  packages:
    packageList:
    - jq
    sccRegistrationCode: $SCC_REGISTRATION_CODE
----

onde `installDevice` é o dispositivo a ser usado para instalar o sistema operacional, `username` e `encryptedPassword` são as credenciais a serem usadas para acessar o sistema, `packageList` é a lista de pacotes a serem instalados (`jq` é necessário internamente durante o processo de instalação) e `sccRegistrationCode` é o código de registro usado para obter os pacotes e dependências durante o build e pode ser obtido do SUSE Customer Center.

A seção `helm` contém a lista de charts Helm a serem instalados, os repositórios a serem usados, e a configuração de versão para todos eles.

A seção `network` contém a configuração para a rede, como o `apiHost` e o `apiVIP` a serem usados pelo componente `RKE2`.
O `apiVIP` deve ser um endereço IP que não seja usado na rede e não deve fazer parte do pool DHCP (caso usemos DHCP). Além disso, quando usamos o `apiVIP` em um cluster de vários nós, ele é usado para acessar o servidor de API do Kubernetes.
O `apiHost` é a resolução de nomes para o `apiVIP` a ser usado pelo componente `RKE2`.

A seção `nodes` contém a lista de nós a serem usados no cluster. Neste exemplo, um cluster de nó único está sendo usado, mas ele pode ser estendido para um cluster de vários nós adicionando mais nós à lista (removendo o comentário das linhas).

[NOTE]
====
* Os nomes dos nós devem ser exclusivos no cluster.
* Opcionalmente, use o campo `initializer` para especificar o host de inicialização; caso contrário, será o primeiro nó da lista.
* Os nomes dos nós devem ser os mesmos que os nomes de host definidos na <<mgmt-cluster-network-folder,Pasta de rede>> quando a configuração de rede for necessária.
====

=== Pasta Personalizada

A pasta `custom` contém as seguintes subpastas:

[,console]
----
...
├── custom
│ ├── scripts
│ │ ├── 99-register.sh
│ │ ├── 99-mgmt-setup.sh

│     ├── mgmt-stack-setup.service

- A pasta `custom/files` contém os arquivos de configuração a serem usados pelo cluster de gerenciamento.
- A pasta `custom/scripts` contém os scripts a serem usados pelo cluster de gerenciamento.


A pasta `custom/files` contém os seguintes arquivos:

* `basic-setup.sh`: contém parâmetros de configuração para `Metal^3^`, `Rancher` e `MetalLB`. Modifique este arquivo apenas se desejar alterar os namespaces a serem usados.
+
[,shell]
----
#!/bin/bash
# Pre-requisites. Cluster already running
export KUBECTL="/var/lib/rancher/rke2/bin/kubectl"
export KUBECONFIG="/etc/rancher/rke2/rke2.yaml"

##################
# METAL3 DETAILS #
##################
export METAL3_CHART_TARGETNAMESPACE="metal3-system"

###########
# METALLB #
###########
export METALLBNAMESPACE="metallb-system"

###########
# RANCHER #
###########
export RANCHER_CHART_TARGETNAMESPACE="cattle-system"
export RANCHER_FINALPASSWORD="adminadminadmin"

die(){
  echo ${1} 1>&2
  exit ${2}
}
----

* `metal3.sh`: contém a configuração para o componente `Metal^3^` a ser usado (nenhuma modificação necessária). Em versões futuras, este script será substituído, utilizando `Rancher Turtles` em vez disso, para facilitar.
+
[,shell]
----
#!/bin/bash
set -euo pipefail

BASEDIR="$(dirname "$0")"
source ${BASEDIR}/basic-setup.sh

METAL3LOCKNAMESPACE="default"
METAL3LOCKCMNAME="metal3-lock"

trap 'catch $? $LINENO' EXIT

catch() {
  if [ "$1" != "0" ]; then
    echo "Error $1 occurred on $2"
    ${KUBECTL} delete configmap ${METAL3LOCKCMNAME} -n ${METAL3LOCKNAMESPACE}
  fi
}

# Get or create the lock to run all those steps just in a single node
# As the first node is created WAY before the others, this should be enough
# TODO: Investigate if leases is better
if [ $(${KUBECTL} get cm -n ${METAL3LOCKNAMESPACE} ${METAL3LOCKCMNAME} -o name | wc -l) -lt 1 ]; then
  ${KUBECTL} create configmap ${METAL3LOCKCMNAME} -n ${METAL3LOCKNAMESPACE} --from-literal foo=bar
else
  exit 0
fi

# Wait for metal3
while ! ${KUBECTL} wait --for condition=ready -n ${METAL3_CHART_TARGETNAMESPACE} $(${KUBECTL} get pods -n ${METAL3_CHART_TARGETNAMESPACE} -l app.kubernetes.io/name=metal3-ironic -o name) --timeout=10s; do sleep 2 ; done

# Get the ironic IP
IRONICIP=$(${KUBECTL} get cm -n ${METAL3_CHART_TARGETNAMESPACE} ironic -o jsonpath='{.data.IRONIC_IP}')

# If LoadBalancer, use metallb, else it is NodePort
if [ $(${KUBECTL} get svc -n ${METAL3_CHART_TARGETNAMESPACE} metal3-metal3-ironic -o jsonpath='{.spec.type}') == "LoadBalancer" ]; then
  # Wait for metallb
  while ! ${KUBECTL} wait --for condition=ready -n ${METALLBNAMESPACE} $(${KUBECTL} get pods -n ${METALLBNAMESPACE} -l app.kubernetes.io/component=controller -o name) --timeout=10s; do sleep 2 ; done

  # Do not create the ippool if already created
  ${KUBECTL} get ipaddresspool -n ${METALLBNAMESPACE} ironic-ip-pool -o name || cat <<-EOF | ${KUBECTL} apply -f -
  apiVersion: metallb.io/v1beta1
  kind: IPAddressPool
  metadata:
    name: ironic-ip-pool
    namespace: ${METALLBNAMESPACE}
  spec:
    addresses:
    - ${IRONICIP}/32
    serviceAllocation:
      priority: 100
      serviceSelectors:
      - matchExpressions:
        - {key: app.kubernetes.io/name, operator: In, values: [metal3-ironic]}
    EOF

  # Same for L2 Advs
  ${KUBECTL} get L2Advertisement -n ${METALLBNAMESPACE} ironic-ip-pool-l2-adv -o name || cat <<-EOF | ${KUBECTL} apply -f -
  apiVersion: metallb.io/v1beta1
  kind: L2Advertisement
  metadata:
    name: ironic-ip-pool-l2-adv
    namespace: ${METALLBNAMESPACE}
  spec:
    ipAddressPools:
    - ironic-ip-pool
    EOF
fi

# Clean up the lock cm

${KUBECTL} delete configmap ${METAL3LOCKCMNAME} -n ${METAL3LOCKNAMESPACE}
----

- `rancher.sh`: contém a configuração para o componente `Rancher` a ser usado (nenhuma modificação necessária).
+
[,shell]
----
#!/bin/bash
set -euo pipefail

BASEDIR="$(dirname "$0")"
source ${BASEDIR}/basic-setup.sh

RANCHERLOCKNAMESPACE="default"
RANCHERLOCKCMNAME="rancher-lock"

if [ -z "${RANCHER_FINALPASSWORD}" ]; then
  # If there is no final password, then finish the setup right away
  exit 0
fi

trap 'catch $? $LINENO' EXIT

catch() {
  if [ "$1" != "0" ]; then
    echo "Error $1 occurred on $2"
    ${KUBECTL} delete configmap ${RANCHERLOCKCMNAME} -n ${RANCHERLOCKNAMESPACE}
  fi
}

# Get or create the lock to run all those steps just in a single node
# As the first node is created WAY before the others, this should be enough
# TODO: Investigate if leases is better
if [ $(${KUBECTL} get cm -n ${RANCHERLOCKNAMESPACE} ${RANCHERLOCKCMNAME} -o name | wc -l) -lt 1 ]; then
  ${KUBECTL} create configmap ${RANCHERLOCKCMNAME} -n ${RANCHERLOCKNAMESPACE} --from-literal foo=bar
else
  exit 0
fi

# Wait for rancher to be deployed
while ! ${KUBECTL} wait --for condition=ready -n ${RANCHER_CHART_TARGETNAMESPACE} $(${KUBECTL} get pods -n ${RANCHER_CHART_TARGETNAMESPACE} -l app=rancher -o name) --timeout=10s; do sleep 2 ; done
until ${KUBECTL} get ingress -n ${RANCHER_CHART_TARGETNAMESPACE} rancher > /dev/null 2>&1; do sleep 10; done

RANCHERBOOTSTRAPPASSWORD=$(${KUBECTL} get secret -n ${RANCHER_CHART_TARGETNAMESPACE} bootstrap-secret -o jsonpath='{.data.bootstrapPassword}' | base64 -d)
RANCHERHOSTNAME=$(${KUBECTL} get ingress -n ${RANCHER_CHART_TARGETNAMESPACE} rancher -o jsonpath='{.spec.rules[0].host}')

# Skip the whole process if things have been set already
if [ -z $(${KUBECTL} get settings.management.cattle.io first-login -ojsonpath='{.value}') ]; then
  # Add the protocol
  RANCHERHOSTNAME="https://${RANCHERHOSTNAME}"
  TOKEN=""
  while [ -z "${TOKEN}" ]; do
    # Get token
    sleep 2
    TOKEN=$(curl -sk -X POST ${RANCHERHOSTNAME}/v3-public/localProviders/local?action=login -H 'content-type: application/json' -d "{\"username\":\"admin\",\"password\":\"${RANCHERBOOTSTRAPPASSWORD}\"}" | jq -r .token)
  done

  # Set password
  curl -sk ${RANCHERHOSTNAME}/v3/users?action=changepassword -H 'content-type: application/json' -H "Authorization: Bearer $TOKEN" -d "{\"currentPassword\":\"${RANCHERBOOTSTRAPPASSWORD}\",\"newPassword\":\"${RANCHER_FINALPASSWORD}\"}"

  # Create a temporary API token (ttl=60 minutes)
  APITOKEN=$(curl -sk ${RANCHERHOSTNAME}/v3/token -H 'content-type: application/json' -H "Authorization: Bearer ${TOKEN}" -d '{"type":"token","description":"automation","ttl":3600000}' | jq -r .token)

  curl -sk ${RANCHERHOSTNAME}/v3/settings/server-url -H 'content-type: application/json' -H "Authorization: Bearer ${APITOKEN}" -X PUT -d "{\"name\":\"server-url\",\"value\":\"${RANCHERHOSTNAME}\"}"
  curl -sk ${RANCHERHOSTNAME}/v3/settings/telemetry-opt -X PUT -H 'content-type: application/json' -H 'accept: application/json' -H "Authorization: Bearer ${APITOKEN}" -d '{"value":"out"}'
fi

# Clean up the lock cm
${KUBECTL} delete configmap ${RANCHERLOCKCMNAME} -n ${RANCHERLOCKNAMESPACE}
----

[#metal3-media-server]
[NOTE]
====
O Servidor de Mídia é um recurso opcional incluído no Metal^3^ (por padrão, está desabilitado). Para usar o recurso Metal3, você precisa configurá-lo no manifesto anterior.
Para usar o servidor de mídia Metal^3^, especifique a seguinte variável:

- adicione `enable_metal3_media_server` a `true` para habilitar o recurso de servidor de mídia na seção global.
- Inclua a seguinte configuração sobre o servidor de mídia, onde $\{MEDIA_VOLUME_PATH\} é o caminho para o volume de mídia (por exemplo, `/home/metal3/bmh-image-cache`).
+
[,yaml]
----
metal3-media:
  mediaVolume:
    hostPath: ${MEDIA_VOLUME_PATH}
----

Um servidor de mídia externo pode ser usado para armazenar as imagens e, caso você queira usá-lo com TLS, precisará fornecer o pacote de CA confiável para o Metal^3^.

*Prepare o pacote de CA:*

Primeiro, prepare seu arquivo de pacote de CA contendo todos os certificados necessários pelo Metal^3^. Isso inclui o(s) certificado(s) de CA do seu servidor de mídia externo.
+
*Opcional – Pacote de CA do sistema:* Se o Metal^3^ também precisar confiar em CAs públicas (por exemplo, ao acessar recursos HTTPS externos), você pode incluir o pacote de CA do sistema. Extraia-o de uma imagem de contêiner e concatene-o com seus certificados personalizados:
+
[,shell]
----
# Extract system CAs from a container image
podman run --rm registry.suse.com/bci/bci-base:latest cat /etc/ssl/certs/ca-certificates.crt > system-cas.pem

# Concatenate system CAs with your custom CA
cat system-cas.pem your-custom-ca.crt > ca-bundle.pem
----
+
Ou, se você precisar apenas da sua CA personalizada:
+
[,shell]
----
cp your-custom-ca.crt ca-bundle.pem
----
+
[IMPORTANT]
====
Se você incluir o pacote de CA do sistema, você se torna responsável por mantê-lo atualizado. As CAs do sistema em imagens de contêiner podem ficar desatualizadas à medida que os certificados expiram ou são revogados. Atualize periodicamente o pacote extraindo-o novamente de uma imagem de contêiner atualizada.
====

*Crie o ConfigMap:*

Você pode criar o ConfigMap de duas maneiras:

. *Usando um arquivo de manifesto (recomendado para EIB):* Crie o arquivo `kubernetes/manifests/metal3-cacert-configmap.yaml` e inclua o conteúdo do pacote de CA em linha. Você precisa recuar corretamente cada linha do certificado com 4 espaços:
+
[,yaml]
----
apiVersion: v1
kind: Namespace
metadata:
  name: metal3-system
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: tls-ca-bundle
  namespace: metal3-system
data:
  ca-bundle.pem: |
    -----BEGIN CERTIFICATE-----
    MIIDXTCCAkWgAwIBAgIJAKJ... (your certificate content here)
    ...
    -----END CERTIFICATE-----
    -----BEGIN CERTIFICATE-----
    MIIEkjCCA3qgAwIBAgIQCgF... (additional certificates if any)
    ...
    -----END CERTIFICATE-----
----
+
Para preencher este arquivo automaticamente a partir do seu `ca-bundle.pem`, você pode usar:
+
[,shell]
----
cat > kubernetes/manifests/metal3-cacert-configmap.yaml <<EOF
apiVersion: v1
kind: Namespace
metadata:
  name: metal3-system
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: tls-ca-bundle
  namespace: metal3-system
data:
  ca-bundle.pem: |
$(sed 's/^/    /' ca-bundle.pem)
EOF
----

. *Usando o kubectl diretamente (para implantação manual):* Se você não estiver usando o EIB e quiser criar o ConfigMap diretamente no cluster:
+
[,shell]
----
kubectl -n metal3-system create configmap tls-ca-bundle --from-file=ca-bundle.pem=./ca-bundle.pem
----

- Defina o valor de `global.trustedCAs` no arquivo `metal3.yaml` para referenciar o nome do ConfigMap:
+
[,yaml]
----
global:
  trustedCAs: tls-ca-bundle
----

=== Pasta de rede

A pasta `network` contém tantos arquivos quanto nós no cluster de gerenciamento. No nosso caso, temos apenas um nó, portanto, temos apenas um arquivo chamado `mgmt-cluster-node1.yaml`.
O nome do arquivo deve corresponder ao nome do host definido no arquivo de definição `mgmt-cluster.yaml` na seção network/node descrita acima.

Se você precisar personalizar a configuração de rede, por exemplo, para usar um endereço IP estático específico (cenário sem DHCP), você pode usar o arquivo `mgmt-cluster-node1.yaml` na pasta `network`. Ele contém as seguintes informações:

* `$\{MGMT_GATEWAY\}`: O endereço IP do gateway.
* `$\{MGMT_DNS\}`: O endereço IP do servidor DNS.
* `$\{MGMT_MAC\}`: O endereço MAC da interface de rede.
* `$\{MGMT_NODE_IP\}`: O endereço IP do cluster de gerenciamento.

routes:

    table-id: 254

  config:
    server:
    - ${MGMT_DNS}
    - 8.8.8.8
interfaces:
- name: eth0
  type: ethernet
  state: up
  mac-address: ${MGMT_MAC}
  ipv4:
    address:
    - ip: ${MGMT_NODE_IP}
      prefix-length: 24
    dhcp: false
    enabled: true
  ipv6:
    enabled: false

----

Se você quiser usar DHCP para obter o endereço IP, você pode usar a seguinte configuração (o endereço `MAC` deve ser definido corretamente usando a variável `$\{MGMT_MAC\}`):

- name: eth0
  type: ethernet
  state: up
  mac-address: ${MGMT_MAC}
  ipv4:

    enabled: true

    enabled: false

=== Modificações na pasta kubernetes

- Atualize o arquivo `kubernetes/helm/values/metal3.yaml` para definir o parâmetro do Helm chart `metal3-ironic.ipa.useHauler` como `true` (valor booleano).

+
[,yaml]
----
global:
  ironicIP: ${METAL3_VIP}
  enable_vmedia_tls: false
  predictableNicNames: "true"
  # trustedCAs: tls-ca-bundle  # Optional: Uncomment and set to ConfigMap name for additional trusted CAs

  ipa:
    useHauler: true
  persistence:
    ironic:
      size: "5Gi"

----

- Atualize o arquivo `kubernetes/helm/values/rancher.yaml` para modificar o parâmetro `hostname`. Em ambientes air-gapped, serviços externos de resolução de DNS como o `sslip.io` não estão acessíveis. Há duas opções:

.. *Opção 1: Usar DNS interno* (Recomendado): Configure seu servidor DNS interno para resolver o nome de host do Rancher e atualize o arquivo de acordo:
+
[,yaml,subs="attributes"]
----
hostname: rancher.yourdomain.internal
bootstrapPassword: "foobar"
replicas: 1
global:
  cattle:
    systemDefaultRegistry: "registry.rancher.com"
----

.. *Opção 2: Usar injeção em /etc/hosts*: Se você não tiver um servidor DNS interno, poderá injetar uma entrada estática `/etc/hosts` via EIB. Crie um arquivo em `eib/os-files/etc/hosts` na sua estrutura de diretórios EIB com um conteúdo como:
+
[,shell,subs="attributes"]
----
# Static DNS resolution for Rancher in air-gapped environment
$\{INGRESS_VIP} rancher-$\{INGRESS_VIP}.sslip.io
----
+
Em seguida, atualize o arquivo `rancher.yaml` para usar este nome de host:
+
[,yaml,subs="attributes"]
----
hostname: rancher-$\{INGRESS_VIP}.sslip.io
bootstrapPassword: "foobar"
replicas: 1
global:
  cattle:
    systemDefaultRegistry: "registry.rancher.com"
----
+
[IMPORTANT]
====
Ao usar a Opção 2, lembre-se de que o arquivo `/etc/hosts` precisará estar presente em qualquer sistema que precise acessar a interface do Rancher, não apenas nos nós do cluster de gerenciamento.
====

- Você precisa modificar o `$\{MGMT_CLUSTER_REGISTRY_IP\}` com um IP estático reservado para o SUSE Private Registry nos seguintes arquivos:

  - $\{MGMT_CLUSTER_REGISTRY_IP\}/32

+
[,yaml,subs="attributes"]
----
core:
  secretName: suse-registry-tls
expose:
  tls:
    certSource: secret
    enabled: true
    secret:
      secretName: suse-registry-tls
  type: loadBalancer

    registry:
      size: 20Gi
----

- O `kubernetes/manifests/suse-private-registry-creds.yaml` deve ser criado com o seguinte conteúdo:

[,yaml,subs="attributes"]
----
apiVersion: v1
kind: Secret
metadata:
  name: suse-registry
  namespace: suse-private-registry
type: kubernetes.io/dockerconfigjson
data:
  .dockerconfigjson: $\{DOCKER_CONFIG_JSON_BASE64\}
---
apiVersion: v1
kind: Secret
metadata:
    name: suse-registry-tls
    namespace: suse-private-registry
type: kubernetes.io/tls
data:
    tls.crt: $\{TLS_CRT_BASE64\}
    tls.key: $\{TLS_KEY_BASE64\}
----

Você precisa modificar o `$\{DOCKER_CONFIG_JSON_BASE64\}`, `$\{TLS_CRT_BASE64\}` e `$\{TLS_KEY_BASE64\}`. Para configurar corretamente o docker config json (base64), você pode fazer o seguinte:

[,shell,subs="attributes"]
----
# $\{DOCKER_CONFIG_JSON_BASE64\} CONTENT
echo -n '{"auths":{"&lt;MGMT_CLUSTER_REGISTRY_IP&gt;":{"username":"&lt;USERNAME&gt;","password":"&lt;PASSWORD&gt;","auth":"&lt;AUTH&gt;"}}}' | base64 -w 0
----

onde o IP é o mesmo que o `$\{MGMT_CLUSTER_REGISTRY_IP\}` configurado anteriormente, e os valores `&lt;USERNAME&gt;` e `&lt;PASSWORD&gt;` podem ser recuperados da https://documentation.suse.com/cloudnative/suse-private-registry/html/private-registry/pr-deployment.html#pr-deployment-kube-secrets[documentação oficial do SUSE Private Registry]; o valor `&lt;AUTH&gt;` definido no campo `auth` é a codificação base64 da concatenação `&lt;USERNAME&gt;:&lt;PASSWORD&gt;`.


Para definir o conteúdo dos campos `tls.crt` e `tls.key` no manifesto do Secret `suse-registry-tls` acima, você pode gerar seu próprio certificado autoassinado TLS e a chave privada relacionada executando os seguintes comandos:

[,shell,subs="attributes"]
----
# Generate a self-signed certificate and key
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -sha256 -days 365 -nodes

# Convert them to base64 for the suse-private-registry-creds.yaml file
cat cert.pem | base64 -w 0
cat key.pem | base64 -w 0
----

== Provisionar o cluster de gerenciamento

A imagem anterior contém todos os componentes explicados acima e pode ser usada para provisionar o cluster de gerenciamento usando uma máquina virtual ou um servidor bare metal (usando o recurso de virtual-media).

[#mgmt-cluster-dualstack]
== Considerações e configuração de pilha dupla

Os exemplos mostrados nas seções anteriores fornecem orientação e exemplos sobre como configurar um cluster de gerenciamento IPv4 de pilha única. Tal cluster de gerenciamento é independente do status operacional dos clusters downstream, que podem ser configurados individualmente para operar em configuração de pilha única IPv4/IPv6 ou pilha dupla, uma vez implantados. No entanto, a maneira como o cluster de gerenciamento é configurado tem um impacto direto nos protocolos de comunicação que podem ser usados durante a fase de provisionamento, onde as comunicações in-band e out-of-band devem ocorrer de acordo com os protocolos suportados pelo cluster de gerenciamento e pelo host downstream. Caso se espere que alguns ou todos os BMCs e/ou nós do cluster downstream usem IPv6, uma configuração de pilha dupla para o cluster de gerenciamento é necessária.

[NOTE]
====
Clusters de gerenciamento IPv6 de pilha única ainda não são suportados.
====

Para obter a funcionalidade de pilha dupla, o Kubernetes deve receber CIDRs IPv4 e IPv6 para PODs e Serviços. No entanto, outros componentes também exigem ajustes específicos antes de criar a imagem do cluster de gerenciamento com o EIB. Os serviços de provisionamento Metal^3^ (Ironic) podem ser configurados de diferentes maneiras, dependendo da sua infraestrutura ou requisitos:

- Os serviços Ironic podem ser configurados para escutar em todas as interfaces do sistema em vez de um único endereço IP, portanto, desde que o(s) host(s) do cluster de gerenciamento tenha(m) endereços IPv4 e IPv6 atribuídos à interface relevante, qualquer um deles pode potencialmente ser usado durante o provisionamento. Observe que, neste momento, apenas um desses endereços pode ser selecionado para a geração da URL (para consumo por outros serviços, por exemplo, o Baremetal Operator, BMCs, etc.); como consequência, para habilitar comunicações IPv6 com os BMCs, o Baremetal Operator pode ser instruído a expor e transmitir uma URL IPv6 ao lidar com definições BMH que incluam um endereço IPv6. Em outras palavras, quando um BMC é identificado como compatível com IPv6, o provisionamento será realizado apenas via IPv6, e via IPv4 em todos os outros casos.

- Um único nome de host, resolvendo para IPv4 e IPv6, pode ser usado pelo Metal^3^ para permitir que o Ironic use esses endereços para vinculação e criação de URL. Essa abordagem permite uma configuração fácil e comportamento flexível (tanto IPv4 quanto IPv6 permanecem viáveis em cada etapa de provisionamento), mas requer uma infraestrutura com servidores DNS, alocações de IP e registros preexistentes já em vigor.

Em ambos os casos, o Kubernetes precisará saber quais CIDRs usar para IPv4 e IPv6, portanto, você pode adicionar as seguintes linhas ao seu `kubernetes/config/server.yaml` no diretório EIB, certificando-se de listar o IPv4 primeiro:

[,yaml]
----
service-cidr: 10.96.0.0/12,fd12:4567:789c::/112
cluster-cidr: 193.168.0.0/18,fd12:4567:789b::/48
----

Alguns contêineres aproveitam a rede do host, portanto, modifique a configuração de rede para o(s) host(s), no diretório `network`, para habilitar a conectividade IPv6:

[,yaml]
----
routes:
  config:
  - destination: 0.0.0.0/0
    next-hop-address: ${MGMT_GATEWAY_V4}
    next-hop-interface: eth0
  - destination: ::/0
    next-hop-address: ${MGMT_GATEWAY_V6}
    next-hop-interface: eth0 
dns-resolver:
  config:
    server:
    - ${MGMT_DNS}
    - 8.8.8.8
    - 2001:4860:4860::8888
interfaces:
- name: eth0
  type: ethernet
  state: up
  mac-address: ${MGMT_MAC}
  ipv4:
    address:
    - ip: ${MGMT_CLUSTER_IP_V4}
      prefix-length: 24
    dhcp: false
    enabled: true
  ipv6:
    address:
    - ip: ${MGMT_CLUSTER_IP_V6}
      prefix-length: 128
    dhcp: false
    autoconf: false
    enabled: true
----

Substitua os espaços reservados pelos endereços IP do gateway, servidor DNS adicional (se necessário), o endereço MAC da interface de rede e o endereço IP do cluster de gerenciamento. Se a autoconfiguração de endereço for preferida, consulte o trecho a seguir e apenas defina a variável `$\{MGMT_MAC\}`:

[,yaml]
----
interfaces:
- name: eth0
  type: ethernet
  state: up
  mac-address: ${MGMT_MAC}
  ipv4:
    enabled: true
    dhcp: true
  ipv6:
    enabled: false
    dhcp: true
    autoconf: true
----
