[#kernel-image-for-real-time]
== Imagem do kernel para tempo real

A imagem do kernel de tempo real não é necessariamente melhor do que um kernel padrão.
É um kernel diferente ajustado para um caso de uso específico. O kernel de tempo real é ajustado para menor latência ao custo de throughput. O kernel de tempo real não é recomendado para uso geral, mas, em nosso caso, este é o kernel recomendado para cargas de trabalho de telecomunicações onde a latência é um fator chave.

Existem quatro recursos principais:

* Execução determinística:
+
Obtenha maior previsibilidade — garanta que processos de negócios críticos sejam concluídos a tempo, sempre, e forneça um serviço de alta qualidade, mesmo sob cargas pesadas do sistema. Ao proteger recursos essenciais do sistema para processos de alta prioridade, você pode garantir maior previsibilidade para aplicações sensíveis ao tempo.
+
* Baixo jitter:
+
O baixo jitter, construído sobre a tecnologia altamente determinística, ajuda a manter as aplicações sincronizadas com o mundo real. Isso ajuda serviços que precisam de cálculos contínuos e repetidos.
+
* Herança de prioridades:
+
Herança de prioridades refere-se à capacidade de um processo de menor prioridade assumir uma prioridade mais alta quando há um processo de maior prioridade que exige que o processo de menor prioridade termine antes que ele possa concluir sua tarefa. O SUSE Linux Enterprise Real Time resolve esses problemas de inversão de prioridade para processos de missão crítica.
+
* Interrupções de thread:
+
Processos executados em modo de interrupção em um sistema operacional de propósito geral não são preemptíveis. Com o SUSE Linux Enterprise Real Time, essas interrupções foram encapsuladas por threads do kernel, que são interrompíveis e permitem que as interrupções de hardware e software sejam preemptadas por processos de maior prioridade definidos pelo usuário.
+
No nosso caso, se você instalou uma imagem de tempo real como `SUSE Linux Micro RT`, o kernel de tempo real já está instalado. A partir do https://scc.suse.com/[SUSE Customer Center], você pode baixar a imagem do kernel de tempo real.
+

[NOTE]
====
Para mais informações sobre o kernel de tempo real, visite https://www.suse.com/products/realtime/[SUSE Real Time].
====

[#kernel-args]
== Argumentos do kernel para baixa latência e alto desempenho

Configurar os argumentos apropriados do kernel é essencial para otimizar o desempenho, alcançar baixa latência e garantir a implantação bem-sucedida de clusters para cargas de trabalho de telecomunicações. Embora alguns parâmetros sejam projetados especificamente para permitir que o kernel de tempo real funcione de forma ideal, esta seção se aplica tanto às configurações de kernel RT quanto às padrão. Além disso, certos argumentos são obrigatórios para que o método de Provisionamento de Rede Direcionado implante com sucesso nós de cluster downstream.

* Remova `kthread_cpus` ao usar o kernel de tempo real do SUSE. Este parâmetro controla em quais CPUs as threads do kernel são criadas. Ele também controla quais CPUs são permitidos para o PID 1 e para o carregamento de módulos do kernel (o auxiliar de espaço do usuário kmod). Este parâmetro não é reconhecido e não tem qualquer efeito.

* Isole os núcleos da CPU usando `isolcpus`, `nohz_full`, `rcu_nocbs` e `irqaffinity`. Para uma lista abrangente de técnicas de CPU pinning, consulte o capítulo <<cpu-pinning-host,CPU Pinning on Host>>.

* Adicione as flags `domain,nohz,managed_irq` ao argumento de kernel `isolcpus`. Sem nenhuma flag, `isolcpus` é equivalente a especificar apenas a flag `domain`. Isso isola as CPUs especificadas do agendamento, incluindo tarefas do kernel. A flag `nohz` interrompe o tick do agendador nas CPUs especificadas (se apenas uma tarefa estiver executável em uma CPU), e a flag `managed_irq` evita o roteamento de interrupções externas (dispositivo) gerenciadas nas CPUs especificadas. Observe que as linhas IRQ de dispositivos NVMe são totalmente gerenciadas pelo kernel e, como consequência, serão roteadas para os núcleos não isolados (housekeeping). Por exemplo, a linha de comando fornecida ao final desta seção resultará em apenas quatro filas (mais uma fila de administração/controle) alocadas no sistema:

+
[,shell]
----
for I in $(grep nvme0 /proc/interrupts | cut -d ':' -f1); do cat /proc/irq/${I}/effective_affinity_list; done | column
39      0       19      20      39
----
+
Este comportamento evita qualquer interrupção causada por E/S de disco em qualquer aplicação sensível ao tempo em execução nos núcleos isolados, mas pode exigir atenção e um projeto cuidadoso para cargas de trabalho focadas em armazenamento.

* Ajuste os ticks (interrupções de temporizador periódicas do kernel):
** `skew_tick=1`: os ticks podem, às vezes, ocorrer simultaneamente. Em vez de todas as CPUs receberem seu tick de temporizador exatamente no mesmo momento, `skew_tick=1` faz com que ocorram em momentos ligeiramente deslocados. Isso ajuda a reduzir o jitter do sistema, resultando em tempos de resposta de interrupção mais consistentes e menores (um requisito essencial para aplicações sensíveis à latência).
** `nohz=on`: interrompe o tick de temporizador periódico em CPUs ociosas.
** `nohz_full=<cpu-cores>`: Interrompe o tick de temporizador periódico em CPUs especificadas que são dedicadas a aplicações de tempo real.

* Desative o tratamento de Machine Check Exception (MCE) especificando `mce=off`. MCEs são erros de hardware detectados pelo processador e desativá-los pode evitar logs ruidosos.

* Adicione `nowatchdog` para desativar o watchdog de soft-lockup, que é implementado como um temporizador em execução no contexto de interrupção de hardware do temporizador. Quando ele expira (ou seja, um soft lockup é detectado), ele imprimirá um aviso (no contexto de interrupção de hardware), executando quaisquer alvos de latência. Mesmo que nunca expire, ele entra na lista de temporizadores, aumentando ligeiramente a sobrecarga de cada interrupção de temporizador. Esta opção também desativa o watchdog NMI, para que os NMIs não possam interferir.

* `nmi_watchdog=0` desativa o watchdog NMI (Non-Maskable Interrupt). Isso pode ser omitido quando `nowatchdog` é usado.

* RCU (Read-Copy-Update) é um mecanismo de kernel que permite acesso simultâneo e sem bloqueio para muitos leitores a dados compartilhados. Um callback RCU, uma função acionada após um 'período extra', garante que todos os leitores anteriores tenham terminado para que os dados antigos possam ser recuperados com segurança. Nós ajustamos o RCU, particularmente para cargas de trabalho sensíveis, para descarregar esses callbacks de CPUs dedicadas (fixadas), evitando que operações do kernel interfiram em tarefas críticas e sensíveis ao tempo.
** Especifique as CPUs fixadas em `rcu_nocbs` para que os callbacks RCU não sejam executados nelas. Isso ajuda a reduzir o jitter e a latência para as cargas de trabalho de tempo real.
** `rcu_nocb_poll` faz com que as CPUs sem callback façam 'polling' regularmente para verificar se o tratamento de callback é necessário. Isso pode reduzir a sobrecarga de interrupção.
** `rcupdate.rcu_cpu_stall_suppress=1` suprime avisos de travamento de CPU RCU, que às vezes podem ser falsos positivos em sistemas de tempo real com carga pesada
** `rcupdate.rcu_expedited=1` acelera o período extra para operações RCU, tornando as seções críticas de leitura mais responsivas
** `rcupdate.rcu_normal_after_boot=1` Quando usado com rcu_expedited, permite que o RCU reverta para a operação normal (não acelerada) após a inicialização do sistema.
** `rcupdate.rcu_task_stall_timeout=0` desativa o detector de travamento de tarefas RCU, evitando possíveis avisos ou paradas do sistema devido a tarefas RCU de longa duração.
** `rcutree.kthread_prio=99` define a prioridade da thread de callback do kernel RCU para o valor mais alto possível (99), garantindo que ela seja agendada imediatamente para processar callbacks prontamente quando necessário.

* Adicione `ignition.platform.id=openstack` para que o Metal^3^ e a API de Cluster provisionem/desprovisionem o cluster com sucesso. Isso é usado pelo agente Python do Metal^3^, que se originou do OpenStack Ironic.

* Habilite https://documentation.suse.com/smart/network/html/network-interface-predictable-naming/index.html[Nomeação previsível de interface de rede] via `net.ifnames=1`. A partir do SUSE Linux Micro 6.2, isso é habilitado por padrão e uma configuração explícita não é necessária. Para versões anteriores à 6.2, isso deve ser definido explicitamente como um argumento do kernel. Isso se alinha com a configuração `predictableNicNames` no gráfico Helm Metal^3^ do Cluster de Gerenciamento, que é necessária para que o Provisionamento de Rede Direcionado funcione corretamente. A nomenclatura consistente de interface de rede também é crítica quando o SR-IOV é utilizado.

* Remova `intel_pstate=passive`. Esta opção configura `intel_pstate` para funcionar com governadores cpufreq genéricos, mas para fazer isso funcionar, ela desativa os P-states gerenciados por hardware (`HWP`) como um efeito colateral. Para reduzir a latência de hardware, esta opção não é recomendada para cargas de trabalho em tempo real.

* Substitua `intel_idle.max_cstate=0 processor.max_cstate=1` por `idle=poll`. Para evitar transições de C-State, a opção `idle=poll` é usada para desativar as transições de C-State e manter a CPU no C-State mais alto. A opção `intel_idle.max_cstate=0` desativa `intel_idle`, portanto `acpi_idle` é usada, e `acpi_idle.max_cstate=1` então define o C-state máximo para acpi_idle.
Em arquiteturas {x86-64}, o primeiro ACPI C-State é sempre `POLL`, mas ele usa uma função `poll_idle()`, que pode introduzir uma pequena latência ao ler o clock periodicamente e reiniciar o loop principal em `do_idle()` após um tempo limite (isso também envolve limpar e definir a flag de tarefa `TIF_POLL`).
Em contraste, `idle=poll` executa um loop contínuo, aguardando ativamente que uma tarefa seja reagendada. Isso minimiza a latência de saída do estado ocioso, mas ao custo de manter a CPU funcionando em velocidade máxima na thread ociosa.

* Desative o C1E no BIOS. Esta opção é importante para desativar o estado C1E no BIOS para evitar que a CPU entre no estado C1E quando ociosa. O estado C1E é um estado de baixo consumo de energia que pode introduzir latência quando a CPU está ociosa.

O restante desta documentação aborda parâmetros adicionais, incluindo huge pages e IOMMU.

Isso fornece um exemplo de argumentos de kernel para um servidor Intel de 32 núcleos, incluindo os ajustes mencionados anteriormente:

[#cpu-pinning-host]
== Fixação de CPU no Host

A fixação de CPU, também conhecida como afinidade de processador, é a técnica de vincular um processo ou thread a um núcleo de CPU específico, impedindo que o agendador do sistema operacional o mova. Ao garantir que um processo sempre seja executado no mesmo núcleo, ele se beneficia do acesso mais rápido aos dados que permanecem na memória cache desse núcleo. Essa prática é comum em ambientes de computação de alto desempenho porque melhora drasticamente o desempenho e reduz a sobrecarga.

=== Isolamento de CPUs via TuneD
`tuned` é uma ferramenta de ajuste de sistema que monitora as condições do sistema para otimizar o desempenho usando vários perfis predefinidos. Um recurso importante é sua capacidade de isolar núcleos de CPU para cargas de trabalho específicas, como aplicativos em tempo real. Isso evita que o SO utilize esses núcleos e potencialmente aumente a latência.

Para habilitar e configurar esse recurso, a primeira coisa é criar um perfil para os núcleos de CPU que queremos isolar. Neste exemplo, entre 64 núcleos, dedicamos 60 núcleos (`1-30,33-62`) para o aplicativo e os 4 núcleos restantes são usados para manutenção. Observe que o design de CPUs isoladas depende fortemente dos aplicativos em tempo real.

[,shell]
----
$ echo "export tuned_params" >> /etc/grub.d/00_tuned

$ echo "isolated_cores=1-30,33-62" >> /etc/tuned/cpu-partitioning-variables.conf

$ tuned-adm profile cpu-partitioning
Tuned (re)started, changes applied.
----

=== Isolamento de CPUs via argumentos do kernel
Em seguida, precisamos modificar a opção do GRUB para isolar os núcleos da CPU e outros parâmetros importantes para o uso da CPU.
As seguintes opções são importantes para serem personalizadas com as especificações do seu hardware atual:

[,shell]

|===
| parameter | value | descrição

| isolcpus
| domain,nohz,managed_irq,1-30,33-62
| Isole os núcleos 1-30 e 33-62. `domain` indica que essas CPUs fazem parte do domínio de isolamento. `nohz` habilita a operação sem tick nessas CPUs isoladas quando estão ociosas, para reduzir interrupções. `managed_irq` isola as CPUs fixadas de serem alvo de IRQs. Isso contempla `irqaffinity=0-7`, que já direciona a maioria das IRQs para os núcleos de manutenção.

| skew_tick
| 1
| Esta opção permite que o kernel desloque as interrupções do temporizador entre as CPUs isoladas.

| nohz
| on
| Quando habilitada, a interrupção periódica do temporizador do kernel (o 'tick') para em qualquer núcleo de CPU que se torne ocioso. Isso beneficia principalmente as CPUs de manutenção (`0,31,32,63`), conservando energia e reduzindo ativações desnecessárias nesses núcleos de uso geral.

| nohz_full
| 1-30,33-62
| Para os núcleos isolados, isso interrompe o tick e faz isso mesmo quando a CPU está executando uma única tarefa ativa. Isso significa que faz a CPU rodar em modo full tickless (ou 'dyntick'). O kernel só entregará interrupções de temporizador quando elas forem realmente necessárias.

| rcu_nocbs
| 1-30,33-62
| Esta opção descarrega o processamento de callback RCU de núcleos de CPU especificados.

| rcu_nocb_poll
| 
| Quando esta opção está definida, as CPUs sem callback RCU farão polling regularmente para verificar se o tratamento de callback é necessário, em vez de serem explicitamente despertadas por outras CPUs. Isso pode reduzir a sobrecarga de interrupção.

| irqaffinity
| 0,31,32,63
| Esta opção permite que o kernel execute as interrupções nos núcleos de manutenção.

| inativo
| Fazer poll
| Isso minimiza a latência de saída do estado ocioso, mas ao custo de manter a CPU funcionando em velocidade máxima na thread ociosa.

| nmi_watchdog
| 0
| Esta opção desativa apenas o watchdog NMI. Isso pode ser omitido quando `nowatchdog` estiver definido.

| nowatchdog
|
| Esta opção desativa o watchdog de soft-lockup, que é implementado como um temporizador executado no contexto de interrupção de hardware do temporizador.
|===

Os comandos a seguir modificam a configuração do GRUB e aplicam as alterações mencionadas acima para que estejam presentes na próxima inicialização:

Edite o arquivo `/etc/default/grub` com os parâmetros acima e o arquivo ficará assim:

[,shell]
----
GRUB_CMDLINE_LINUX="BOOT_IMAGE=/boot/vmlinuz-6.4.0-9-rt root=UUID=77b713de-5cc7-4d4c-8fc6-f5eca0a43cf9 skew_tick=1 rd.timeout=60 rd.retry=45 console=ttyS1,115200 console=tty0 default_hugepagesz=1G hugepagesz=1G hugepages=40 hugepagesz=2M hugepages=0 ignition.platform.id=openstack net.ifnames=1 intel_iommu=on iommu=pt irqaffinity=0,31,32,63 isolcpus=domain,nohz,managed_irq,1-30,33-62 nohz_full=1-30,33-62 nohz=on mce=off nosoftlockup nowatchdog nmi_watchdog=0 quiet rcu_nocb_poll rcu_nocbs=1-30,33-62 rcupdate.rcu_cpu_stall_suppress=1 rcupdate.rcu_expedited=1 rcupdate.rcu_normal_after_boot=1 rcupdate.rcu_task_stall_timeout=0 rcutree.kthread_prio=99 security=selinux selinux=1 idle=poll"
----

Atualize a configuração do GRUB:
[,shell]
----
$ transactional-update grub.cfg
$ reboot
----

Para validar que os parâmetros sejam aplicados após a reinicialização, o seguinte comando pode ser usado para verificar a linha de comando do kernel:

[,shell]
----
$ cat /proc/cmdline
----

Existe outro script que pode ser usado para ajustar a configuração da CPU e os parâmetros de rede, que basicamente realiza as seguintes etapas:

* Defina o governador da CPU como `performance`.
* Desative a migração de timer para as CPUs isoladas.
* Migre as threads kdaemon para as CPUs de manutenção.
* Defina a latência das CPUs isoladas para o menor valor possível.
* Atrase as atualizações do vmstat para 300 segundos.
* Configure os parâmetros de ajuste de rede para desempenho ideal.

O script está disponível em https://raw.githubusercontent.com/suse-edge/telco-cloud-examples/refs/heads/{release-tag-telco-cloud}/telco-examples/downstream-clusters/dhcp-less/eib/custom/files/performance-settings.sh[repositório de exemplos do SUSE Telco Cloud].

[#cpu-pinning-k8s]
== Fixação de CPU no Kubernetes

=== Versões do RKE2 < v1.32
Habilite a fixação de CPU em seu cluster RKE2 editando o arquivo de configuração do RKE2. Adicione os argumentos do kubelet abaixo no arquivo `/etc/rancher/rke2/config.yaml`. Certifique-se de especificar os núcleos de CPU de housekeeping nos argumentos `kubelet-reserved` e `system-reserved`:

[,yaml]
----
kubelet-arg:
- "cpu-manager-policy=static"
- "cpu-manager-policy-options=full-pcpus-only=true"
- "cpu-manager-reconcile-period=0s"
- "kubelet-reserved=cpu=0,31,32,63"
- "system-reserved=cpu=0,31,32,63"
----

=== Versões do RKE2 >= v1.32
Se a sua versão do RKE2 for v1.32 ou superior, argumentos de linha de comando não podem ser usados para configurar o kubelet, seguindo a prática upstream do Kubernetes. Para configurar a fixação de CPU, um arquivo de configuração do kubelet precisa ser criado. Consulte https://documentation.suse.com/cloudnative/rke2/latest/en/install/configuration.html#_kubelet_configuration[documentação do RKE2].

Crie um novo arquivo de configuração do kubelet, como `01-cpu-pinning.conf`, e coloque-o no diretório `/var/lib/rancher/rke2/agent/etc/kubelet.conf.d/`:

[,yaml]
----
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
cpuManagerPolicy: static
reservedSystemCPUs: 0,31,32,63
topologyManagerPolicy: single-numa-node
----

Para que as alterações de configuração entrem em vigor, uma reinicialização do serviço RKE2 apropriado (servidor ou agente) é necessária. Esta ação interromperá brevemente o serviço RKE2 no host. Execute apenas um dos seguintes comandos, dependendo do tipo de nó:

[,shell]
----
# If the node is RKE2 agent
systemctl restart rke2-agent
# Else if the node is RKE2 server
systemctl restart rke2-server
----

=== Implante cargas de trabalho aproveitando a fixação de CPU.

Existem três maneiras de usar o recurso usando o `Static Policy` definido no kubelet, dependendo das solicitações e limites que você define em sua carga de trabalho:

1. `BestEffort` Classe de QoS: Se você não definir nenhuma solicitação ou limite para `CPU`, o pod será agendado no primeiro `CPU` disponível no sistema.
+
Um exemplo de uso da `BestEffort` Classe de QoS poderia ser:
+
[,yaml]
----
spec:
  containers:
  - name: nginx
    image: nginx
----
+
2. `Burstable` Classe de QoS: Se você definir uma solicitação de CPU, que não é igual aos limites, ou se não houver solicitação de CPU.
+
Exemplos de uso da `Burstable` Classe de QoS poderiam ser:
+
[,yaml]
----
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
      requests:
        memory: "100Mi"
----
+
ou
+
[,yaml]
----
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "2"
      requests:
        memory: "100Mi"
        cpu: "1"
----
+
3.  `Guaranteed` Classe de QoS: Se você definir uma solicitação de CPU, que é igual aos limites.
+
Um exemplo de uso da Classe de QoS `Guaranteed` poderia ser:
+
[,yaml]
----
spec:
  containers:
    - name: nginx
      image: nginx
      resources:
        limits:
          memory: "200Mi"
          cpu: "2"
        requests:
          memory: "200Mi"
          cpu: "2"
----


[#network-parameters]
== Parâmetros de rede

O ajuste de rede é essencial para alcançar o desempenho ideal em cargas de trabalho de telecomunicações. O script performance-settings.sh inclui uma função `configure_network_tuning` que define vários parâmetros de rede do kernel para otimizar tamanhos de buffer, processamento de pacotes e desempenho de UDP.

[NOTE]
====
Os valores de ajuste de rede fornecidos são exemplos que foram testados e validados. No entanto, eles devem ser adaptados ao seu caso de uso específico, requisitos de carga de trabalho e configuração de hardware.
====

Os seguintes parâmetros de rede são configurados pelo script:

=== Parâmetros de rede principais

* `net.core.rmem_max` (1342177280 bytes): Tamanho máximo do buffer de recebimento do soquete. Este parâmetro define a quantidade máxima de memória que pode ser alocada para receber dados em qualquer soquete.

* `net.core.wmem_max` (516777216 bytes): Tamanho máximo do buffer de envio do soquete. Este parâmetro define a quantidade máxima de memória que pode ser alocada para o envio de dados em qualquer soquete.

* `net.core.rmem_default` (10000000 bytes): Tamanho padrão do buffer de recebimento do soquete. Este é o tamanho inicial do buffer para receber dados em novos soquetes.

* `net.core.wmem_default` (10000000 bytes): Tamanho padrão do buffer de envio do soquete. Este é o tamanho inicial do buffer para enviar dados em novos soquetes.

* `net.core.netdev_max_backlog` (416384 packets): Número máximo de pacotes enfileirados no lado de entrada quando a interface recebe pacotes mais rápido do que o kernel consegue processá-los. Aumentar este valor ajuda a evitar a perda de pacotes durante picos de tráfego.

* `net.core.optmem_max` (25165824 bytes): Tamanho máximo do buffer auxiliar permitido por soquete. Isso afeta o tamanho dos buffers de memória de opções.

* `net.core.netdev_budget` (1024 pacotes): Número máximo de pacotes que podem ser processados em uma execução de softirq. Isso ajuda a controlar a utilização da CPU durante o processamento de pacotes.

=== Parâmetros específicos de UDP

* `net.ipv4.udp_mem` (11416320 15221760 22832640 pages): Controla a quantidade de memória (em páginas) usada pelo UDP. Os três valores representam:
** Limite mínimo: Abaixo desse valor, o UDP não sofre pressão de memória.
** Limite de pressão: O UDP começa a aplicar pressão de memória
** Limite máximo: Máximo de páginas de memória para UDP

* `net.ipv4.udp_rmem_min` (16384 bytes): Tamanho mínimo do buffer de recebimento para soquetes UDP. Garante um tamanho de buffer básico para recepção UDP.

* `net.ipv4.udp_wmem_min` (16384 bytes): Tamanho mínimo do buffer de envio para soquetes UDP. Garante um tamanho de buffer básico para transmissão UDP.

=== Agendamento em tempo real

* `kernel.sched_rt_runtime_us` (-1): Desativa o mecanismo de limitação de tempo real. Definir isso como -1 permite tempo de CPU ilimitado para tarefas em tempo real, o que é essencial para cargas de trabalho de telecomunicações que exigem latência determinística.

[IMPORTANT]
====
Esses parâmetros são configurados automaticamente ao usar o script performance-settings.sh do repositório SUSE Telco Cloud Examples. O script deve ser integrado ao seu processo de criação de imagem conforme descrito na seção <<atip-automated-provisioning,Automated Provisioning>>.
====

=== Bond CNI
Em termos gerais, o bonding fornece um método para agregar múltiplas interfaces de rede em uma única interface lógica "bonded". Isso é normalmente usado para aumentar a disponibilidade do serviço introduzindo caminhos de rede redundantes, mas também pode ser usado para aumentar a largura de banda com certos modos de bond.
Os seguintes plug-ins CNI são suportados para o plug-in Bond CNI em combinação com o multus:

* MACVLAN
* Dispositivo do Host
* SR-IOV

==== Bond CNI com MACVLAN
Para usar o plug-in Bond CNI com MACVLAN, são necessárias duas interfaces livres no contêiner. O exemplo a seguir usa 'enp8s0' e 'enp9s0'. Comece criando definições de anexo de rede para eles:

Para usar este bond, o pod precisa conhecer todas as interfaces. Uma definição de pod de exemplo pode ser assim:

[,shell,subs="attributes"]
----

        k8s.v1.cni.cncf.io/networks: '[
{"name": "enp8s0-conf",
"interface": "net1"

{"name": "enp9s0-conf",
"interface": "net2"

"interface": "bond0"

  restartPolicy: Never

      - "-c"
      - "sleep 60m"

Observe como a anotação se refere a todas as redes e como ela define o mapeamento entre as interfaces 'enp8s0 -> net1' e 'enp9s0 -> net2'.

==== Bond CNI com SR-IOV
Usar o Bond CNI com SR-IOV é bastante simples. Para mais detalhes sobre como configurar o SR-IOV, consulte <<sriov>>. Conforme descrito lá, você deve criar `SriovNetworkNodePolicies` que define `resourceNames`, bem como o número de funções virtuais e afins. [#sriov]
== SR-IOV

SR-IOV (Single Root I/O Virtualization) permite que um único dispositivo físico, como um adaptador de rede, separe seus recursos entre múltiplas `PCIe` funções de hardware. Isso permite acesso direto aos recursos para várias aplicações.

Fornecemos dois métodos distintos para implantar `SR-IOV` em seu cluster:

* <<option1-sriov-deviceplugin>>: Este método oferece suporte a dispositivos de rede e acelerador vRAN.
* <<option2-sriov-helm>>: Este método automatizado proporciona uma implantação mais simples. Este método é apenas para dispositivos de rede.

Em casos raros em que você precisa de ambas as soluções - usando o Operador de Rede para dispositivos de rede e o Plugin de Dispositivo para Aceleradores vRAN - você deve implantá-los em namespaces separados do Kubernetes. Essa separação é essencial para evitar conflitos entre as duas implantações.

O Plugin de Dispositivo SR-IOV usa um configMap contendo um arquivo JSON para definir quais recursos de hardware o Kubernetes deve expor. Esta configuração baseia-se em dois conceitos principais: `selectors` (para descoberta de hardware) e `resources` (para exposição no Kubernetes).

Um `resource` é a entidade nomeada que os pods consomem (por exemplo, `rancher.io/intel_fec_5g`). Os recursos podem ser definidos como um de dois tipos:

* `accelerator`: Usado para placas aceleradoras vRAN (como ACC100/vRAN Boost).
* `netdevice`: Usado para interfaces de rede padrão (NICs).

Você define os dispositivos de destino usando `selectors` para filtrar o hardware no nó:

* `vendors`: `8086` (Intel)
* `devices`: `57c3` (FEC VF), `1889` (NIC VF)
* `drivers`: `vfio-pci`
* `pfNames`: `eno16595np0` (nome da interface física)

Para placas de rede, você também pode selecionar um subconjunto de Funções Virtuais (VFs) de uma Função Física:

* `pfNames`: `["eth1#1,2,3,4,5,6"]` ou `[eth1#1-6]`

Para permitir que os pods solicitem os dispositivos, cada recurso deve ter um nome, que é composto por um prefixo e um nome:

* `resourceName`: `pci_sriov_net_bh_dpdk`
* `resourcePrefix`: `rancher.io`

Os pods então solicitariam o nome do recurso combinado: `rancher.io/pci_sriov_net_bh_dpdk`.

[NOTE]
====
Este documento não lista todos os seletores possíveis. Diferentes tipos de recursos usam diferentes conjuntos de seletores. Para detalhes abrangentes, consulte o https://github.com/k8snetworkplumbingwg/sriov-network-device-plugin[repositório do SR-IOV Network Device Plugin].

[#dpdk]
== DPDK

`DPDK` (Data Plane Development Kit) é um conjunto de bibliotecas e drivers para processamento rápido de pacotes. Ele é usado para acelerar cargas de trabalho de processamento de pacotes executadas em uma ampla variedade de arquiteturas de CPU.
O DPDK inclui bibliotecas de plano de dados e drivers otimizados para a placa de interface de rede (`NIC`) para os seguintes fins:

1. Um gerenciador de filas implementa filas sem bloqueio.
2. Um gerenciador de buffers pré-aloca buffers de tamanho fixo.
3. Um gerenciador de memória aloca pools de objetos na memória e usa um anel para armazenar objetos livres; garante que os objetos sejam distribuídos igualmente em todos os canais `DRAM`.
4. Drivers de modo de polling (`PMD`) são projetados para funcionar sem notificações assíncronas, reduzindo a sobrecarga.
5. Uma estrutura de pacotes consiste em um conjunto de bibliotecas que auxiliam no desenvolvimento do processamento de pacotes.

As etapas a seguir mostrarão como habilitar `DPDK` e como criar `VFs` a partir do `NICs` para serem usados pelas interfaces `DPDK`:

[#acceleration]
== Aceleração vRAN (`Intel ACC100/VRB1/VRB2`)

À medida que os provedores de serviços de comunicação migram de redes 4G para 5G, muitos estão adotando arquiteturas de rede de acesso via rádio virtualizada (vRAN) para maior capacidade de canal e implantação mais fácil de serviços e aplicações baseados em borda. As soluções vRAN estão idealmente localizadas para fornecer serviços de baixa latência com a flexibilidade de aumentar ou diminuir a capacidade com base no volume de tráfego em tempo real e na demanda na rede.

Uma das cargas de trabalho 4G e 5G que mais consomem processamento é a camada 1 de RAN (`L1`) `FEC`, que resolve erros de transmissão de dados em canais de comunicação não confiáveis ou ruidosos. A tecnologia `FEC` detecta e corrige um número limitado de erros em dados 4G ou 5G, eliminando a necessidade de retransmissão. Como a transação de aceleração `FEC` não contém informações de estado da célula, ela pode ser facilmente virtualizada, permitindo benefícios de agrupamento e fácil migração de células.

Historicamente, a Intel fornecia a placa aceleradora vRAN ACC100 para executar rapidamente algoritmos FEC de Camada 1, liberando poder de processamento do host para a CPU principal. Desde então, a Intel integrou essa tecnologia diretamente em CPUs mais novas, começando com Sapphire Rapids, sob o nome `Intel vRAN Boost` (VRB). O Intel vRAN Boost atua como um acelerador de descarregamento na própria CPU, eliminando a necessidade de uma placa de hardware separada. Esta seção detalha a configuração do SUSE Telco Cloud para que as cargas de trabalho aproveitem o ACC100 ou o Intel vRAN Boost.

[#huge-pages]
== Huge pages

Quando um processo usa `RAM`, o `CPU` marca a porção exata utilizada por esse processo. Para alcançar eficiência, o `CPU` aloca `RAM` em blocos conhecidos como `pages`; o tamanho padrão de `page` em muitas plataformas é `4 KB`. Páginas podem ser trocadas para o disco (entre outras operações).

Como o espaço de endereçamento do processo é virtual, o `CPU` e o sistema operacional devem manter o controle de quais `pages` pertencem a cada processo e onde cada um está armazenado. Quanto maior o número de `pages`, mais tempo leva para consultar os mapeamentos de memória. Por exemplo, um processo usando `1 GB` de memória envolve 262.144 entradas para verificar (1 GB / 4 KB). Se cada `page table entry` ocupa 8 bytes, isso resulta em um total de `2 MB` (262.144 * 8) de dados a serem consultados.

A maioria das arquiteturas de `CPU` atuais permite a definição de blocos de `pages` cada um com um tamanho maior que o valor padrão de `4 KB` (sendo `1 GB` e `2 MB` valores típicos suportados) conhecidos como `huge pages`, o que reduz o número de entradas que o `CPU/Operating System` deve consultar.

* Parâmetros kernel

Para habilitar `huge pages`, devemos adicionar os seguintes parâmetros do kernel. Neste exemplo, configuramos 40 páginas de tamanho `1 GB` cada e 0 páginas de tamanho `2 MB` cada, embora os tamanhos de páginas grandes a serem suportados e a quantidade exata de páginas para cada caso devam ser ajustados de acordo com os requisitos de memória do seu aplicativo.

|===
| parameter | value | descrição

| hugepagesz
| 1G
| Esta opção permite definir o tamanho de "huge pages" para 1 GB

| hugepages
| 40
| Este é o número de "huge pages" solicitadas para alocar na inicialização para o tamanho definido logo antes (1 GB)

| hugepagesz
| 2M
| Esta opção permite definir o tamanho de "huge pages" para 2 MB

| hugepages
| 0
| Este é o número de "huge pages" solicitadas para alocar na inicialização para o tamanho definido logo antes (2 MB)

| default_hugepagesz
| 1G
| Este é o valor padrão para o tamanho de "huge pages"
|===

Modifique o arquivo GRUB `/etc/default/grub` para adicionar estes parâmetros em `GRUB_CMDLINE_LINUX`:

[,shell]
----
default_hugepagesz=1G hugepagesz=1G hugepages=40 hugepagesz=2M hugepages=0
----

Atualize a configuração do GRUB e reinicie o sistema para aplicar as alterações:

[,shell]
----
$ transactional-update grub.cfg
$ reboot
----

Para validar que os parâmetros foram aplicados após a reinicialização, você pode verificar a linha de comando:

[,shell]
----
$ cat /proc/cmdline
----

* Usando huge pages

Para usar as huge pages, precisamos montá-las:

[,shell]
----
$ mkdir -p /hugepages
$ mount -t hugetlbfs nodev /hugepages
----

Implante uma carga de trabalho do Kubernetes, criando os recursos e os volumes:

[,yaml]
----
...
 resources:
   requests:
     memory: "24Gi"
     hugepages-1Gi: 16Gi
     intel.com/intel_sriov_oru: '4'
   limits:
     memory: "24Gi"
     hugepages-1Gi: 16Gi
     intel.com/intel_sriov_oru: '4'
...
----

[,yaml]
----
...
volumeMounts:
  - name: hugepage
    mountPath: /hugepages
...
volumes:
  - name: hugepage
    emptyDir:
      medium: HugePages
...
----


[#numa-aware-scheduling]
== Agendamento com reconhecimento de NUMA

O acesso não uniforme à memória ou a arquitetura de memória não uniforme (`NUMA`) é um design de memória física usado na arquitetura `SMP` (multiprocessadores), em que o tempo de acesso à memória depende da sua localização em relação a um processador. Sob `NUMA`, um processador pode acessar sua própria memória local mais rapidamente do que a memória não local, ou seja, memória local para outro processador ou memória compartilhada entre processadores.

=== Identificando nós NUMA

Para identificar os nós `NUMA`, em seu sistema use o seguinte comando:

[,shell]
----
$ lscpu | grep NUMA
NUMA node(s):                       1
NUMA node0 CPU(s):                  0-63
----

[NOTE]
====
Para este exemplo, temos apenas um nó `NUMA` mostrando 64 `CPUs`.

`NUMA` precisa ser habilitado no `BIOS`. Se `dmesg` não tiver registros da inicialização NUMA durante a inicialização, as mensagens relacionadas a `NUMA` no buffer de anel do kernel podem ter sido sobrescritas.
====

[#private-registry]
== Configuração de registro privado

`Containerd` pode ser configurado para se conectar a registros privados e usá-los para extrair imagens privadas em cada nó.

Na inicialização, `RKE2` verifica se um arquivo `registries.yaml` existe em `/etc/rancher/rke2/` e instrui `containerd` a usar quaisquer registros definidos no arquivo. Se você deseja usar um registro privado, crie este arquivo como root em cada nó que usará o registro.

Para adicionar o registro privado, crie o arquivo `/etc/rancher/rke2/registries.yaml` com o seguinte conteúdo:

[,yaml]
----
mirrors:
  docker.io:
    endpoint:
      - "https://registry.example.com:5000"
configs:
  "registry.example.com:5000":
    auth:
      username: xxxxxx # this is the registry username
      password: xxxxxx # this is the registry password
    tls:
      cert_file:            # path to the cert file used to authenticate to the registry
      key_file:             # path to the key file for the certificate used to authenticate to the registry
      ca_file:              # path to the ca file used to verify the registry's certificate
      insecure_skip_verify: # may be set to true to skip verifying the registry's certificate
----

ou sem autenticação:

[,yaml]
----
mirrors:
  docker.io:
    endpoint:
      - "https://registry.example.com:5000"
configs:
  "registry.example.com:5000":
    tls:
      cert_file:            # path to the cert file used to authenticate to the registry
      key_file:             # path to the key file for the certificate used to authenticate to the registry
      ca_file:              # path to the ca file used to verify the registry's certificate
      insecure_skip_verify: # may be set to true to skip verifying the registry's certificate
----

Para que as alterações no registro entrem em vigor, você precisa realizar a configuração deste arquivo antes de iniciar o RKE2 no nó ou reiniciar o RKE2 em cada nó configurado.

[NOTE]
====
Para obter mais informações sobre isso, verifique https://documentation.suse.com/cloudnative/rke2/latest/en/install/containerd_registry_configuration.html#_registries_configuration_file[configuração do registro do containerd rke2].

[#ptp-configuration]
== Precision Time Protocol

[#ptp-introduction]
=== Introdução

O Precision Time Protocol (PTP), definido pelo padrão IEEE 1588, distribui tempo de alta precisão através de uma rede de pacotes. Quando as interfaces de rede (NICs) registram o carimbo de data/hora de pacotes PTP em hardware, ele atinge uma precisão de sub-microssegundos, muito além do que o NTP pode oferecer. Em ambientes de telecomunicações, o PTP é um bloco de construção central das redes de acesso via rádio (RAN) 5G, onde as unidades de rádio exigem alinhamento rigoroso de fase e tempo para transmitir corretamente. O SUSE Telco Cloud implementa PTP através do pacote `linuxptp` e tem como alvo os perfis de telecomunicações ITU-T G.8275.1 e ITU-T G.8275.2 descritos abaixo.

Um domínio PTP é construído a partir de um pequeno conjunto de funções de relógio:

* *Grandmaster (GM)*: a fonte primária de tempo para o domínio. Ele normalmente é sincronizado com um Primary Reference Time Clock (PRTC), geralmente controlado por um receptor GNSS, e transmite o tempo para os nós a jusante. A precisão do GM define o teto de qualidade para todo o domínio.
* *Ordinary Clock (OC)*: um nó final com uma única porta PTP. Em uma implantação de telecomunicações, ele atua como receptor de tempo, disciplinando seu relógio local a partir de um Grand Master ou Boundary Clock a montante. Um nó de computação executando uma carga de trabalho de rádio é um OC típico.
* *Boundary Clock (BC)*: um nó multiporta que recebe tempo em uma porta (receptor de tempo) e o regenera para outros nós em suas portas restantes (transmissor de tempo). A inserção de Boundary Clocks ao longo do caminho encurta o caminho entre cada OC e a referência, limitando o erro que a rede acumularia salto após salto.

A distinção entre um Ordinary Clock e um Boundary Clock é central ao projetar a topologia:

* Um *Ordinary Clock* possui uma *única* porta PTP e fica na borda do domínio.
Ele apenas consome tempo para disciplinar seu próprio relógio e nunca encaminha tempo para outros nós.
* Um *Boundary Clock* possui *múltiplas* portas PTP. Ele consome tempo em sua porta de receptor de tempo e *o regenera* em suas portas de transmissor de tempo, encerrando a cadeia de temporização upstream e iniciando uma nova downstream. Essa regeneração é o que evita que erros se acumulem ao longo de uma longa cadeia de nós.

Os seguintes elementos de hardware e sinalização suportam essas funções:

* *Relógio de Hardware PTP (PHC)*: o relógio integrado à NIC que o PTP realmente sincroniza. Alinhar o relógio do sistema operacional ao PHC é uma etapa separada tratada por um daemon dedicado.
* *Ethernet Síncrona (SyncE)*: sincronização de frequência na camada física. O PTP transporta fase e tempo dentro de pacotes, enquanto o SyncE recupera uma frequência estável diretamente do sinal Ethernet. O SyncE é um *aprimoramento opcional*: O PTP por si só já fornece fase e tempo, e o SyncE é adicionado apenas quando um nó precisa de maior estabilidade de frequência e maior tempo de espera caso a fonte de tempo PTP seja perdida temporariamente.
* *Loop de Travamento de Fase Digital (DPLL)*: um bloco de temporização de hardware que trava em um sinal de referência e o filtra para gerar um relógio estável e limpo. É ele que disciplina o PHC a partir das entradas disponíveis e, em plataformas com mais de uma NIC, mantém os diferentes relógios das NICs alinhados.

Em cada nó, essas funções são realizadas pelos daemons `linuxptp`: `ptp4l` executa o protocolo PTP e disciplina o PHC, e `phc2sys` alinha o relógio do sistema ao PHC. Em um Grandmaster, `ts2phc` adicionalmente controla o PHC a partir da referência GNSS. Suas funções e instalação são abordadas em <<ptp-prerequisites>>.

O relógio de hardware em si é gerenciado pelo subsistema DPLL do kernel Linux em conjunto com o driver de rede. O grau de controle de temporização, e como a temporização é distribuída dentro de um nó com múltiplas NICs, depende de onde o DPLL gerenciável está localizado:

* *NIC com um DPLL integrado*: o DPLL está incorporado na NIC e é configurado através do subsistema DPLL do Linux. Ele seleciona e trava na referência escolhida e disciplina o PHC, oferecendo controle total da frequência e do holdover.
* *NIC sem um DPLL integrado*: a NIC não expõe nenhum DPLL configurável. `ptp4l` disciplina o PHC diretamente, e o subsistema pode, no máximo, relatar o status de travamento (somente leitura); o manuseio avançado de frequência, então, depende de uma fonte de temporização externa.
* *DPLL embarcado compartilhado entre várias NICs*: o DPLL não está embutido em uma única NIC, mas reside na plataforma, externo às NICs. Ele disciplina e mantém os PHCs de várias NICs alinhados a partir de uma referência comum, para que cada NIC no nó compartilhe o mesmo tempo. Este arranjo é usado em plataformas multi-NIC que distribuem a temporização internamente em vez de depender de cabeamento externo.

As redes de telecomunicações padronizam dois perfis ITU-T, que diferem principalmente no transporte utilizado e em quanto da rede subjacente deve ser compatível com PTP:

* *ITU-T G.8275.1* (suporte total de temporização): roda diretamente sobre Ethernet (Camada 2) usando multicast. Cada nó ao longo do caminho deve ser compatível com PTP e atuar como um Boundary Clock, o que proporciona a maior precisão. A menos que indicado de outra forma, os cenários neste guia usam este perfil.
* *ITU-T G.8275.2* (suporte parcial de temporização): roda sobre IP (Camada 3) usando unicast.
Nós intermediários não precisam suportar PTP, portanto a temporização pode cruzar segmentos de rede que não são compatíveis com temporização, ao custo de uma precisão menor.

[#ptp-prerequisites]
=== Pré-requisitos

Este guia cobre apenas perfis específicos de telecomunicações, portanto, assume-se o uso de carimbo de data/hora por hardware e um relógio de hardware PTP (PHC) na NIC. Adaptadores de rede de nível de telecomunicações fornecem suporte a PTP em hardware; você pode confirmar os recursos de uma determinada interface com `ethtool -T`:

[,console]
----
# ethtool -T eno16495np0
Time stamping parameters for eno16495np0:
Capabilities:
        hardware-transmit
        software-transmit
        hardware-receive
        software-receive
        software-system-clock
        hardware-raw-clock
PTP Hardware Clock: 0
Hardware Transmit Timestamp Modes:
        off
        on
Hardware Receive Filter Modes:
        none
        all
----

Verifique os recursos `hardware-transmit`, `hardware-receive` e `hardware-raw-clock` e um índice `PTP Hardware Clock` de 0 ou superior (um valor de `-1` significa que a interface não possui PHC). Substitua `eno16495np0` pela interface que você pretende usar para PTP.

O PTP está incluído no pacote `linuxptp`. Ele disponibiliza três programas de espaço do usuário — `ptp4l`, `phc2sys` e `ts2phc` — que são executados como daemons de longa duração gerenciados pelo `systemd` (um serviço dedicado para cada: `ptp4l.service`, `phc2sys.service` e `ts2phc.service`). Coletivamente, eles executam o protocolo e mantêm os relógios sincronizados:

* `ptp4l`: o daemon PTP. Ele executa o protocolo IEEE 1588 nas interfaces configuradas, aplica o Best Master Clock Algorithm (BMCA) para determinar a função de cada porta e disciplina o PHC da NIC. Uma única instância de `ptp4l` pode gerenciar várias portas, o que permite que um nó atue como um Boundary Clock.
* `phc2sys`: sincroniza dois relógios. Ele é normalmente usado para alinhar o relógio do sistema (sistema operacional) ao PHC que o `ptp4l` mantém sincronizado, para que a hora do sistema também siga o PTP.
* `ts2phc`: "time stamp to PHC". Ele disciplina o PHC a partir de um sinal de tempo externo, como o PPS fornecido por um receptor GNSS. Ele é usado em um Grandmaster e para manter múltiplos PHCs alinhados dentro do mesmo nó.

A maneira recomendada de instalar o PTP em um cluster downstream é adicionar o pacote `linuxptp` ao `packageList` do arquivo de definição do Edge Image Builder (EIB), para que ele seja implantado automaticamente durante o provisionamento. Veja a xref:../quickstart/eib.adoc#eib-configuring-rpm-packages[documentação do EIB] para obter mais informações sobre a instalação de pacotes.

[,yaml,subs="attributes"]
----
apiVersion: {version-eib-api-latest}
image:
  imageType: RAW
  arch: x86_64
  baseImage: {micro-base-rt-image-raw}
  outputImageName: eibimage-slmicrort-telco.raw
operatingSystem:
  systemd:
    enable:
      - ptp4l
      - phc2sys
  packages:
    packageList:
      - linuxptp
    sccRegistrationCode: $SCC_REGISTRATION_CODE
----

[NOTE]
====
O pacote `linuxptp` não habilita `ptp4l`, `phc2sys` ou `ts2phc` por padrão.
Após implantar os arquivos de configuração, use a seção `systemd` do manifesto para habilitar os daemons de nó necessários (veja os cenários abaixo).
====

Finalmente, o perfil PTP em uso determina se os switches de rede entre os nós devem ser configurados como dispositivos compatíveis com PTP:

* *ITU-T G.8275.1 (suporte total de temporização)*: é executado diretamente sobre Ethernet (Camada 2) usando multicast. Cada nó ao longo do caminho deve ser compatível com PTP e atuar como um Boundary Clock, o que proporciona a maior precisão; portanto, os switches intermediários devem ser configurados para PTP. A menos que indicado de outra forma, os cenários neste guia usam este perfil.
* *ITU-T G.8275.2 (suporte parcial de temporização)*: é executado sobre IP (Camada 3) usando unicast.
Nós intermediários não precisam oferecer suporte ao PTP, portanto, o tempo pode atravessar segmentos de rede que não são sensíveis ao tempo e os switches não precisam de configuração de PTP, ao custo de menor precisão.

[#ptp-scenario-oc]
=== Cenário 1a - Ordinary Clock (apenas PTP)

*Explicação*

Esta é a implantação de PTP mais simples: um único nó de cluster consome tempo de uma fonte upstream e disciplina seus relógios locais, sem nunca encaminhar o tempo para outro nó. O nó é executado como um Ordinary Clock (OC) com uma única porta PTP na função de Time Receiver.

No nó OC, o tempo é tratado inteiramente pelos daemons `linuxptp`, independentemente do perfil em uso. Nenhuma configuração de DPLL ou `ts2phc` é necessária, porque o nó usa uma única NIC e o `ptp4l` disciplina seu PHC diretamente:

* O `ptp4l` executa o protocolo PTP na interface de recepção. O Best Master Clock Algorithm (BMCA) seleciona o nó upstream como mestre, a porta local transita para o estado `SLAVE` e o `ptp4l` disciplina o PTP Hardware Clock (PHC) da NIC.
Definir `clientOnly 1` restringe o nó à função de Time Receiver, portanto, ele nunca pode ser selecionado como mestre.
* O `phc2sys` alinha o relógio do sistema (`CLOCK_REALTIME`) ao PHC que o `ptp4l` mantém sincronizado, para que o horário do sistema operacional também siga o PTP.

O cenário pode ser implementado com qualquer um dos perfis de telecomunicações. Eles diferem no transporte e no que a rede interveniente deve fornecer, e estão documentados abaixo como dois modelos independentes:

* *<<ptp-scenario-oc-model1,Modelo 1 — ITU-T G.8275.1>>* (multicast de Camada 2): use-o quando cada salto entre o mestre e o OC for compatível com PTP. Ele oferece a maior precisão e é o padrão para implantações de telecomunicações.
* *<<ptp-scenario-oc-model2,Modelo 2 — ITU-T G.8275.2>>* (unicast de Camada 3): use-o quando o OC precisar alcançar o mestre através de uma rede que não é compatível com PTP, ao custo de menor precisão.

[IMPORTANT]
====
Um Ordinary Clock executa um único perfil PTP por vez. Os dois modelos são mutuamente exclusivos: configure apenas um deles em um determinado nó. Crie apenas o arquivo de configuração do perfil escolhido e referencie apenas esse arquivo em `/etc/sysconfig/ptp4l`. Não crie ambos `/etc/ptp4l-G.8275.1.conf` e `/etc/ptp4l-G.8275.2.conf`, e nunca passe ambos os arquivos para a linha `OPTIONS=`.
====

[[ptp-scenario-oc-model1]]
*Modelo 1 — ITU-T G.8275.1 (multicast de Camada 2)*

O G.8275.1 é executado diretamente sobre Ethernet e endereça suas mensagens ao MAC multicast não encaminhável `01:80:C2:00:00:0E`, que bridges padrão não encaminham, portanto, cada dispositivo no caminho deve terminar e regenerar o PTP. Os componentes são:

* *Grandmaster (GM)*: a referência upstream para o domínio PTP (domínio `24` para G.8275.1), tipicamente travada em uma fonte GNSS/PRTC.
* *PTP-aware switch*: atua como um Boundary Clock. Sua porta em direção ao GM é um Time Receiver e sua porta em direção ao OC é um Time Transmitter. Ambas as portas devem estar com o PTP habilitado.
* *Ordinary Clock (OC)*: o nó do cluster, recebendo tempo em sua única porta PTP.

.Ordinary Clock (OC) — G.8275.1 (multicast de Camada 2)
image::product-atip-ptp-scenario-oc.png[Cenário 1a - Ordinary Clock (apenas PTP) com G.8275.1,scaledwidth=100%]

Configure o nó da seguinte forma:

. Identifique o índice PHC `<N>` da interface usada para PTP (aqui `eno8403np1`); o valor do campo impresso `PTP Hardware Clock` (que também pode aparecer como `Hardware timestamp provider index`) fornece o dispositivo `/dev/ptp<N>` que o `ptp4l` disciplina e que o `phc2sys` lê como sua fonte:
+
[,console]
----
# ethtool -T eno8403np1
Time stamping parameters for eno8403np1:
Capabilities:
        hardware-transmit
        hardware-receive
        hardware-raw-clock
PTP Hardware Clock: 1
...
----
+
Neste exemplo, o PHC de `eno8403np1` é `/dev/ptp1`.

. Crie o `ptp4l`arquivo de configuração `/etc/ptp4l-G.8275.1.conf`. A interface é declarada como uma seção (`[eno8403np1]`), portanto, o daemon não precisa da flag `-i`:
+
[#ptp-conf-oc-g8275-1]
.Configuração de Relógio Comum — ITU-T G.8275.1
====
[source,]
----
# Telecom G.8275.1 — Ordinary Clock (Time Receiver)
[global]
domainNumber                    24
priority2                       255
dataset_comparison              G.8275.x
G.8275.portDS.localPriority     128
G.8275.defaultDS.localPriority  128
maxStepsRemoved                 255
logAnnounceInterval             -3
logSyncInterval                 -4
logMinDelayReqInterval          -4
announceReceiptTimeout          3
clientOnly                      1
ptp_dst_mac                     01:80:C2:00:00:0E
network_transport               L2
summary_interval                3
message_tag                     "ptp4l"
uds_address                     /var/run/ptp4l
uds_ro_address                  /var/run/ptp4lro

[eno8403np1]
----
====
+
O valor `ptp_dst_mac` é fixo para G.8275.1: é o endereço multicast não encaminhável `01:80:C2:00:00:0E` que confina o PTP a um único link e é a razão pela qual cada dispositivo no caminho deve ser compatível com PTP. O `uds_address` expõe um socket de gerenciamento que o `phc2sys` usa para acompanhar o estado da porta.

. Aponte `ptp4l` para este arquivo em `/etc/sysconfig/ptp4l`:
+
[source,]
----
OPTIONS="-f /etc/ptp4l-G.8275.1.conf"
----

. Configure `phc2sys` em `/etc/sysconfig/phc2sys` para disciplinar o relógio do sistema a partir do PHC da interface PTP (`/dev/ptp1`). Os valores `--uds_address` e `--domainNumber` devem corresponder à configuração `ptp4l`:
+
[source,]
----
OPTIONS="-s /dev/ptp1 -w -m --uds_address /var/run/ptp4l --domainNumber 24"
----
+
`-s /dev/ptp1` seleciona o PHC como o relógio de origem, `-w` aguarda `ptp4l` para sincronizar antes de ajustar o relógio do sistema, e `-m` imprime o status do servo no log.

. Habilite e inicie ambos os serviços:
+
[,console]
----
# systemctl enable --now ptp4l phc2sys
----

. Verifique se `ptp4l` travou no upstream master. A porta muda para `SLAVE` e o offset relatado (`rms`) converge para um valor baixo e estável:
+
[,console]
----
# journalctl -u ptp4l -f
ptp4l[...]: "ptp4l" port 1 (eno8403np1): UNCALIBRATED to SLAVE on MASTER_CLOCK_SELECTED
ptp4l[...]: "ptp4l" rms 1502498567 max 8499416372 freq  -3977 +/- 43609 delay  11 +/- 607
ptp4l[...]: "ptp4l" rms   40 max   99 freq +10129 +/-   30 delay 211 +/-   3
ptp4l[...]: "ptp4l" rms    7 max   15 freq +10125 +/-   13 delay 211 +/-   2
ptp4l[...]: "ptp4l" rms    6 max   16 freq +10118 +/-   12 delay 213 +/-   2
----

. Verifique se `phc2sys` está disciplinando o relógio do sistema. O estado do servo progride de `s0` (desbloqueado) através de `s1` (passo inicial) para `s2` (travado), e o offset estabiliza em torno de zero:
+
[,console]
----
# journalctl -u phc2sys -f
phc2sys[...]: CLOCK_REALTIME phc offset 45583145631 s0 freq   -1673 delay   0
phc2sys[...]: CLOCK_REALTIME phc offset 45583157513 s1 freq  +10207 delay   0
phc2sys[...]: CLOCK_REALTIME phc offset          4 s2 freq  +10211 delay   0
phc2sys[...]: CLOCK_REALTIME phc offset         13 s2 freq  +10221 delay   0
----
+
Um estado `s2` estável com um pequeno offset confirma que o nó está travado e o relógio do sistema está seguindo o PTP.

*Modelo 2 — ITU-T G.8275.2 (unicast de Camada 3)*

O G.8275.2 é executado sobre IP (Camada 3) usando unicast: o OC troca mensagens diretamente com o endereço IP do master, portanto a rede interveniente não precisa ser compatível com PTP e nenhum switch habilitado para PTP é necessário. Os componentes são:

* *Master (GM ou Boundary Clock)*: o master upstream, acessível por IP no domínio G.8275.2 (domínio `44`).

[#ptp-scenario-bc-single-nic]
=== Cenário 2a - Relógio de Fronteira (apenas PTP) com NIC única multiporta, incluindo propagação para servidor de Relógio Comum

*Explicação*

Este cenário estende a cadeia de temporização com um Relógio de Fronteira (BC) que regenera o PTP em direção a um Relógio Comum (OC) downstream, inteiramente sobre ITU-T G.8275.1 (apenas PTP, Camada 2). O BC usa uma única NIC multiporta: uma instância de `ptp4l` gerencia várias portas na mesma NIC, portanto, nem `ts2phc` nem roteamento DPLL são necessários (ao contrário dos cenários de múltiplas NICs).

O cenário envolve os seguintes componentes:

* *Grandmaster (GM)*: a referência para o domínio PTP (domínio `24`), normalmente travado em uma fonte GNSS/PRTC (a bancada de teste usada aqui não possui GNSS, daí o `gm.ClockClass` degradado mostrado mais adiante). Ele envia o tempo no segmento upstream.
* *Switch compatível com PTP*: atua como um Relógio de Fronteira (T-BC) no caminho de temporização; cada porta que transporta PTP possui `ptp enable`.
* *Relógio de Fronteira (servidor BC)*: um nó multiporta em uma única NIC que faz a ponte entre dois segmentos PTP. Sua porta `eno8403np1` está voltada para o segmento *upstream* como um Receptor de Tempo (SLAVE) e disciplina o PHC da NIC; `eno8503np2` (e `eno8603np3`) estão voltadas para o segmento *downstream* como Transmissores de Tempo que regeneram o PTP. O BC termina a cadeia de temporização upstream e inicia uma nova downstream.
* *Relógio Comum (servidor OC)*: um nó de porta única (`ens6f0np0`) no segmento *downstream*, onde seu único mestre PTP é o BC. Ele disciplina seus relógios locais a partir do tempo que o BC regenera.

A temporização é gerenciada pelos daemons `linuxptp` em cada nó:

* No *BC server*, uma única instância `ptp4l` gerencia todas as suas portas. O BMCA seleciona o GM como mestre em `eno8403np1`, que muda para `SLAVE` e disciplina o PHC. `eno8503np2` e `eno8603np3` são forçados a `serverOnly 1`, portanto, eles atuam apenas como Transmissores de Tempo.
Como todas as portas compartilham o mesmo PHC da NIC, o tempo recebido está diretamente disponível para as portas de transmissão; um Boundary Clock é implícito automaticamente quando mais de uma porta é configurada, portanto, nenhuma configuração `clock_type` ou `ts2phc` é necessária.
* No *OC server*, `ptp4l` é executado com `clientOnly 1` em `ens6f0np0`, portanto, a porta atua apenas como um Receptor de Tempo. `phc2sys` alinha o relógio do sistema ao PHC.
* No servidor OC, `clientOnly 1` é o que garante que ele nunca se torne um mestre. O atributo `localPriority` — usado pelo BMCA G.8275.x apenas como critério de desempate, quando clockClass, clockAccuracy, variance e priority2 são iguais, onde um valor menor é preferido — reforça essa ordenação: o servidor BC mantém o `128` padrão, enquanto o servidor OC usa o `250` de menor preferência.

O BC faz a ponte entre dois segmentos PTP separados: um segmento *upstream* entre o GM e sua porta `eno8403np1`, e um segmento *downstream* entre sua porta `eno8503np2` e o OC. Eles são mantidos separados, por exemplo, em VLANs diferentes do switch ou em redes separadas. Como o BC é o único mestre no segmento downstream, o OC sincroniza a partir do BC e nunca diretamente do GM.

Como no <<ptp-scenario-oc,Scenario 1a>>, este cenário usa o MAC multicast não encaminhável `01:80:C2:00:00:0E`; bridges padrão não o encaminham, portanto, cada dispositivo compatível com PTP termina e regenera o PTP. O mesmo endereço deve ser definido em cada nó do caminho de temporização.

.O Boundary Clock (apenas PTP), NIC única, com propagação para um Ordinary Clock

*Configuração*

Cada porta de switch no caminho de temporização (em direção ao GM, ao BC e ao OC) deve estar com o PTP habilitado. Os dois nós do cluster são então configurados da seguinte forma.

*Boundary Clock (servidor BC)*

. Identifique o PHC da NIC PTP (`ethtool -T eno8403np1`); em uma única NIC, todas as portas compartilham o mesmo PHC. Neste exemplo, é `/dev/ptp1`.

. Crie `/etc/ptp4l-G.8275.1.conf`. A porta receptora `[eno8403np1]` não tem flag de função, então o BMCA a seleciona como Time Receiver; `[eno8503np2]` e `[eno8603np3]` são definidos como `serverOnly 1` para atuar como Time Transmitters. Declarar mais de uma porta implica um Boundary Clock:
+
[#ptp-conf-bc-single-nic-bc]

====
[source,]
----

[global]

priority2                       255
dataset_comparison              G.8275.x

G.8275.defaultDS.localPriority  128

summary_interval                3

uds_address                     /var/run/ptp4l
uds_ro_address                  /var/run/ptp4lro

[eno8403np1]

[eno8503np2]
serverOnly                      1

[eno8603np3]
serverOnly                      1
----
====

. Aponte `ptp4l` para este arquivo em `/etc/sysconfig/ptp4l`:
+
[source,]
----

----

. Opcionalmente, alinhe o relógio do sistema com `phc2sys` em `/etc/sysconfig/phc2sys`, usando o PHC da NIC compartilhada como fonte:
+
[source,]
----
OPTIONS="-s /dev/ptp1 -w -m --uds_address /var/run/ptp4l --domainNumber 24"
----

. Habilite e inicie os serviços e verifique se `eno8403np1` está sincronizado com o GM. A porta receptora muda para `SLAVE` e o offset (`rms`) converge para um valor baixo:
+
[,console]

# journalctl -u ptp4l -f

ptp4l[...]: "ptp4l" port 1 (eno8403np1): UNCALIBRATED to SLAVE on MASTER_CLOCK_SELECTED
ptp4l[...]: "ptp4l" rms    8 max   24 freq +10092 +/-  18 delay   211 +/-   2
ptp4l[...]: "ptp4l" rms    4 max   11 freq +10069 +/-   7 delay   210 +/-   2
ptp4l[...]: "ptp4l" rms    3 max    9 freq +10070 +/-   6 delay   213 +/-   3
----

. Identifique o PHC da interface PTP (`ethtool -T ens6f0np0`); neste exemplo, é `/dev/ptp1`.

. Crie `/etc/ptp4l-G.8275.1.conf` com uma única porta e `clientOnly 1`, para que o nó atue apenas como Time Receiver. O `localPriority` mais alto (`250`) o mantém abaixo do BC no BMCA :

+
[source,]
----
# /etc/sysconfig/ptp4l
OPTIONS="-f /etc/ptp4l-G.8275.1.conf"

# /etc/sysconfig/phc2sys
OPTIONS="-s /dev/ptp1 -w -m --uds_address /var/run/ptp4l --domainNumber 24"
----

. Verifique se `ens6f0np0` está sincronizado com o tempo regenerado do BC. A porta muda para `SLAVE` e o offset (`rms`) estabiliza:
+
[,console]
----
# journalctl -u ptp4l -f
ptp4l[...]: "ptp4l" selected best master clock d0460c.ffff.05c130
ptp4l[...]: "ptp4l" port 1 (ens6f0np0): UNCALIBRATED to SLAVE on MASTER_CLOCK_SELECTED
ptp4l[...]: "ptp4l" rms   15 max   34 freq +11699 +/-  25 delay   468 +/-   5
ptp4l[...]: "ptp4l" rms   13 max   30 freq +11701 +/-  23 delay   468 +/-   4
ptp4l[...]: "ptp4l" rms   14 max   30 freq +11697 +/-  24 delay   467 +/-   4
----
+
O OC obtém seu tempo do Boundary Clock upstream, que é seu mestre imediato.
A linha `selected best master clock`, no entanto, relata a identidade do *Grandmaster* (`d0460c.ffff.05c130`, o GM) e não a do Boundary Clock: um Boundary Clock encaminha a identidade do Grandmaster inalterada enquanto anuncia sua própria porta como o pai, para que a cadeia permaneça rastreável até o Grandmaster. Para ver ambas as identidades explicitamente, consulte o conjunto de dados pai no OC (exemplo de saída):
+
[,console]
----
# pmc -f /etc/ptp4l-G.8275.1.conf -u -b 0 'GET PARENT_DATA_SET'
sending: GET PARENT_DATA_SET
    507c6f.fffe.4ae178-0 seq 0 RESPONSE MANAGEMENT PARENT_DATA_SET
        parentPortIdentity                    000000.fffe.001101-2
        parentStats                           0
        observedParentOffsetScaledLogVariance 0xffff
        observedParentClockPhaseChangeRate    0x7fffffff
        grandmasterPriority1                  128
        gm.ClockClass                         165
        gm.ClockAccuracy                      0xfe
        gm.OffsetScaledLogVariance            0xffff
        grandmasterPriority2                  120
        grandmasterIdentity                   d0460c.ffff.05c130
----
+
As duas identidades diferem, o que é exatamente o que uma implantação de Boundary Clock deve mostrar:
+
* `parentPortIdentity` (`000000.fffe.001101-2`) — o *mestre imediato*: a porta de transmissão do Boundary Clock, o clock do qual o OC realmente recebe o tempo.
* `grandmasterIdentity` (`d0460c.ffff.05c130`) — a *raiz da árvore de temporização*: o Grandmaster, encaminhado inalterado através do Boundary Clock.
+
Os valores `gm.ClockClass`, `gm.ClockAccuracy` e `grandmasterPriority` carregam a qualidade anunciada do Grandmaster usada pelo BMCA. Se as duas identidades fossem iguais, o OC estaria sincronizando diretamente de um Grandmaster, sem nenhum Boundary Clock no caminho.

=== Cenário 3a - Boundary Clock (apenas PTP) multi-NIC com módulo de temporização interno (DPLL baseado em GNR-D)

*Explicação*

{product} suporta temporização precisa em uma variedade de plataformas, incluindo os projetos mais recentes baseados em Intel Granite Rapids-D (GNR-D). Esses servidores normalmente incluem um controlador Ethernet de alta velocidade integrado e uma ou mais placas adicionais (AICs) com um controlador Ethernet para portas extras. Ao contrário das gerações de plataforma anteriores, eles também são equipados com um DPLL dedicado que roteia os sinais de temporização através do sistema e das diferentes NICs internamente, não exigindo mais cabeamento externo para manter todos os PHCs das NICs sincronizados.
A implantação geral é, portanto, simplificada, mas etapas e componentes de software específicos são necessários, como o DPLL no momento da inicialização e a configuração do sinal interno.

Este cenário estende o <<ptp-scenario-bc-single-nic,Cenário 2a>> para um Boundary Clock (BC) construído em várias NICs, inteiramente sobre ITU-T G.8275.1 (apenas PTP, Camada 2). Uma porta do controlador integrado recebe PTP do Grandmaster e as placas adicionais regeneram o PTP downstream. Ao contrário do caso de NIC única, cada NIC tem seu próprio PHC; o DPLL integrado e `ts2phc` os mantêm alinhados, e uma instância de `ptp4l` é executada por PHC.

[IMPORTANT]
====
Nesta versão {product}, este cenário é suportado apenas para a variante de kernel "default" (ou seja, não "PREEMPT_RT").
O suporte para a variante de kernel "RT" será adicionado em uma versão futura.
====

.Pré-requisitos
* Baixe e instale o driver de kernel mais recente para os _Intel 800 Series Network Devices_ a partir do https://www.intel.com/content/www/us/en/download/19630/intel-network-adapter-driver-for-800-series-devices-under-linux.html[site da Intel].
* Selecione o arquivo zip contendo os "ice_RPM_Files", descompacte o arquivo e instale o `ice-kmp-default-*sles16sp0.x86_64.rpm`. Este RPM contém, por exemplo, `ice-kmp-default-2.4.5_k6.12.0_160000.5-1.sles16sp0.x86_64.rpm`:
+
[,console]
----
# transactional-update pkg install ice-kmp-default-2.4.5_k6.12.0_160000.5-1.sles16sp0.x86_64.rpm
----
+
Reinicie o servidor para tornar a alteração persistente e efetiva.

[NOTE]
====
* Um sistema Dell PowerEdge XR8720t é usado como sistema de referência nos exemplos; as interfaces de kernel e a configuração de porta podem ser diferentes em um servidor GNR-D diferente. Ajuste os nomes dos dispositivos de acordo.
* Assume-se uma implantação de telco e o arquivo de controle de telco G.8275.1 é usado nas seções a seguir.
====

O cenário envolve os seguintes componentes:

* *Grandmaster (GM)*: a referência para o domínio PTP (domínio `24`), no segmento upstream.
* *Switch compatível com PTP*: atua como um Relógio de Fronteira (T-BC) no caminho de temporização; cada porta que transporta PTP possui `ptp enable`. Os segmentos upstream e downstream são mantidos separados em VLANs diferentes do switch (uma VLAN dedicada para cada segmento).
* *Boundary Clock (BC server)*: o nó GNR-D. Seu controlador integrado recebe PTP do GM em `eno8403np1` e disciplina o PHC integrado (`/dev/ptp1`). O DPLL integrado distribui esse tempo para as placas add-in e `ts2phc` mantém seus PHCs (`/dev/ptp2`, `/dev/ptp3`) alinhados com `/dev/ptp1`. Cada placa add-in regenera o PTP downstream (por exemplo, em `eno16495np0`), atuando como um Transmissor de Tempo.
* *Ordinary Clock (OC server)*: um nó de porta única (`ens6f0np0`) no segmento downstream, cujo único mestre PTP é o BC.

O tempo no *BC server* é gerenciado por vários daemons `linuxptp` trabalhando juntos, porque os PHCs são fisicamente separados:

* Uma instância de `ptp4l` no controlador integrado (`/dev/ptp1`) executa o protocolo PTP em `eno8403np1`. O BMCA seleciona o GM como mestre, a porta muda para `SLAVE` e `ptp4l` disciplina `/dev/ptp1`.
* O DPLL integrado é cabeado de modo que o PHC integrado o controle através dos pinos SDP, e o DPLL, por sua vez, controla os relógios das placas add-in. Este é o substituto interno para o cabeamento 1PPS externo usado em plataformas anteriores.
* `ts2phc` mantém os PHCs das placas add-in alinhados a `/dev/ptp1` a partir do sinal que o DPLL distribui.
* Uma instância `ptp4l` separada por placa add-in (`/dev/ptp2`, `/dev/ptp3`) regenera o PTP em suas portas, todas forçadas para `serverOnly 1` (Time Transmitters).
* Um Boundary Clock deve encaminhar os atributos auxiliares do Grandmaster (classe de relógio, precisão, etc.) além do tempo. Isso acontece automaticamente apenas dentro de uma única instância `ptp4l`, portanto, `pmc` é usado para encaminhar esses valores da instância integrada para as instâncias add-in (veja o passo 5). `pmc` (cliente de gerenciamento PTP) é a ferramenta `linuxptp` que consulta e atualiza o estado de runtime de uma instância `ptp4l` em execução através de seu socket de gerenciamento.

[NOTE]
====
No controlador integrado, apenas *uma* de suas portas é a porta administrativa que gerencia o PHC. Inspecione `/sys/class/ptp/ptp1/device/net/` para encontrá-la (por exemplo, `eno8703np0`); é a porta usada para configurar os sinais DPLL, e não é necessariamente a porta que transporta PTP (`eno8403np1`).
====

[NOTE]
====
A configuração descrita aqui é completamente estática. Se o GM ficar indisponível, a sincronização downstream dependerá exclusivamente das capacidades de holdover do host; nenhuma alternância automática para uma fonte diferente de referência de tempo será realizada.
====

. Configure os sinais de temporização internos (DPLL).
+
Conecte o PHC integrado ao DPLL e deixe o DPLL alimentar as placas add-in, usando a porta administrativa encontrada acima (`eno8703np0`) e os índices `ptpN` corretos:
+
[#gnrd-startup-setup]
.`01-gnrd-startup-setup.sh`
====
[source,bash]
----
#!/bin/bash

# The admin port that manages the PHC is under /sys/class/ptp/ptp1/device/net/ (e.g. eno8703np0).
# Only one port of the integrated E825-C NIC exposes it.

# Let the DPLL drive the Ethernet clock on the integrated controller
echo 4 1 > /sys/class/net/eno8703np0/device/tspll_cfg

# Feed the DPLL from the integrated PHC through the SDP pins:
# SDP0 -> 1 pulse per second (1PPS, 1 Hz): enable the pin, then set a 1 s period
echo 2 2 > /sys/class/ptp/ptp1/pins/SDP0
echo 2 0 0 1 0 > /sys/class/ptp/ptp1/period

# SDP2 -> 1000 pulses per second (1kPPS, 1 kHz): enable the pin, then set a 1 ms period
echo 2 1 > /sys/class/ptp/ptp1/pins/SDP2
echo 1 0 0 0 1000000 > /sys/class/ptp/ptp1/period

# Propagate the pulses from the DPLL to the add-in cards (SDP1 on each add-in PHC)
echo 1 1 > /sys/class/ptp/ptp2/pins/SDP1
echo 1 1 > /sys/class/ptp/ptp3/pins/SDP1
----
====
+
Essas configurações são perdidas na reinicialização, portanto, execute o script na inicialização a partir de uma unidade `systemd` do tipo oneshot, ordenada antes de `ts2phc` e `ptp4l`:
+
[source,ini]
----
# /etc/systemd/system/gnrd-ptp-dpll-setup.service
[Unit]
Description=GNR-D PTP DPLL and internal signal setup
Before=ts2phc.service ptp4l@nac.service ptp4l@aic1.service ptp4l@aic2.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/bin/01-gnrd-startup-setup.sh

[Install]
WantedBy=multi-user.target
----

. Alinhe os PHCs das placas add-in com `ts2phc`.
+
`ts2phc` ("time stamp to PHC") alinha os PHCs das placas add-in a um relógio de referência. Aqui, a referência é o PHC da NIC integrada (`/dev/ptp1`, já disciplinado pelo GM através de sua instância `ptp4l`), passado na linha de comando com `-s /dev/ptp1`. O DPLL integrado fornece o 1PPS derivado dessa referência para cada placa add-in em seu pino `SDP1`; `ts2phc` registra o carimbo de data/hora desses pulsos de entrada (EXTTS) e ajusta o PHC de cada placa add-in de acordo, para que todos os PHCs no nó acabem compartilhando o mesmo tempo.
+
[NOTE]
====
O alinhamento dos PHCs das placas add-in requer duas configurações complementares, em níveis diferentes:

* *Hardware*: o pino de entrada `SDP1` de cada PHC da placa add-in deve ser habilitado para que o DPLL integrado entregue o pulso 1PPS a ele. Isso é feito no script de configuração do DPLL da etapa anterior (`echo 1 1 > /sys/class/ptp/ptpN/pins/SDP1`).
* *Software*: o `ts2phc` deve ser instruído a registrar o carimbo de data/hora dessa entrada e ajustar o PHC. É isso que a configuração abaixo faz (`ts2phc.channel`, `ts2phc.pin_index`, `ts2phc.extts_polarity`).

Sem habilitar o pino, o pulso nunca chega ao PHC; sem a configuração `ts2phc`, o pulso nunca é aplicado a ele. Ambos são necessários.
====
+
Crie seu arquivo de configuração:
+
[#gnrd-ts2phc-config]
.`/etc/ts2phc-cf-all.cfg` — arquivo de configuração `ts2phc`
====
[source,]
----
[global]
use_syslog              0
verbose                 1
logging_level           7
ts2phc.pulsewidth       100000000

[eno16495np0]
ts2phc.channel          1
ts2phc.extts_polarity   rising
ts2phc.pin_index        1

[eno16595np0]
ts2phc.channel          1
ts2phc.extts_polarity   rising
ts2phc.pin_index        1
----
====
+
Cada placa add-in é configurada por meio de uma seção nomeada após sua primeira porta (`[eno16495np0]`, `[eno16595np0]`), que identifica o PHC a ser disciplinado. Os parâmetros mapeiam o pulso do DPLL para essa placa add-in:
+
* `ts2phc.pin_index` e `ts2phc.channel`: o pino e o canal onde o DPLL entrega o 1PPS (`SDP1` nesta configuração, portanto `pin_index 1`).
* `ts2phc.extts_polarity`: a borda do pulso a ser registrada (`rising`).
* `ts2phc.pulsewidth`: a largura de pulso de entrada esperada, em nanossegundos (100 ms aqui).
+
Execute-o manualmente como `ts2phc -f /etc/ts2phc-cf-all.cfg -s /dev/ptp1 -m`, ou deixe `systemd` gerenciá-lo através de `/etc/sysconfig/ts2phc`:
+
[source,]
----
# /etc/sysconfig/ts2phc
OPTIONS="-f /etc/ts2phc-cf-all.cfg -s /dev/ptp1 -m"
----

. Execute uma instância `ptp4l` por PHC.
+
O controlador integrado executa uma instância orientada por BMCA (o receptor), e cada placa add-in executa uma instância com todas as portas forçadas para `serverOnly 1`. Cada instância deve usar um socket de controle e um socket somente leitura diferentes. Crie os três arquivos de configuração:
+
[#gnrd-ptp4l-config-nac]

====
[source,]

[eno8403np1]

====
+
A instância integrada declara apenas `eno8403np1`, a porta que recebe PTP do GM, e não define `serverOnly` ou `clientOnly` nela: ela depende do BMCA para atribuir a função. Com um GM alcançável em `eno8403np1`, o BMCA o seleciona como o Receptor de Tempo (`SLAVE`) e disciplina `/dev/ptp1`. As outras portas do controlador integrado não são declaradas, porque neste nó a downstream regeneração é realizada pelas placas add-in em vez do controlador integrado. As placas add-in, em contraste, forçam `serverOnly 1` porque devem ser sempre Transmissores de Tempo — elas obtêm seu tempo do DPLL e `ts2phc`, não recebendo PTP, portanto, nunca devem ser eleitas como receptores. Se for necessário um controle mais rigoroso, adicione a flag `serverOnly` ou `clientOnly` explicitamente sob a interface.
+
Os valores de `G.8275.portDS.localPriority` e `G.8275.defaultDS.localPriority` (`128` na instância integrada, `250` nas placas add-in) atuam como um desempate BMCA G.8275.x: eles são comparados apenas após `clockClass`, `clockAccuracy`, variância e `priority2`, e um valor menor é preferido. Manter o `128` padrão na instância integrada faz com que ela supere as instâncias add-in (`250`), o que mantém a ordenação Transmissor de Tempo/Receptor de Tempo dentro do nó determinística e direciona qual porta o BMCA elege, conforme refletido nos estados de porta relatados por `ptp4l`.

. Encaminhe os parâmetros do Grandmaster através das instâncias `ptp4l`.
+
Um Boundary Clock deve encaminhar não apenas o tempo, mas também os parâmetros auxiliares do Grandmaster (classe de clock, precisão, offset UTC, e assim por diante). Isso acontece automaticamente entre portas da *mesma* instância `ptp4l`, mas não entre as instâncias separadas que gerenciam PHCs diferentes. Os valores são aplicados em tempo de execução com `pmc` sobre o socket UDS de cada instância (`SET GRANDMASTER_SETTINGS_NP`).
+
[IMPORTANT]
====
Os valores aplicados com `pmc` são mantidos apenas no processo `ptp4l` em execução; eles *não* são gravados no arquivo `.conf` e *não* sobrevivem a uma reinicialização. Se uma instância `ptp4l` for reiniciada, ela reverte para os padrões do arquivo e os valores devem ser encaminhados novamente. Automatize o encaminhamento (veja abaixo) em vez de executá-lo manualmente uma vez.
====
+
Assim que o controlador integrado estiver bloqueado no GM, consulte os valores do Grandmaster. O auxiliar abaixo usa o arquivo de configuração da instância a ser consultada como seu argumento:
+
[#gnrd-get-pmc-values]
.`get_pmc_values.sh` — consultar os valores do Grandmaster de uma instância `ptp4l`
====
[source,bash]
----
#!/bin/bash
# Retrieve Grandmaster information via pmc for the given ptp4l config file
set -euo pipefail

echo "PARENT_DATA_SET (Grandmaster clock values):"
pmc -f "$1" -u -b 0 'GET PARENT_DATA_SET' | grep gm

echo "TIME_PROPERTIES_DATA_SET:"
pmc -f "$1" -u -b 0 'GET TIME_PROPERTIES_DATA_SET'
----
====
+
Em seguida, encaminhe esses valores para as instâncias add-in. O script a seguir lê os valores da instância integrada e os aplica a cada instância add-in. Edite a seção "Input variables" para corresponder aos nomes dos arquivos de configuração e execute-o assim que o sistema estiver sincronizado com um GM:
+
[#gnrd-pmc-forward]
.`04-ptp-forward-GM.sh` — encaminhar os valores do Grandmaster para as instâncias add-in
====
[source,bash]
----
#!/bin/bash

set -euo pipefail

################## Input variables ##################
VERBOSE=1

CONFIG_FILE_NAC=/etc/ptp4l-nac.conf
CONFIG_FILES_AICS=(/etc/ptp4l-aic1.conf /etc/ptp4l-aic2.conf)

#####################################################


# Check the system is synchronized to a GM
GM_PRESENT=$(pmc -f ${CONFIG_FILE_NAC} -u -b 0 'GET TIME_STATUS_NP' | awk '/gmPresent/ {print $2}')

if [ -z "$GM_PRESENT" ]; then
    echo "Failed to get GM value from ptp4l instance for NAC, exiting..."
    exit 1
elif [ "${GM_PRESENT}" != "true" ]; then
    echo "No GM present, exiting..."
    exit 1
fi

# Get the "upstream" Grandmaster values
PDS_GM_VALUES=$(pmc -f ${CONFIG_FILE_NAC} -u -b 0 'GET PARENT_DATA_SET' | awk 'BEGIN {ORS=" "} /gm./ {print $2}')
TPDS_GM_VALUES=$(pmc -f ${CONFIG_FILE_NAC} -u -b 0 'GET TIME_PROPERTIES_DATA_SET' | awk 'BEGIN {ORS=" "} NR>2 {print $2}')

if [ -z "$PDS_GM_VALUES" ]; then
    echo "No PARENT_DATA_SET values retrieved, exiting ..."
    exit 2
elif [ -z "$TPDS_GM_VALUES" ]; then
    echo "No TIME_PROPERTIES_DATA_SET values retrieved, exiting ..."
    exit 2
fi

# Unpack from PARENT_DATA_SET
read CLOCK_CLASS CLOCK_ACCURACY VARIANCE <<< $PDS_GM_VALUES

# Unpack from TIME_PROPERTIES_DATA_SET
read UTC_OFFSET LEAP_61 LEAP_59 UTC_OFFSET_VALID PTP_TIMESCALE T_TRACEABLE F_TRACEABLE T_SOURCE <<< $TPDS_GM_VALUES

if [ "$VERBOSE" -eq 1 ]; then
    echo "Read from PARENT_DATA_SET: clockClass=${CLOCK_CLASS} clockAccuracy=${CLOCK_ACCURACY} offsetScaledLogVariance=${VARIANCE}"
    echo "Read from TIME_PROPERTIES_DATA_SET: currentUtcOffset=${UTC_OFFSET} leap61=${LEAP_61} leap59=${LEAP_59}" \
         "currentUtcOffsetValid=${UTC_OFFSET_VALID} ptpTimescale=${PTP_TIMESCALE} timeTraceable=${T_TRACEABLE}" \
         "frequencyTraceable=${F_TRACEABLE} timeSource=${T_SOURCE}"
fi


# Forward these values to the "downstream" Time Receivers, updating the ptp4l instances
for FILE in "${CONFIG_FILES_AICS[@]}"; do
    if [ "$VERBOSE" -eq 1 ]; then
        echo "Updating GRANDMASTER_SETTINGS_NP (${FILE})"
    fi

    pmc -f ${FILE} -u -b 0 'SET GRANDMASTER_SETTINGS_NP
       clockClass              '${CLOCK_CLASS}'
       clockAccuracy           '${CLOCK_ACCURACY}'
       offsetScaledLogVariance '${VARIANCE}'
       currentUtcOffset        '${UTC_OFFSET}'
       leap61                  '${LEAP_61}'
       leap59                  '${LEAP_59}'
       currentUtcOffsetValid   '${UTC_OFFSET_VALID}'
       ptpTimescale            '${PTP_TIMESCALE}'
       timeTraceable           '${T_TRACEABLE}'
       frequencyTraceable      '${F_TRACEABLE}'
       timeSource              '${T_SOURCE}'' &> /dev/null

    if [ $? -ne 0 ]; then
        echo "Failed to update ptp4l instance using config file \"${FILE}\", exiting ..."
        exit 1
    fi
done
----
====
+
Como os valores não são persistentes, execute este script a partir de um timer `systemd` para que sejam atualizados periodicamente e após qualquer reinicialização de instância:
+
[source,ini]
----
# /etc/systemd/system/ptp-forward-gm.service
[Unit]
Description=Forward Grandmaster parameters to the add-in ptp4l instances
Wants=ptp4l@nac.service ptp4l@aic1.service ptp4l@aic2.service

== SCTP - Stream Control Transmission Protocol
De https://en.wikipedia.org/wiki/Stream_Control_Transmission_Protocol[Stream Control Transmission Protocol - Wikipedia]

[quote]
____
O Stream Control Transmission Protocol (SCTP) é um protocolo de comunicação de rede de computadores na camada de transporte do conjunto de protocolos da Internet.
Originalmente destinado ao transporte de mensagens do Signaling System 7 (SS7) em telecomunicações, o protocolo fornece o recurso orientado a mensagens do User Datagram Protocol (UDP), garantindo ao mesmo tempo o transporte confiável e em sequência de mensagens com controle de congestionamento, como o Transmission Control Protocol (TCP).
Ao contrário do UDP e do TCP, o protocolo suporta multihoming e caminhos redundantes para aumentar a resiliência e a confiabilidade.

O SCTP é padronizado pela Internet Engineering Task Force (IETF) no RFC 9260. A implementação de referência do SCTP foi lançada como parte da versão 7 do FreeBSD e, desde então, foi amplamente portada para outras plataformas.
____

Nas especificações 3GPP 4G (LTE), o SCTP (Stream Control Transmission Protocol) atua como o transporte fundamental da Camada 4 para mensagens de sinalização do plano de controle em todo o Evolved Packet Core (EPC), incluindo a conexão de sinalização com o domínio da Radio Access Network (RAN). As especificações 3GPP 5G, por outro lado, removeram a necessidade de SCTP dentro da Core Network através da introdução da Service Based Architecture (SBA), que substitui todas as interfaces de sinalização baseadas em Diameter-over-SCTP por HTTP/2. No entanto, ele ainda é necessário dentro do domínio 5G RAN:

* nas interfaces de sinalização entre os elementos de rede que compõem uma instância gNodeB "desagregada" (interface F1-C entre DU e CU-CP e interface E1 entre CU-CP e CU-UP).

* na interface Xn-C que conecta instâncias gNodeB para fins de sinalização.

* no ponto de referência N2 (também conhecido como NG-C) usado para conectar instâncias gNodeB (domínio RAN) com instâncias AMF (domínio Core Network) para fins de sinalização.

Em seguida, você deve habilitar o módulo do kernel `sctp` do Linux (`lksctp`) nos nós de cluster downstream que hospedam as cargas de trabalho de telecomunicações compatíveis com SCTP que o utilizam:

* Para carregar manualmente o módulo do kernel `sctp` em um nó Linux:

[,shell]
----
$ sudo modprobe sctp
----

* Para automatizar o carregamento do módulo do kernel `sctp` a cada inicialização do nó, crie um arquivo chamado `sctp.conf` no diretório `/etc/modules-load.d/` que contenha simplesmente a string `sctp` (ou seja, o nome do módulo do kernel que a unidade https://www.freedesktop.org/software/systemd/man/latest/modules-load.d.html[systemd-modules-load.service] deve carregar na inicialização).

[,shell]
----
$ echo "sctp" > /etc/modules-load.d/sctp.conf
$ reboot
----

A maneira mais fácil e melhor de garantir que o módulo do kernel `sctp` seja carregado a cada inicialização do nó é adicionar esse arquivo `/etc/modules-load.d/sctp.conf` à imagem bruta criada com o Edge Image Builder (EIB) usada para provisionar nós downstream; consulte a xref:../quickstart/eib.adoc#adding-operating-system-files[documentação do Edge Image Builder (EIB)] para obter mais informações sobre como fazer isso.
